### 1.1 思谋科技 — C++ 开发

**Q1: C++ 基本特征？**

**A**: 面向对象三大特征：封装（public/protected/private 访问控制）、继承（代码复用 + is-a 关系）、多态（虚函数 + 运行时动态绑定）。C++11 后核心新特性：move 语义、智能指针、lambda、auto/decltype、constexpr、variadic templates。C++ 核心优势：零开销抽象 + 精细内存控制 + 与硬件接口（CUDA）的原生对接。

---

**Q2: 智能指针用过哪几种？shared_ptr vs unique_ptr 区别？**

**A**: 三种：unique_ptr（独占所有权，零开销）、shared_ptr（共享所有权，引用计数）、weak_ptr（观察 shared_ptr 不增计数，打破循环引用）。

区别：
| 对比项 | unique_ptr | shared_ptr |
|--------|-----------|------------|
| 所有权 | 独占 | 共享 |
| 拷贝 | 禁止（= delete） | 允许（引用计数 +1） |
| 大小 | 1 指针（= 裸指针） | 2 指针（对象 + control block） |
| 开销 | 零 | 每次拷贝/析构 atomic 操作 |
| 选择原则 | **优先使用** | 仅在需要共享所有权时 |

---

**Q3: unique_ptr 独占怎么保证？**

**A**: 编译期强制——删除了拷贝构造函数和拷贝赋值运算符（`= delete`）。只允许 move 构造和 move 赋值。试图拷贝 `unique_ptr` 会直接编译报错。

---

**Q4: shared_ptr 引用计数原理？对象间怎么共享？control block 结构？**

**A**: Control block（堆上分配，~16-32 字节）包含：
- `use_count`（强引用计数）: 拷贝 +1，析构 -1（atomic 操作）
- `weak_count`（弱引用计数）: weak_ptr 拷贝 +1
- `deleter`: 自定义删除器
- `allocator`: 内存分配器

生命周期：use_count → 0 → 调用 deleter 销毁对象；weak_count 也 → 0 → 销毁 control block 本身。

`make_shared<T>(args)` 一次分配 control block + 对象（内存局部性好，减少一次 `new`）。

---

**Q5: 多态用过吗？virtual 背后机制？**

**A**: 虚函数多态机制：
1. 每个含 `virtual` 的类有一张 **vtable**（函数指针数组，编译期生成，存在 .rodata 段）
2. 每个对象头部有 **vptr**（8 字节指针）指向其所属类的 vtable
3. 调用虚函数 → 通过 vptr 找 vtable → 取对应 slot 的函数指针 → 间接调用

子类 override → vtable 中对应 slot 替换为子类函数地址。

项目实例：`DeviceAllocator` 基类定义 `allocate()/free()` 虚函数 → `NvidiaAllocator`（cudaMalloc）和 `MetaxAllocator`（macaMalloc）子类各自实现。

---

**Q6: 父类析构函数能否 virtual？不声明会怎样？**

**A**: **必须 virtual**。不声明 → `delete 基类指针` 时只调基类析构函数，不调子类析构 → 子类资源泄漏（未定义行为）。

经验法则：
- 有虚函数的类 → 析构函数**必须** virtual
- 无继承用途的类 → **不要** virtual（避免 vptr 8 字节空间开销 + 间接调用开销）

---

**Q7: 深浅拷贝区别？**

**A**: 浅拷贝：复制指针值（两个对象指向同一块内存）→ 析构时 double free。深拷贝：重新分配内存 + 复制内容 → 两个独立副本。

现代 C++ 准则：
- **Rule of Zero**（首选）: 全用智能指针管理资源，不手写任何特殊函数
- **Rule of Five** (C++11): 手动管理资源时必须同时实现：析构、拷贝构造、拷贝赋值、move 构造、move 赋值

---

**Q8: move 原理？任意对象都能 move 吗？**

**A**: `std::move` 将左值转为右值引用（xvalue），触发 move 构造/赋值 → **资源转移**（交换内部指针）而非深拷贝。旧对象进入 valid-but-unspecified 状态。

**不是任意对象都能 move**：
- 需有 move ctor/assign（编译器可隐式生成，但若自定义了拷贝构造则不会自动生成）
- 内置类型（int/float/指针）move = copy（无资源可转移）
- 没有 move ctor 会 fallback 到拷贝构造（不报错但无性能收益）

---

**Q9: vector 底层？unordered_map 底层？map 底层？**

**A**:
| 容器 | 底层结构 | 查找 | 特点 |
|------|---------|------|------|
| `vector` | 连续内存动态数组 (size/capacity/data 三指针) | O(1) 随机访问 | 扩容 2× → 摊还 O(1) push_back |
| `unordered_map` | 哈希表（开链法, 每 bucket 一个链表） | O(1) 平均 | 负载因子 > 1 触发 rehash |
| `map` | 红黑树（自平衡 BST） | O(log n) | 有序遍历，迭代器稳定 |

---

**Q10: 内存对齐是什么？**

**A**: CPU 按字长（4/8 字节）一次读取内存。未对齐的访问可能需两次读取 + 拼接 → 性能下降或直接 fault。

编译器自动对齐：struct 成员按各自 `alignof` 对齐，struct 末尾 padding 到最大对齐倍数。`alignas(N)` 手动指定对齐。

CUDA 也有对齐要求：全局内存按 128 字节事务访问（32 线程 × 4 字节 = 128 字节 coalesced）。

---

**Q11: new vs malloc 区别？**

**A**:
| 对比项 | `new` | `malloc` |
|--------|-------|----------|
| 步骤 | 分配 + 调用构造函数 | 只分配原始字节 |
| 返回 | `T*`（类型安全） | `void*`（需强转） |
| 失败 | 抛 `std::bad_alloc` | 返回 `NULL` |
| 配套释放 | `delete`（调析构 + 释放） | `free`（只释放） |
| 可重载 | `operator new` / placement new | 不可重载 |

**不可混用** new/free 或 malloc/delete。

---

**Q12: 手撕: 写一个线程安全的队列**

**A**:
```cpp
template<typename T>
class ThreadSafeQueue {
    std::queue<T> q_;
    mutable std::mutex mtx_;
    std::condition_variable cv_;
public:
    void push(T val) {
        std::lock_guard<std::mutex> lk(mtx_);
        q_.push(std::move(val));
        cv_.notify_one();  // 唤醒一个等待线程
    }
    T pop() {  // 阻塞式
        std::unique_lock<std::mutex> lk(mtx_);
        cv_.wait(lk, [this]{ return !q_.empty(); });
        T val = std::move(q_.front());
        q_.pop();
        return val;
    }
    bool try_pop(T& val) {  // 非阻塞
        std::lock_guard<std::mutex> lk(mtx_);
        if (q_.empty()) return false;
        val = std::move(q_.front());
        q_.pop();
        return true;
    }
};
```

要点：push 用 `lock_guard`（RAII），pop 用 `unique_lock` + `condition_variable::wait`（需 unlock/relock）。

### 1.2 AIRS — 深度学习模型部署优化实习生

**Q1: 为什么做手写算子(矩阵乘)？**

**A**: 三个层面：
1. **学习目的**: 理解 CUDA 并行编程、Shared Memory Tiling、Bank Conflict 消除、Warp 调度等底层优化原理
2. **优化理解**: 逐层加优化（SMEM Tiling → Bank Conflict Free → Double Buffer → 向量化）理解 cuBLAS/CUTLASS 的优化思路和性能边界
3. **工程价值**: 项目中 Linear 最终走 cuBLAS（生产最优解），但理解底层有助于 profiling 和 debug。手写 SGEMM 达到 cuBLAS ~60% 性能

---

**Q2: FlashAttention V2 原理与解决的瓶颈？**

**A**: **瓶颈**: 标准 Attention 产生 O(N²) 的 QK^T scores 矩阵，需写回 HBM 做 Softmax 再读回 → N=32K 时 HBM 读写成为主要瓶颈。

**FlashAttention 原理**: Tiled Online Softmax——将 K/V 分 Bc 大小的块，逐块在 SRAM 中计算局部 softmax（tracking running max & running sum），用数学恒等式递推合并全局 softmax，无需完整 N×N 矩阵。

**V2 改进**: 优化非因果 mask 时的计算量 + 更好的 warp 间分工。

**核心收益**: IO 复杂度 O(N²) → O(N²d/M)（M=SRAM 大小），SRAM 内完成所有中间计算，只写最终 output 到 HBM。

---

**Q3: INT8 对称量化与 per-channel 具体算法步骤？**

**A**: Per-channel 对称量化（W8A16）步骤：
1. 对权重矩阵每一行（output channel）计算 `scale = max(|w_row|) / 127`
2. 量化：`q = round(w / scale)`，clamp 到 [-128, 127]，存为 int8
3. 推理时反量化：`w_fp16 = q * scale` 还原到 FP16
4. GEMM 走 `cublasGemmEx` FP16 Tensor Core

优势：权重内存减半（FP16 2.4GB → INT8 1.2GB），Decode Memory-Bound 时直接加速。

---

**Q4: 激活值优化？GPTQ / AWQ 原理？**

**A**:
- **GPTQ**（二阶量化）: 利用 Hessian 矩阵信息逐列量化——量化一列权重后，将量化误差**最优补偿**到尚未量化的列（OBQ 框架），显著降低量化损失。适合 INT4/INT3 极低 bit 量化。
- **AWQ**（激活感知量化）: 观察到 ~1% 的 salient channels（对应激活值大的通道）对精度影响极大 → 对 salient channels 乘放大因子 s 保护精度，其余正常量化。核心洞察：**保护少数关键通道 > 全局优化量化参数**。
- 两者都是 **weight-only** post-training 方案，不需要重新训练。

### 1.3 足下科技 — HPC 实习生（AI 芯片方向）

#### 一面

**Q1: bank conflict 除了 padding 还有什么办法？**

**A**: 三种方法：
1. **Padding**（项目采用）: `sA[T][T+1]`，步长与 32 互质 → 0 conflict。简单但浪费 ~3% SMEM
2. **Swizzle/XOR**（CUTLASS 采用）: 存取时 `col ^ row` 置换列地址→ 每 thread 访问不同 bank，零额外空间
3. **转置布局**: 改变 SMEM 矩阵存储方式，使计算时的访问模式从列跳跃变为行连续

> 详见本文 §2 深度 Q&A "Bank Conflict" 条目有完整原理图解。

---

**Q2: nsys 和 ncu 怎么定位分析？关注什么指标？**

**A**:
- **nsys profile**: 看 GPU timeline → 定位 kernel 占比、CPU-GPU 空隙（launch overhead / H2D 同步等待）。关注：GPU 活跃率、kernel 耗时分布
- **ncu** 分析单个 kernel: 关注 **SM Throughput %** 和 **Memory Throughput %** → 判断 Compute-Bound 还是 Memory-Bound
  - **Stall Reasons**: Memory Throttle / Instruction Fetch / Execution Dependency → 精准定位瓶颈
  - **Roofline 图**: 直观显示 kernel 距硬件天花板的差距和优化方向

---

**Q3: FlashAttention v2 怎么将 O(N²) 降到 O(Bc×Bc)？为什么比标准 attention 快？**

**A**: SMEM 一次只装 Bc 行的 K/V（如 Bc=32），局部 scores 矩阵大小 = d_head × Bc → SMEM 用量 O(Bc²) 而非 O(N²)。通过 online softmax（tracking running max + running sum）逐块累加，数学等价于全局 softmax。

比标准 attention 快的**根因**: 减少 HBM 读写。Standard 需读写 N×N scores 矩阵回 HBM；FlashAttention 全程在 SMEM/Reg 完成 softmax，只写最终 output O(N×d) 到 HBM。

---

**Q4: INT8 143x 加速比怎么测出来的？做了哪些优化？为什么一开始那么慢？**

**A**: 初始 0.4 tok/s，瓶颈定位：每次 Forward 对整个权重矩阵做 INT8→FP32 反量化。28 层 × 7 Linear = **196 次/token** dequant，dequant 耗时远超 GEMM 本身。

优化：
1. **Persistent FP16 weight cache**: 首次推理统一 dequant 全部权重并缓存 FP16 版本，后续直接引用
2. **cublasGemmEx FP16 Tensor Core**: 替代 FP32 cublasSgemm

结果：0.4 → 57.5 tok/s = **143×**。后续 + KV Cache INT8 + CUDA Graph → 132 tok/s (**330×**)。

---

**Q5: SGEMM double buffer 怎么实现？SM 硬件怎么调度？代码流程？**

**A**: 两组 SMEM `sA[2][T][T+1]`，Load tile[t+1]→`buf[nxt]` 的同时 Compute `buf[cur]`。

硬件调度: SM 的 **LSU**(load/store unit) 和 **FP32 Core** 是独立流水线 → 同一 Warp 的 `ld.global` 和 `fma` 走不同 pipeline 实现 **ILP**；不同 Warp 通过 **TLP**（零开销切换）进一步重叠。

代码流程: Prologue(load tile[0]) → MainLoop(交替 buffer, load+compute 重叠) → Epilogue(compute 最后 tile)。每迭代只需 **1 次 sync**（因 read/write 操作不同 buffer）。

> 详见本文 §2 深度 Q&A "SGEMM Double Buffer" 条目有完整代码。

**Q6: 适配国产卡有没有做底层优化？**

**A**: 已做的关键适配：
1. **compat.cuh 兼容层**: `WARP_SIZE` 参数化（NVIDIA=32, 某些国产卡可能=128）→ 影响 `__shfl_down_sync` 归约轮数和 SMEM 数组大小
2. **Runtime Launch Config**: `get_num_sm()` 运行时查询 → Grid 动态调整，不硬编码 SM 数量
3. **BLAS 路径**: `cublasSgemm` → `macablasSgemm` / `topsblasSgemm` 映射

尚需实际硬件验证的方向：Tile 参数调优、带宽差异 Profiling、非 Tensor Core 矩阵加速硬件适配。

**Q7: 微架构级访存与指令优化针对什么算子？**

**A**: 主要针对 **SGEMM** 和 **Self-Attention**：
- **访存优化**: SMEM Tiling（减少 Global 访问）、128 字节 Coalesced Access（连续地址映射到同一事务）、Bank Conflict Free（padding/swizzle）
- **指令优化**: Double Buffer ILP（ld/fma 走不同 pipeline）、向量化加载（`float4` 一次读 16 字节）
- **归约算子**（RMSNorm/Argmax）: Warp Shuffle `__shfl_down_sync` 替代 SMEM reduction（减少同步开销）

**Q8: 精度怎么保证？怎么对比？有没有和 TensorRT 对比？**

**A**: 两层验证：
1. **逐算子正确性测试**: Python 端以 HuggingFace Transformers (PyTorch) 为 reference，对比每个算子输出 `atol=1e-5, rtol=1e-5`
2. **端到端测试**: 对比完整 generate 输出文本与 HF 是否一致

未与 TensorRT 对比——项目定位是**从零实现学习推理引擎原理**，非生产级替代品。

**Q9: 了解 vLLM、SGLang 吗？**

**A**:
- **vLLM**: Continuous Batching（不等 batch 填满，动态合并新请求）+ PagedAttention（KV Cache 分页管理，避免预分配碎片）。核心 Scheduler 管理 running/waiting/swapped 三个请求队列
- **SGLang**: 在 vLLM 基础上加 RadixAttention（Prefix Caching，共享公共前缀的 KV Cache）+ 结构化生成（JSON/Regex 约束 decode）
- 定位区别：两者是 **serving framework**（调度 + 多用户）；我的项目是 **inference engine**（单模型单请求的底层执行层）

---

**Q10: 了解 TVM、MLIR 编译器优化吗？**

**A**:
- **TVM**: DL 编译器。计算图 → 算子调度（schedule primitives: tile/split/bind/vectorize）→ 代码生成（CUDA/LLVM）。AutoTVM/Ansor 自动搜索最优 schedule
- **MLIR**: 多级 IR 框架（Dialect 体系）。Linalg Dialect → Affine Dialect → GPU/LLVM Dialect 逐层 lowering
- 与手写 kernel 的关系：TVM/MLIR 自动化程度高但天花板略低；手写 kernel 灵活但开发成本高。工业界常用 CUTLASS（模板库）作折中

#### 二面

**Q1: SGEMM 全优化流程？按重要性怎么排序？为什么能 work？**

**A**: 优化链（按重要性排序）：
1. **SMEM Tiling**（最关键, ~5-10×）: 数据从 Global Memory → Shared Memory 批量搬运，复用 T² 次 → Global 访问量降 T 倍
2. **消除 Bank Conflict**（~1.2-1.5×）: padding `sA[T][T+1]` 使步长与 32 互质 → warp 内并行访问
3. **Double Buffer**（~1.2-1.3×）: 两组 SMEM 实现 Load/Compute **ILP** → 隐藏 Global Memory 延迟
4. **向量化**（~1.1-1.2×）: `float4` 一次读 16 字节 → 减少 Load 指令数
5. **Register Tiling**: 每线程算 TM×TN 子块，减少 SMEM → Register 的重复读取

**为什么能 work**: SGEMM 的数据复用度极高（O(N³) 计算 vs O(N²) 数据），通过层级缓存（Global → SMEM → Register）逐步提高复用倍数。

---

**Q2: 增加 register 对性能影响？register spilling？导致什么？**

**A**: 每线程寄存器增加 → SM 能同时驻留的 Warp 减少 → **Occupancy 降低** → TLP（线程级并行延迟隐藏）受限。

Register spilling：用量超过物理上限（sm_89: 每线程最多 255 个, 每 SM 65536 个）→ 溢出数据存到 **local memory**（实际走 L2 Cache → DRAM，比 register 慢 ~100×）。

诊断：`nvcc --ptxas-options=-v` 查看 `spill loads/stores`；Nsight Compute Memory chart 看 local memory traffic。

---

**Q3: RMSNorm 计算公式？什么类型的算子？**

**A**: 公式：$\text{output} = \frac{x}{\sqrt{\text{mean}(x^2) + \epsilon}} \cdot \gamma$

两步计算：
1. **Reduce**（并行归约）: 求 $x^2$ 的均值 → Warp Shuffle + Block Reduce
2. **Elementwise**: 除以 RMS 值 × 可学习参数 $\gamma$

**Memory-Bound 算子**（AI ≈ 3 FLOP/Byte）——每个元素只做几次运算但都要完整读写一次。优化重点在带宽利用率而非算力。

---

**Q4: bank conflict 是什么？在 SGEMM 中为什么会产生？**

**A**: Shared Memory 分 32 个 bank，连续 4 字节映射到连续 bank。同一 Warp 的 32 个线程访问**同一 bank 的不同地址** → 串行化（N-way conflict）。

SGEMM 中产生的原因：读 `sA` 的一列时，warp 内 32 线程读 `sA[0..31][k]` → 列方向步长 = 行宽 = 32 float = 128 字节 = **恰好 32 个 bank → 每线程命中同一 bank** → 32-way conflict。

解决：padding `sA[32][33]` 使步长 = 33，与 32 互质 → 线程分散到不同 bank。

### 1.4 旷视未来 — 大模型推理系统优化实习生

**Q1: 为什么用 FP32 做 SGEMM 优化？现在都是 FP16/BF16**

**A**: **教学驱动**——FP32 SGEMM 是理解 CUDA 优化原理的经典入门（Tiling、Bank Conflict、Roofline 分析最直观、精度验证最简单）。

项目并非止步 FP32：
- Linear 走 cuBLAS（自动选择 Tensor Core）
- Self-Attention 实现了 **F32/F16/BF16 三种路径**
- INT8 量化全程走 FP16 Tensor Core
- FP32 手写 SGEMM 的价值在于**理解优化方法论**，生产环境一定用 FP16/INT8

---

**Q2: 后面有没有做 FP16/BF16 优化？**

**A**: Self-Attention 算子用 C++ 模板 `ComputeType` 实现了 **F32/F16/BF16 三条路径**。Naive 和 FlashAttention 两种模式均支持全部三种精度。

FlashAttention 中 **FP16/BF16 的 Bc=64**（vs F32 的 Bc=32），因为半精度数据更小，相同 SMEM 空间可装更大 tile → 更少 tiling 迭代次数。

INT8 量化推理全程走 **FP16 Tensor Core**（cublasGemmEx）。

---

**Q3: 用的 INT8 TC 还是 FP16 TC？**

**A**: **FP16 Tensor Core**。INT8 权重 dequant 为 FP16 后用 `cublasGemmEx(CUDA_R_16F, CUDA_R_16F, CUBLAS_COMPUTE_16F)`。

没用 INT8 TC 的原因：INT8 Tensor Core（IMMA）要求 A 和 B **都是 INT8**，而我们是 weight-only 量化（W8A16），激活值保持 FP16。如果改成 W8A8（如 SmoothQuant）才能用 INT8 TC。

---

**Q4: 量化在什么情况下有加速效果？weight-only 什么时候会加速？**

**A**: **LLM Decode 是 Memory-Bound**（M=1 GEMV，AI ≈ 0.5 FLOP/Byte，远低于 Roofline kink）。瓶颈是**读权重的带宽**，不是算力。

- **Weight-only 量化**（W8A16/W4A16）：权重内存减半/减 4× → 带宽需求成比例降低 → Decode **直接加速**
- **Prefill**（大 seq_len, Compute-Bound）：weight-only 加速有限——此时算力才是瓶颈
- **W8A8**（SmoothQuant）：weight + activation 都量化 → Prefill 也能加速（INT8 TC 减计算量）

---

**Q5: W4A32/W8A32 量化方式很少见？**

**A**: 面试时表述不准确——实际实现是 **W8A16** 而非 W8A32（INT8 权重 dequant 到 FP16 后走 FP16 Tensor Core）。

- 一般没人做 W_xA32 的组合，因为 FP32 无法用 Tensor Core，白白浪费了量化节省带宽的优势
- 业界标准组合：**W8A16**（推理常用）、**W4A16**（GPTQ/AWQ）、**W8A8**（SmoothQuant）

---

**Q6: FP32 算力为什么比 BF16/FP16 低很多？**

**A**: RTX 4060 Ti: FP32 = 22 TFLOPS, FP16 TC = 176 TFLOPS (**8×**)。

原因：**Tensor Core** 是专用矩阵乘加速单元，只支持 FP16/BF16/TF32/INT8/FP8 精度。
- FP32 只能用 CUDA Core（每 SM 128 个 FP32 ALU，每 cycle 做 1 FMA）
- FP16 Tensor Core 每 cycle 做 4×4×4 MMA → 单指令 128 FMA → 吞吐量高数倍
- 这也是为什么**量化 + Tensor Core** 是推理优化标配

2. **FlashDecoding**: 将 KV 按 token 维度分给多个 block 并行处理，最后 reduce 合并 → 解决长上下文 Decode 单 block 瓶颈
3. **GQA/MQA**: 多个 Query head 共享 Key/Value head，KV Cache 减 N/G 倍

**Q6: 你的 FlashAttention 实现**

**A**: 核心是 **Online Softmax**：
```
for each KV block (size Bc):
    scores = Q × K_block^T                     // d_head × Bc, 存 SMEM
    block_max = max(scores)
    m_new = max(m_old, block_max)               // 更新全局 max
    correction = exp(m_old - m_new)             // rescale 因子
    sum_new = sum_old * correction + Σexp(scores - m_new)
    O_new = O_old * correction + exp(scores - m_new) × V_block
最终: O = O_new / sum_new
```

数学上等价于全局 softmax——通过 running max 和 running sum 的递推关系保证精度。

**Q7: 你对 runtime 了解多少？**

- **Continuous Batching**: 不等 batch 满就开始执行，新请求随时插入正在运行的 batch
- **Iteration-level scheduling**: 每个 decode step 都重新做调度决策

## 2. 面试复盘深度 Q&A

### Q: Bank Conflict 除了 Padding 还有什么解决方法？（面试原题）

**A**: 三种主要方法：

**① Padding（项目采用）**：`sA[T][T+1]`，每行多 1 float → 步长与 32 互质 → 0 conflict。优点：一行改动；缺点：浪费 ~3% SMEM 空间。

**② Swizzle / XOR 置换（cuBLAS/CUTLASS 采用）**：
```
存储和读取时对列索引做 XOR: sA[row][col ^ row]

不做 Swizzle 的列访问 (col=0):
  Thread 0 → sA[0][0] → Bank 0
  Thread 1 → sA[1][0] → Bank 0  ← 32-way conflict!

Swizzle 后 (col ^ row):
  Thread 0 → sA[0][0^0=0] → Bank 0
  Thread 1 → sA[1][0^1=1] → Bank 1  ✓
  Thread 2 → sA[2][0^2=2] → Bank 2  ✓
  → 每 thread 访问不同 Bank，零额外空间开销
```

**③ 转置数据布局**：改变 SMEM 中矩阵的存储方式（如转置存储），使计算时的访问模式从按列跳跃（stride=32）变为按行连续（stride=1），天然避免 conflict。

**补充**：同一 Warp 所有线程访问**同一地址** → 硬件 Broadcast → 不是 conflict。只有"同一 Bank 的**不同**地址"才产生 conflict。

> **面试一句话**：Padding 最简单但浪费空间，Swizzle(XOR) 零开销是工业界标准（CUTLASS 采用），还可以通过转置布局使访问模式避开冲突。

### Q: SGEMM Double Buffer 怎么实现？硬件怎么调度？代码流程？（面试原题）

#### 问题根源：标准 Tiled SGEMM 的串行瓶颈

```
标准 Tiled SGEMM 每次迭代:
  ┌─────────────────┐     ┌──────────────────┐
  │ Load: Global→SMEM│────→│ __syncthreads() │
  │ (~400 cycles)    │     └──────┬───────────┘
  └─────────────────┘            │
  ┌─────────────────┐     ┌──────▼───────────┐
  │ Compute: FMA    │────→│ __syncthreads() │
  │ (~100 cycles)   │     └─────────────────┘
  └─────────────────┘
  问题: Load 和 Compute 完全串行 → FMA 等 LSU, LSU 等 FMA → 硬件利用率低
```

#### 核心思想：两组 SMEM 缓冲区，加载和计算重叠

```
时间线对比:
  标准:       [Load0][Compute0][Load1][Compute1][Load2][Compute2]
               空闲FMA  空闲LSU  空闲FMA  空闲LSU

  Double Buf: [Load0][Load1 + Compute0][Load2 + Compute1][Compute2]
                      ↑↑↑ 重叠 ↑↑↑      ↑↑↑ 重叠 ↑↑↑
               prologue                              epilogue
```

#### 硬件调度机制：SM 内独立流水线并行

```
SM 内部:
  ┌─────────────────────────────────────┐
  │  Warp Scheduler ×4                  │
  │  每 cycle 从就绪 Warp 选指令发射     │
  └──────┬──────────┬───────────────────┘
         │          │
  ┌──────▼───┐ ┌────▼────┐
  │ FP32 Core│ │  LSU    │    ← 独立流水线!
  │ (FMA)    │ │(ld/st)  │
  │ ~4 cyc   │ │~400 cyc │
  └──────────┘ └─────────┘

两层重叠机制:
  ILP (指令级并行): 同一 Warp 发射 ld.global → LSU, fma → FP32
    前提: load 写 buf[nxt], compute 读 buf[cur] → 无数据依赖
  TLP (线程级并行): Warp A 等 load → stall → Scheduler 切 Warp B 做 compute
    → Warp 切换 0 开销 (硬件上下文常驻寄存器文件)
```

#### 代码完整流程

```cuda
#define T 32
__global__ void sgemm_double_buffer(
    float* C, const float* A, const float* B, int M, int N, int K)
{
    __shared__ float sA[2][T][T+1], sB[2][T][T+1]; // [2] = 双缓冲
    int row = blockIdx.y * T + threadIdx.y;
    int col = blockIdx.x * T + threadIdx.x;
    float sum = 0.0f;
    int cur = 0;

    // ===== Prologue: 加载第一个 tile → buf[0] =====
    sA[0][threadIdx.y][threadIdx.x] =
        (row < M && threadIdx.x < K) ? A[row*K + threadIdx.x] : 0.f;
    sB[0][threadIdx.y][threadIdx.x] =
        (threadIdx.y < K && col < N) ? B[threadIdx.y*N + col] : 0.f;
    __syncthreads();

    // ===== Main Loop: 加载下一 tile + 计算当前 tile =====
    for (int t = T; t < K; t += T) {
        int nxt = 1 - cur;

        // Phase A: Load tile[t] → buf[nxt] (→ LSU pipeline)
        sA[nxt][threadIdx.y][threadIdx.x] =
            (row < M && t+threadIdx.x < K) ? A[row*K+t+threadIdx.x] : 0.f;
        sB[nxt][threadIdx.y][threadIdx.x] =
            (t+threadIdx.y < K && col < N) ? B[(t+threadIdx.y)*N+col] : 0.f;

        // Phase B: Compute buf[cur] (→ FP32 pipeline, 与 Phase A 重叠!)
        for (int k = 0; k < T; k++)
            sum += sA[cur][threadIdx.y][k] * sB[cur][k][threadIdx.x];

        cur = nxt;
        __syncthreads(); // 确保 buf[nxt] 加载完 + buf[cur旧] 读完
    }

    // ===== Epilogue: 计算最后一个 tile =====
    for (int k = 0; k < T; k++)
        sum += sA[cur][threadIdx.y][k] * sB[cur][k][threadIdx.x];

    if (row < M && col < N) C[row*N+col] = sum;
}
```

#### 关键追问

```
Q: 为什么只需 1 个 __syncthreads()/迭代？(标准 Tiling 要 2 个)
A: Load 写 buf[nxt], Compute 读 buf[cur] → 操作不同 buffer → 无数据冲突
   只需迭代末尾 1 次 sync: ① 确保 load 完 ② 确保 compute 完
   标准 Tiling 用同一 buffer → load 后 sync + compute 后 sync (防互踩)

Q: SMEM 用量翻倍影响?
A: sA[2][32][33]+sB[2][32][33] ≈ 16.5 KB (标准 ~8.25 KB)
   Occupancy 可能降低，但 ILP 带来的延迟隐藏收益通常大于 Occupancy 损失
   → 面试考点: "不是 Occupancy 越高越好" 的经典例子

Q: Ampere+ 进阶?
A: cp.async 指令: Global → SMEM 绕过寄存器 (由硬件 DMA 直接搬)
   cp.async.wait_group N: 等待异步拷贝完成
   Hopper (sm_90): TMA (Tensor Memory Accelerator) 进一步自动化
   FlashAttention v3 就用了 Warp Specialization + 这种异步 pipeline
```

> **面试一句话**：Double Buffer 用两组 SMEM，Load 下一 tile 到 buf[nxt] 的同时 Compute buf[cur]。硬件上 SM 的 LSU 和 FP32 Core 是独立流水线，同一 Warp 的 ld.global 和 fma 走不同pipeline 实现 ILP。代码是 Prologue→MainLoop(load+compute 交替 buffer)→Epilogue，每迭代只需 1 个 sync。SMEM 翻倍可能降 Occupancy，但 ILP 收益更大。

### Q: Warp Scheduler 调度机制与指令级并行 (ILP)

**A**:

```
Ada Lovelace (sm_89) 每个 SM:
  - 4 个 Warp Scheduler (Sub-Partition)
  - 每个 Scheduler 管理最多 12 个 Warp (最大 48 warps/SM)
  - 每 cycle 每个 Scheduler 选 1 个就绪 Warp 发射 1 条指令

发射规则:
  - 指令就绪 = 所有操作数可用 (寄存器写回完成 or 无依赖)
  - 优先级: Round-Robin 或 Age-based (硬件决定, 不透明)
  - 不同指令类型走不同 Dispatch Port:
    FP32/INT  → FP32 Core Pipeline
    ld/st     → LSU Pipeline  
    sin/cos   → SFU Pipeline
    MMA       → Tensor Core Pipeline

ILP 条件:
  1. 指令间无数据依赖 (RAW/WAW/WAR)
  2. 目标是不同功能单元
  → 编译器/程序员需确保指令交错排布, 避免连续 load 或连续 fma
```

### Q: Speculative Decoding 详解 — 投机解码加速 Decode（展开版）

**A**:

**问题根源**: Decode 每步只生成 1 token，Linear 退化为 GEMV (M=1)，AI ≈ 0.5 FLOP/Byte → Memory-Bound。每步都要读完整权重（7B FP16 = ~14GB），但计算量极少 → GPU 算力严重浪费。

**核心思想: Draft-then-Verify**

```
Step 1: Draft Model (小模型, 如 68M/0.5B) 快速连续生成 K 个 candidate tokens
        [t1', t2', t3', t4', t5']  (K=5, 每步 ~0.2ms)

Step 2: Target Model (大模型, 如 7B) 一次 forward 验证全部 K 个 token
        Forward(model, [t_prev, t1', t2', t3', t4', t5'])
        → 同时得到 K 个位置的 logits

Step 3: 逐个检验接受/拒绝
        t1': P_target >= P_draft → 接受 ✓
        t2': P_target >= P_draft → 接受 ✓
        t3': P_target < P_draft → 以概率 1-Pt/Pd 拒绝 ✗ → 重采样
        本轮: 1 次大模型 forward → 产出 3 个有效 token!
```

**关键洞察**: verify K 个 ≈ generate 1 个成本：Decode 是 Memory-Bound，batch=K 和 batch=1 读同样的权重。

**修正分布数学保证**:
```
对 candidate token x:
  P_t(x) >= P_d(x) → 直接接受
  否则 → 以概率 P_t(x)/P_d(x) 接受

拒绝后从修正分布重采样:
  P_resample(x) = max(0, P_t(x) - P_d(x)) / Σ max(0, P_t(x) - P_d(x))

定理: 最终输出 = 纯 Target Model 分布 (数学无损!)
```

**变体**:
| 方法 | Draft 来源 | 优缺点 | 加速比 |
|------|-----------|--------|--------|
| 标准 Spec Decode | 独立小模型 | 需两套模型, 显存+1 | ~2-3× |
| Medusa | Target 加 N 个 head | 零额外模型, Tree Attention | ~2-2.5× |
| Eagle-2 | 轻量 Decoder 层 | 准确度最高 | ~3-4× |

**面试追问**:
- K 不是越大越好: KV Cache 随 K 增长, K=4-8 最佳
- 只优化 Decode, 对 Prefill 无用 (Prefill 已 batch)
- Draft Model 选同系列缩小版 (词表一致)

### Q: cudaGraph 详解 — 消除 kernel launch 开销（展开版 + 项目实战）

**A**:

**问题**: 单次 kernel launch CPU 端开销 ~5-10µs。Qwen2-1.5B Decode 一步 = 28层 × 11 算子 ≈ 308 kernels/step → 308 × 6µs ≈ 1.85ms 纯 launch 开销。

**核心思想**: 将一系列 CUDA 操作录制成 DAG，一次 launch 整个 Graph。

**三步流程**:
```cuda
// Step 1: 录制 (Capture) — 不真正执行, 只记录
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
rmsnorm_kernel<<<grid, block, 0, stream>>>(...);
cublasSgemm(handle, ...);  // cuBLAS 也在同一 stream
// ... 全部 Decoder kernels
cudaStreamEndCapture(stream, &graph);

// Step 2: 实例化 — Driver 预优化调度
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);

// Step 3: 反复执行
for (step = 0; step < max_tokens; step++) {
    // 更新动态参数 (通过设备内存间接寻址)
    cudaMemcpyAsync(d_token, &token_id, 8, H2D, stream);
    cudaMemcpyAsync(d_pos, &pos, 8, H2D, stream);
    cudaGraphLaunch(graphExec, stream);
}
```

**项目实测 (LLAISYS, RTX 4060 Ti)**:

| 指标 | 无 Graph | 有 Graph | 改善 |
|------|:---:|:---:|:---:|
| Launch overhead/token | ~1850µs | ~131µs | **-93%** |
| INT8+KV8 tok/s | 117.6 | **132.0** | **+12.2%** |
| Graph 节点数 | — | FP32=565, INT8=509 | — |
| Capture 耗时 | — | 一次 4012µs | 首 token only |

**项目中解决的三个难点**:

1. **动态参数**: LLM 每 token 的 token_id/pos/start_pos/total_len 都变。解决：**设备侧指针间接寻址**——Graph 录地址不录值，每 token 用 4× `cudaMemcpyAsync`（pinned→device）更新值
2. **FlashDecoding 动态 Grid**: total_len 变 → Grid 变。解决：固定最大 Grid + `d_total_len` 参数 + idle block early return（`kv_len<=0` 直接退出）
3. **FP32 -12% 回归**: `cudaMemcpy`(同步, default stream) 与 Graph launch(compute stream) 跨 stream 序列化。解决：`cudaMallocHost` + `cudaMemcpyAsync` 在同一 compute stream 上

**适用 vs 不适用**:
| ✅ 适合 | ❌ 不适合 |
|---------|----------|
| Decode (固定 shape, seq=1) | Prefill (seq_len 变) |
| 固定 batch 推理 | Continuous Batching (动态 batch) |
| 重复 pipeline | 含条件分支 / 动态拓扑 |

**面试一句话**: cudaGraph 录制 kernel DAG 一次 launch，我们在 LLAISYS 中实现了静态捕获 + 设备侧间接寻址解决动态参数，消除 93% launch overhead，INT8+KV8 +12.2%。

### Q: SM 资源瓜分与 Occupancy 计算（教学补充）

**A**:

```
SM 的三种有限资源 (决定能同时放几个 Block):
  1. Max Warps: 48 (sm_89) → 每 Block 的 Warp 数 × Block 数 ≤ 48
  2. SMEM: 48 KB (可配到 100 KB) → 每 Block SMEM 用量 × Block 数 ≤ 48 KB
  3. 寄存器: 65536 个 → 每 Block 线程数 × 每线程寄存器数 × Block 数 ≤ 65536

Occupancy = min(三种资源各自允许的 Warp 数) / 48

SMEM 翻倍 → 资源 2 能容纳的 Block 数减半 → 可能降低 Occupancy
但如果 Warp 限制先命中, SMEM 再翻倍也不影响 Occupancy

判断工具: NVIDIA Occupancy Calculator 或 Nsight Compute
实际判断: Nsight Compute 的 "Stall Reasons" 比 Occupancy 数字更有意义
```

### Q: 推理引擎还能怎么继续优化？（开放题标准答法）

**A**: 四层优化路径（从快到慢）:

1. **算子级** (最快): Decode GEMV 专用 kernel、cudaGraph capture、FlashDecoding
2. **内存级** (中等): INT4/KV Cache 量化、CachingAllocator + cudaMemPool
3. **系统级** (较大改动): Continuous Batching + PagedAttention、Speculative Decoding、Prefix Caching
4. **多卡** (最大): Tensor Parallelism (降延迟)、Pipeline Parallelism (提吞吐)

### Q: cp.async vs 传统 load vs TMA（三代 Global→SMEM 搬运）

**A**:

| 代 | 指令 | 路径 | 占寄存器？ | 架构 |
|----|------|------|-----------|------|
| 传统 | ld.global + st.shared | Global → Reg → SMEM | ✅ 占用 | Volta/Turing |
| cp.async | cp.async.ca.shared.global | Global → SMEM (绕过 Reg) | ❌ 不占 | Ampere+ |
| TMA | tma::load(desc, coords) | Global → SMEM (描述符驱动) | ❌, 1指令搬1 tile | Hopper |

cp.async 让 Double Buffer 更强: 寄存器全留给 FMA 计算, 拷贝完全异步。
TMA 进一步: 自动边界检查 + 自动 swizzle + 支持 2D/3D 规则搬运。
