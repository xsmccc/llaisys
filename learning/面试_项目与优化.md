## 1. ★ 项目介绍标准答案（每次面试前背一遍）

### 通用版（3 分钟，适用于所有算子/推理岗）

我做的是一个基于 C++ 和 CUDA 从零实现的大模型推理框架，叫做 LLAISYS，能够端到端运行 DeepSeek-R1-Distill-Qwen-1.5B 模型的推理。

**架构层面**，我设计了一个多后端的 Device 抽象层，通过虚函数接口统一了 CPU、NVIDIA CUDA、沐曦 MUSA 三种设备的内存管理和算子分发。上层的模型代码和算子实现完全不感知具体设备，新增设备只需要实现 DeviceInterface 的几个核心接口——allocate、deallocate、copy、synchronize——就可以直接跑通推理，不需要改动上层代码。

**算子层面**，我从零手写了 12 个核心推理算子的 CUDA kernel，包括 Linear、RMSNorm、RoPE、SwiGLU、SelfAttention、Embedding 等，全部和 PyTorch 的 HuggingFace 官方实现做了精度对齐。

**优化层面**，我做了 9 个关键优化：

第一个是 **INT8 量化加速**。我用 nsys profiler 对推理流程做了一次完整的性能分析，发现瓶颈在于每次前向推理中，INT8 权重都会被反量化成 FP32 再做矩阵乘——28 层 Transformer 每层有 7 个 Linear，总共 196 次反量化。这个操作本身比矩阵乘还慢。我的解法是设计了一个 persistent FP16 weight cache，第一次推理时把 INT8 权重反量化成 FP16 缓存起来，后续推理直接复用 FP16 权重调 cublasGemmEx 走 Tensor Core。这一个优化就把推理速度从 0.4 提升到了 57.5 tok/s，143 倍加速。

第二个是 **自定义 GEMV kernel**。Decode 阶段 batch=1，矩阵乘退化为 GEMV，cuBLAS 的通用 GEMM 路径有大量冗余。我实现了一个 warp-per-output 的 INT8 和 INT4 GEMV kernel，每个 warp 负责一个输出元素，用 char4 向量化加载权重、warp shuffle 做归约、on-the-fly 反量化（先整数累加再乘 scale），最终比 cuBLAS 快 1.65 倍。

第三个是 **FlashAttention 三路径设计**。短序列用 Naive Fused 路径，把所有 attention scores 放在 shared memory 里一次算完，避免 global memory 读写；长序列用 FlashAttention v2 的 tiled online softmax 算法，支持任意长度；decode 阶段用 FlashDecoding，将 KV 序列按 chunk 分到不同 block，多 SM 并行处理后 reduce，在 4K 上下文时加速 1.34 倍。

第四个是 **KV Cache INT8 量化**。KV Cache 在长序列推理中占据大量显存。我实现了 per-token per-head 的对称量化，与权重量化完全正交（独立开关、独立数据通路）。叠加后 INT8+KV INT8 从 76 提升到 118 tok/s，+55%。

第五个是 **CUDA Graph 静态捕获**。Decode 每 token 约 308 次 kernel launch，每次 5-7μs CPU 开销合计约 1.85ms。我实现了"捕获一次，永久重放"的静态 Graph：三个技术难点——① 设备侧指针间接寻址（Graph 录地址不录值）② FlashDecoding d_total_len 适配 + idle block 早退（固定最大 Grid）③ Pinned Memory + cudaMemcpyAsync 消除 default-stream 序列化（修复 FP32 -12% 回归）。最终 INT8+KV8 从 118 提升到 132 tok/s，+12.2%。

其他优化还包括 Fused Add+RMSNorm 减少一次 global memory 读写、QKV 权重合并减少 kernel launch、Prefill 阶段 batch 化提速 5-12 倍。

最终整体推理性能：INT8+KV8+CUDA Graph 达到 ~132 tok/s，INT4 达到 ~33 tok/s，在 RTX 4060 Ti (8GB) 上。超出 HBM Roofline 理论极限（91.3 tok/s）45%——归因于 L2 Cache 命中 + Graph launch gap 消除。

### 针对"跨 GPU 移植"岗位追加（30 秒）

在跨平台方面，我们的框架通过 xmake 构建系统管理多后端编译，已经成功跑通了沐曦 GPU 的适配。移植过程中主要处理的是 API 映射——比如 cudaMalloc 对应 musaMalloc、CUDA stream 对应 MUSA stream——以及计算能力差异导致的 kernel 参数调整。这个经验让我对不同 GPU 架构的异同有比较实际的理解。

### 针对"编译/Triton/TVM"方向的补充话术（被问到时用）

> 我目前没有直接使用 Triton 或 TVM 的经验，但我理解它们的核心——Triton 对 GPU kernel 做自动 tiling 和调度优化，TVM 是端到端的算子编译框架。我现在的经验是手写 CUDA kernel 做极致优化，包括 shared memory 分块、bank conflict 处理、warp shuffle、occupancy 调优，这些都是编译器 codegen 最终要生成的目标代码的逻辑。我相信有了这个 low-level 基础，能很快上手编译方向的工作。

## 2. 简历重点问题速答（小米/小红书共用）

### Q: 你的项目中最有技术深度的部分是什么？

> **Custom GEMV kernel**: 从 bandwidth 分析出发（cuBLAS 用 FP16 缓存 = 浪费量化带宽），设计了 INT8/INT4 直读 on-the-fly dequant 的 GEMV 内核。char4 向量化、shared memory 广播输入、warp shuffle reduce。W8A16 从 67.6→111.8 tok/s (1.65x)。这是 vLLM Marlin / llama.cpp 等所有工业引擎的标准做法。

### Q: 你遇到过最难调试的 bug 是什么？

> **FP16 weight cache stale pointer**。现象：Prefill Batch 后前几个 token 和逐 token 结果不同。用 bisect 缩小到 batch_size=2 就触发。最终发现 CachingAllocator 在模型析构后释放 GPU 内存，新模型分配到同一地址 → 全局 cache map 命中旧数据。根因是 cache 用 raw GPU pointer 做 key，没有和对象生命周期绑定。修复：析构函数清理缓存。

### Q: 你为什么不直接用 vLLM / TensorRT-LLM？从零写有什么意义？

> 1. **深入理解系统底层**: 从零实现让我理解了每一层的设计决策——CachingAllocator 为什么用 best-fit、FlashAttention 的 online softmax 为什么数学上等价、量化的 dequant 开销到底花在哪。这些在用框架时是黑盒。
> 2. **可控性**: 可以针对特定硬件(RTX 4060 Ti)做定制优化，比如 Custom GEMV 的 block size 和向量化策略。
> 3. **面试证明能力**: 能从零构建完整系统 + 逐步优化，比 "我用了 vLLM 并配置了参数" 含金量不同。

### Q: 你的框架和 vLLM/TensorRT-LLM 相比有什么差距？

> 坦诚说差距很大：
> 1. **没有 Continuous Batching / PagedAttention** — 不支持多请求并发
> 2. **没有图优化** — TRT-LLM 的 FP8/INT4 kernel fusion 比手写更系统化
> 3. **单卡** — 没有 Tensor Parallelism
> 4. **只支持 2 个模型** — vLLM 支持 100+ 模型架构
> 
> 但作为学习项目，它的价值在于让我从底层理解了这些系统在做什么。

## 3. 算子分类与核心模式

### 四大算子类型
| 类型 | 代表算子 | 特征 | Bound类型 |
|------|---------|------|-----------|
| **查表** | Embedding | 零计算，纯内存拷贝 | Memory-Bound |
| **逐元素** | Add/SwiGLU/RoPE | 每元素独立，无线程通信 | Memory-Bound |
| **归约** | RMSNorm/Argmax/Softmax | 线程协作求和/求最大 | Memory-Bound |
| **矩阵乘** | Linear/GEMM | 计算密集，cuBLAS/Tensor Core | Compute-Bound |

**所有 Transformer 算子都是这四种的组合。**

### Grid 大小选择策略
```
Elementwise (Add/SwiGLU): Grid = SM × 8, Block = 256
  → 固定 Grid, Grid-Stride Loop 处理任意数据量

Per-row (RMSNorm): Grid = rows, Block = 256
  → 一行一 Block, 归约维度在 Block 内

Per-query-head (Attention): Grid = (seq_len, nhead), Block = 256
  → 每个 (query, head) 一个 Block

Argmax 多 Block: Grid = SM × 4, Block = 256
  → 每 SM 4 Block, 平衡并行度和 Phase2 开销
```

## 4. Add 算子

### 配置
- Grid: `get_num_sm() * 8` (固定, SM89=34×8=272 Blocks)
- Block: 256 threads
- 循环: Grid-Stride Loop

### 代码核心
```cuda
__global__ void add_kernel_f32_vec(float* __restrict__ c,
    const float* __restrict__ a, const float* __restrict__ b, size_t numel)
{
    size_t vec_n = numel / 4;
    float4* c4 = (float4*)c;
    const float4* a4 = (const float4*)a;
    const float4* b4 = (const float4*)b;

    for (size_t i = blockIdx.x * blockDim.x + threadIdx.x;
         i < vec_n; i += blockDim.x * gridDim.x) {
        float4 va = a4[i];  // LD.128
        float4 vb = b4[i];  // LD.128
        c4[i] = {va.x+vb.x, va.y+vb.y, va.z+vb.z, va.w+vb.w};  // ST.128
    }
    // 尾部: tid==0 处理剩余 numel%4 个元素
}
```

## 5. RMSNorm 算子

### 线程映射: 一行一个 Block
```
Grid = (rows, 1, 1)    Block = (256, 1, 1)
为什么? 整行需要求和 (归约) → 同一行的线程必须在同一 Block 才能通信
```

### 两个 Phase
```
Phase 1 (归约): 向量化读 x → sum_sq += x² → block_reduce_sum
Phase 2 (逐元素): inv_rms = rsqrtf(sum_sq/d + ε)
                   out[j] = weight[j] × in[j] × inv_rms

广播模式: thread0 算 inv_rms → __shared__ → __syncthreads → 所有线程读
```

## 6. Argmax 算子

### 关键: 归约的是 (value, index) 对
```
warp_reduce_max: 同时 shfl val 和 idx → 保留更大值的索引
2 次 shfl_down 每轮（val 一次, idx 一次）
```

### Two-Phase Grid Reduce
```
小数据 (≤1024): 单 Block 直接归约
大数据 (词表 151936): 
  Phase 1: SM×4=136 Blocks 各归约一段 → block_vals[136], block_idxs[136]
  Phase 2: 1 Block 归约 136 个结果 → final max_val, max_idx
```

### 持久化缓冲区

static TempReduceBuffer g_temp_buf;  // static → 只增不缩
// 为什么不每次 cudaMalloc?
// cudaMalloc ~1ms 同步 → 推理每 token 调一次 → 性能腰斩
```

## 7. Linear/GEMM 算子

### cuBLAS 行列主序转置恒等式（面试必背）
```
C/C++ 行主序: A[M,K] 内存中行连续
cuBLAS 列主序: 看同一块内存 → A^T[K,M]

要算 C = in × W^T (行主序):
  cuBLAS 眼中: C^T = (in × W^T)^T = W × in^T
  → transa = OP_T, transb = OP_N
  → m=N, n=M, k=K (维度交换!)
```

### Tensor Core
```
硬件: 一条指令完成 16×16×16 矩阵乘加 (MMA)
cuBLAS: cublasGemmEx(..., CUBLAS_GEMM_DEFAULT_TENSOR_OP) 自动启用
sm_89 支持: FP16, BF16, TF32, INT8, FP8 Tensor Core
TF32: 输入 FP32 截断到 19 位 → Tensor Core 加速 → 几乎不损精度
```

### SGEMM 优化全路径
```
Level 0 Naive:     每线程算 1 元素, 全局内存反复读 → ~1-5%
Level 1 Tiling:    SMEM tile [32×32], 复用 32× → ~30%
Level 2 Padding:   sA[32][33] 消除 bank conflict → ~40%
Level 3 Reg Tile:  每线程算 TM×TN 块 → ~60-80%
Level 4 Dbl Buffer: 两组SMEM, Load/Compute 流水重叠 → ~80-95%
Level 5 cuBLAS:    极致优化 → ~95%
Level 6 TensorCore: 专用硬件 → ~100%

Tiled SGEMM 两个 __syncthreads() 的作用:
  1. 搬运后: 确保所有线程搬完 tile 才开始计算
  2. 计算后: 确保所有线程算完才覆盖 sA/sB 加载下一个 tile
```

## 8. Embedding / RoPE / SwiGLU

### Embedding
- 零计算, 纯按行号查表 → float4 搬运

### RoPE
```
公式: a'=a×cos(φ)-b×sin(φ), b'=b×cos(φ)+a×sin(φ)
φ = pos / θ^(2j/d), θ=10000

一维展平反推三维: tid → (i=query_pos, h=head, j=dim_pair)
  j = tid % half_dim
  h = (tid / half_dim) % n_heads
  i = tid / (half_dim * n_heads)

sincosf(): SFU 硬件指令 ~8 cycle 同时出 sin 和 cos
```

### SwiGLU 优化教训
```
版本0 Naive:        68.86µs, DRAM=95.32% → 已跑满带宽
版本1 float4+Grid缩小: 96.35µs → 变慢! Grid 缩 4×, Occupancy 下降
版本2 Grid-Stride+float4: 69.02µs → 既省指令又保 Occupancy

教训: 向量化 ≠ 缩小 Grid! 必须保持足够 Warp 隐藏内存延迟!
```

## 9. SelfAttention 与 FlashAttention v2

### MHA vs GQA vs MQA
| | MHA | GQA | MQA |
|---|---|---|---|
| KV heads | =Q heads | <Q heads | 1 |
| KV Cache | 基准 | 1/group × | 1/nhead × |
| 质量 | 最好 | 接近MHA | 略差 |
| 代表 | GPT-3 | Qwen2/Llama3 | PaLM |

### 项目双路径选择
```
naive_smem = (total_len + 8 + head_dim) × 4B
  ≤ 48KB → Naive Fused（短序列更快，无 Online Softmax 开销）
  > 48KB → FlashAttention v2（任意长度，O(Bc) SMEM）
```

### Naive Fused: 4 Phase
```
Grid = (seq_len, nhead)  Block = 256
SMEM = scores[total_len] + warp[8] + s_q[head_dim]

Phase 1: QK^T — Q 预加载到 SMEM, K 用 float4 从 Global 读
Phase 2: Causal Mask — t > current_pos → -inf
Phase 3: Safe Softmax — reduce_max → exp(s-max) → reduce_sum → 归一化
Phase 4: scores×V — 线程映射 v_head_dim, scores 从 SMEM 读
```

### FlashAttention v2: SMEM 布局
```
s_q [head_dim] float          — Q 全程驻留 SMEM
s_k [Bc × head_dim] T        — K tile (每 tile 覆盖)
s_v [Bc × v_head_dim] T      — V tile (每 tile 覆盖)
warp_buf [8] float            — Block Reduce
tile_scores [Bc] float        — 当前 tile 的 score

K/V 存 T 类型不存 float → 省一半 SMEM → 同样空间下 Bc 更大
```

### Bc 选取计算
```
以 Qwen2 head_dim=128, v_head_dim=128 为例:

F16 (sizeof(T)=2):
  SMEM = 512 + 516Bc
  Bc=64: ~33 KB ✓ (48KB 内)
  Bc=128: ~65 KB ✗

F32 (sizeof(T)=4):
  SMEM = 544 + 1028Bc
  Bc=32: ~33 KB ✓
  Bc=64: ~64 KB ✗

所以: F16/BF16 → Bc=64, F32 → Bc=32
→ F16 每次处理 64 个 KV → 循环次数少一半 → 更快!
```

### Online Softmax 完整推导
```
标准 Softmax 需要先看完所有 score 算 max → 两遍扫描

Online Softmax 逐 tile 更新:
  状态: running_max (m), running_sum (ℓ), o_acc

  处理 Tile A 后: m_A, ℓ_A, õ_A (都基于 m_A)
  处理 Tile B 时: max 可能更新为 m_new > m_A
    旧的 exp 值全错了! 需要修正:
    exp(x - m_new) = exp(x - m_A) × exp(m_A - m_new)
                                     ^^^^^^^^^^^^^^^^ correction factor

  更新公式:
    new_max  = fmaxf(running_max, tile_max)
    old_corr = expf(running_max - new_max)  // ≤1, 旧值缩小
    new_corr = expf(tile_max - new_max)
    running_sum = running_sum × old_corr + tile_sum × new_corr
    o_acc = o_acc × old_corr + tile_ov × new_corr
    running_max = new_max

  最终: output = o_acc / running_sum
```

### Causal 优化
```
kv_len = current_pos + 1 → 后面的 tile 完全跳过!
num_tiles = ceil(kv_len / Bc)
Prefill 早期 token kv_len 小 → 跳过更多 tile → 节省计算
```

### Naive vs Flash 对比
| | Naive | Flash |
|---|---|---|
| SMEM | O(total_len) | O(Bc) 常数 |
| 长度限制 | ~12K (48KB SMEM) | 任意 |
| K 来源 | Global Mem | SMEM |
| Online Softmax | 不需要 | 需要 |
| 短序性能 | 更快 | 略慢 |

### FlashAttention v1 → v2 → v3
```
v1 (2022): 外KV内Q循环 → 中间状态写HBM → 慢
v2 (2023): 外Q内KV循环 → 状态在寄存器 → ~2× faster
v3 (2024): Hopper sm_90, Warp Specialization + FP8 + WGMMA
```

---

### 优化 #1: INT8 量化 — 0.4 → 57.5 tok/s (143x)

**Q: 你的 INT8 优化是怎么做的？为什么原始 INT8 只有 0.4 tok/s？**

> 原始实现每次 GEMM 调用都做三件事：`cudaMalloc` 临时缓冲区 → dequant 整个权重矩阵(INT8→FP32) → `cublasSgemm` → `cudaFree`。
> 
> 这导致：① `cudaMalloc/Free` 每次 ~50μs 同步开销 ② 每 token 要 dequant 196 个权重矩阵（28 层 × 7 个 linear）③ 用 FP32 Sgemm 而不是 FP16 Tensor Core
>
> 优化三步走：
> 1. **CachingAllocator** — best-fit 显存池，消除 malloc 同步 → 0.4→2.6 tok/s
> 2. **FP16 Tensor Core** — dequant 到 FP16 而非 FP32 → 2.6→3.2 tok/s
> 3. **持久化 FP16 权重缓存** — dequant 只做一次，缓存在 `static unordered_map` 中，后续推理直接用缓存 → 3.2→57.5 tok/s
>
> 核心 dequant kernel: `dequant_int8_to_fp16_vec4` — 用 `uint32_t` 一次加载 4 个 INT8 值，解包后乘 per-channel scale，向量化写出 FP16。

**Q: 权重缓存后续遇到什么 bug？**

> CachingAllocator 在析构/重建模型时，GPU 指针地址可能被复用。缓存以 GPU 指针为 key (INT8 原始权重地址)，如果新模型的权重恰好分配到同一地址，会命中旧的 FP16 缓存（内容属于上一个模型的某层）。
>
> 修复：在模型析构函数 `~Qwen2Model()` 中调用 `cleanup_quantized_weight_cache()` 清空全局缓存。这个 bug 在后续 Prefill Batch 优化中也再次触发。

### 优化 #2: INT4 量化 — ~77 tok/s

**Q: INT4 和 INT8 有什么区别？为什么要做 INT4？**

> **动机**：进一步减少显存占用 + 带宽消耗。FP32=6.62GB, INT8+FP16缓存≈5GB, INT4+FP16缓存≈4.1GB, 原始INT4仅0.83GB。8GB GPU上INT4给KV Cache和长序列留更多空间。Custom GEMV直读INT4权重只需INT8一半带宽。但实测INT4(~33 tok/s)慢于INT8(~76 tok/s)——因为4-bit unpack需要bit shift/mask/sign extend约10条指令/元素，从bandwidth-bound变成compute-bound。
>


> INT4 进一步将每个权重从 8 bit 压缩到 4 bit，2 个 INT4 打包在 1 个 uint8 中。
> 
> 关键区别：
> - INT8 用 **per-channel** scale（每行一个 scale）→ 精度高、简单
> - INT4 用 **per-group** scale（每 128 个元素一个 scale）→ 必须分组，否则精度崩溃
> 
> Dequant kernel: `packed_byte & 0x0F` 取低 4 位，`packed_byte >> 4` 取高 4 位，各减 8 得到 [-8,7] 范围，乘 group scale。
> 
> 模型压缩: 6.62 GB → 1.61 GB (4.1x)。推理路径和 INT8 一样：首次 dequant→FP16 缓存→cuBLAS TC。

### 优化 #3: Fused Add+RMSNorm

**Q: 为什么要把 Add 和 RMSNorm 融合？效果如何？**

> 每层 Transformer 有两处残差连接+RMSNorm：`out = RMSNorm(x + residual)`。原来是 2 个独立 kernel：Add kernel 写 HBM → RMSNorm kernel 再读回来。融合后一个 kernel 完成：读 x 和 residual → 加法 + 累积平方和 → block reduce → 归一化输出。省掉一次 HBM 读写。
>
> **实测只提升了 ~1.5%**。原因：Decode (M=1) 时，element-wise 操作(hidden_size=1536 = 6KB)远小于 Linear 权重加载(>100MB per token)。Element-wise 占 decode 时间不到 2%，即使省掉一半也就 1% 提升。
>
> 但这是工程上的正确做法。长序列 prefill 时 (M 大) element-wise 占比会上升，融合的收益更明显。

### 优化 #4: QKV Merge

**Q: QKV Merge 是怎么做的？遇到了什么问题？**

> 原来 Q/K/V 三次独立 GEMM：`Q = input @ W_q`、`K = input @ W_k`、`V = input @ W_v`。三次 launch + 三次读 input。
> 
> 合并：`concat_dim0()` 将 W_q[Nq,K]/W_k[Nk,K]/W_v[Nv,K] 拼接为 W_qkv[N_total,K]，一次 GEMM 输出 [M, N_total]，然后 `slice + view` 零拷贝拆分。
> 
> **修复的 latent bug**: `Tensor::view()` 实现丢了 `_offset` 参数。`new Tensor(new_meta, _storage)` 默认 offset=0，导致 slice 后的 K/V tensor 全部指向 Q 的起始位置，输出全错。加上第三个参数 `_offset` 后修复。
> 
> **FP32 不做合并**：concat需要分配新的连续buffer，旧权重在memcpy完成前不能释放，所以峰值显存是2倍。FP32模型6.6GB权重翻倍=13.2GB，超过8GB GPU上限→OOM 或触发 swap thrash（实测从 14 tok/s 掉到 3.7 tok/s）。只对量化模型合并（权重小得多）。

### 优化 #5: Prefill Batch — prefill 12.9x 加速

**Q: Prefill Batch 解决什么问题？加速有多大？**

> 原来 26 token prompt 逐个前向传播：每 token 一次 forward → 26 次 cuBLAS GEMM，每次 M=1（GEMV），Tensor Core 基本空转（MMA 16×16×16 指令只填了 1 行 → 93.75% 浪费）。
> 
> 改为一次性发送全部 prompt tokens → M=26 的真 GEMM → Tensor Core 高效利用。
> 
> | 模型 | Per-token | Batch | 加速比 |
> |------|-----------|-------|--------|
> | FP32 | 791ms | 153ms | **5.2x** |
> | W8A16 | 385ms | 31ms | **12.3x** |
> | W4A16 | 388ms | 30ms | **12.9x** |

**Q: 为什么量化的加速比 FP32 高这么多？**

> FP16 Tensor Core 的 MMA 指令对 batch size 特别敏感。M=1 时 TC 只填一行（浪费 93.75%），M=26 时可以接近满载。FP32 不走 TC（或只有 TF32 hint），M=26 时 SM 利用率提升有限。
> 
> 理论极限是 26x（26 次→1 次），量化达到了理论极限的 ~50%。

**Q: 实现过程中遇到了什么困难？**

> **非连续内存**: QKV Merge 后的输出 [M, N_total] 做 slice 时，M>1 每行是连续的但行间可能不连续（因为 slice 只是修改 offset，不拷贝数据）。cuBLAS 要求输入连续。
> 
> 解决：写了 `split_qkv_batch()` 函数，M=1 时 slice+view（零拷贝），M>1 时用 `memcpy_async` D2D 显式拷贝到连续缓冲区。拷贝开销 213KB × 3 ≈ 0.4μs，可忽略。
> 
> **W8A16 结果不一致**: Batch prefill 后前几个 token 和逐 token 结果不同。用 bisect 缩小到 batch_size=2 就触发。最终定位到 FP16 weight cache 的 stale pointer 问题——和优化 #1 是同一个 bug 的不同触发路径。

### 优化 #6: FlashDecoding — 长序列 1.34x 加速

**Q: FlashDecoding 解决什么问题？和 FlashAttention 有什么区别？**

> **FlashAttention** 解决的是 prefill 阶段的 O(N²) HBM 读写问题——分块计算避免写出完整 attention score matrix。
> 
> **FlashDecoding** 解决的是 decode 阶段的 **SM 利用率低**问题。Decode 时 M=1（只有 1 个 query），attention kernel 的 grid = (1, nhead=12)，只有 12 个 block 运行。GPU 有 34 个 SM → 利用率 35%。
> 
> FlashDecoding 将 KV 长度维度切分：每 256 个 KV position 一个 block → grid = (num_splits, nhead)。比如 4096 个 KV → 16 splits × 12 heads = 192 blocks，SM 利用率飙升。

**Q: FlashDecoding 的两阶段是怎么工作的？**

> **Phase 1 — Partial kernel**: 每个 block 处理 256 个 KV position，计算 partial output O_i、local max m_i、local sum l_i。不归一化（因为没有全局 max）。
> 
> **Phase 2 — Reduce kernel**: 每个 head 一个 block，收集所有 splits 的 (O_i, m_i, l_i)，用 online softmax 合并：
> ```
> m_global = max(m_1, m_2, ..., m_S)
> O_final = Σ(exp(m_i - m_global) * O_i) / Σ(exp(m_i - m_global) * l_i)
> ```
> `exp(m_i - m_global)` 是修正因子——把每个 split 的局部 softmax 修正到全局 scale。

**Q: 为什么短序列看不到加速？**

> Decode 是 memory-bandwidth bound（加载权重 ~1.3GB/token）。Attention 在 total_len < 1000 时只占 decode 时间 2-3%。即使 attention 快 2x，整体也只提升 1-2%。
> 
> 长序列（4K tokens）时 attention 占比上升到 ~20%——其中 K/V 矩阵变大，naive 路径的单 block 变成瓶颈。这时 FlashDecoding 的并行切分才有实际收益：naive 46.7 tok/s vs FlashDecoding 62.6 tok/s = **1.34x**。

> **FlashDecoding详细流程（面试必背）**：
>
> **触发条件**: seq_len=1 (decode) 且 total_len > 256
>
> **问题**: decode时grid=(1, nhead=12)，34个SM只用12个=35%利用率
>
> **Phase 1 - Partial Kernel**: grid=(num_splits, nhead)，例如4096 KV → (16,12)=192个block
> - 每个block处理256个KV position
> - QK^T → scores → local softmax → 输出三个东西：
>   - partial_O：未归一化的 Σ exp(s-m_local)·V
>   - partial_m：局部max
>   - partial_l：局部exp sum
>
> **Phase 2 - Reduce Kernel**: grid=(nhead,)
> 1. global_max = max(所有split的partial_m)
> 2. global_sum = Σ exp(partial_m[s] - global_max) × partial_l[s]
> 3. final_O = (1/global_sum) × Σ exp(partial_m[s] - global_max) × partial_O[s]
>
> **修正因子原理**: 每个split内部用local_max算softmax，合并时需乘exp(local_max - global_max)把scale修正到全局。

> **FlashDecoding详细流程（面试必背）**：

### 优化 #7: Custom GEMV — W8A16 1.65x, W4A16 1.48x

**Q: 为什么要写 Custom GEMV？cuBLAS 不是已经很快了吗？**

> cuBLAS 走 GEMM 路径，即使 M=1 也加载 **FP16 权重缓存**（2 bytes/weight）。但量化的目的就是减少数据量。我们 INT8 权重只有 1 byte/weight，INT4 只有 0.5 byte/weight。cuBLAS 没法直接用量化权重。
> 
> 所以 cuBLAS 实际上浪费了量化带来的带宽优势：数据量减了但没省带宽。
> 
> Custom GEMV 直接从量化权重读取，寄存器内 on-the-fly dequant → 1.65x 带宽节省。

**Q: 你的 GEMV kernel 怎么设计的？**

> - **8 warps/block (256 threads)**，每个 warp 算 1 个输出行
> - 输入向量 x[K] 加载到 **shared memory**，所有 warp 共享，避免重复读
> - INT8: **`char4` 向量化读取**，一次加载 4 个 INT8 → 4 个 FMA
> - INT4: **`uint32_t` 向量化读取**，一次 32 bit = 8 个 INT4 值，bit shift + mask 解包
> - 每线程累加 partial sum → **warp shuffle reduce** (`__shfl_down_sync`) 汇总到 lane 0
> - Lane 0 加 bias 后写入输出

**Q: 为什么 W4A16 加速不如 W8A16？**

> INT4 unpack 开销大：每个元素需要 bit shift、mask、sign extend、乘 group scale，约 ~10 条指令。INT8 只需要 `(float)val * scale`，约 ~2 条指令。
> 
> INT4 的 per-group scale 也增加了额外读取：每 128 个元素读一个 FP16 scale（额外 2 bytes/group）。
> 
> 结果：INT4 GEMV 不再是纯 bandwidth-bound，计算指令密度变高，memory pipeline 利用率下降。带宽利用率只有 23% vs INT8 的 51%。

**Q: Custom GEMV 会影响 Prefill 吗？**

> 不会。M=1 (decode) 才走 GEMV 路径，M>1 (prefill) 仍走 cuBLAS GEMM + FP16 缓存。因为 prefill 时 M=26+，是 compute-bound，Tensor Core GEMM 比 GEMV 快得多。

### 优化 #8: KV Cache INT8 — 76 → 118 tok/s (+55%)

**Q: KV Cache INT8 是怎么做的？和权重量化有什么关系？**

> KV Cache 在长序列推理中占据大量显存（Qwen2-1.5B: 28层×2KV×2头×128维×8192长度×4B = 224MB FP32）。我实现了 per-token per-head 对称量化：写入时用 warp reduce 求 absmax → scale = absmax/127，量化到 INT8；读取时逐元素乘 scale 还原。
>
> **与权重量化完全正交**：独立开关（环境变量 `LLAISYS_KV_CACHE_INT8=1`）、独立数据通路。零条件依赖。
>
> **有趣发现**：KV INT8 在 FP32 模式下反而退化（14→8 tok/s），因为 8GB 显存中 FP32 权重已占 6.6GB，KV 的 dequant 缓冲区加剧显存压力触发 swap thrashing。但在 INT8 权重下叠加后完全释放收益：76→118 tok/s（+55%）。
>
> **正确性**：INT8+KV INT8 与 INT8-only 输出 **bit-identical**（500 token greedy decode 验证）。

### 优化 #9: CUDA Graph 静态捕获 — 118 → 132 tok/s (+12.2%)

**Q: CUDA Graph 怎么实现的？遇到了哪些难点？**

> **动机**: Decode 每 token 约 308 次 kernel launch，每次 5-7μs CPU 开销合计约 1.85ms/token，占推理时间 22%。
>
> **早期失败**: 最初尝试 `--default-stream per-thread` nvcc flag → 改变全局语义 → cuBLAS、CachingAllocator 等都用默认 stream → 不同 per-thread stream 上异步执行 → 数据竞争 → segfault。**教训**：全局编译 flag 影响范围不可控。
>
> **正确方案**: 创建 explicit `cudaStreamCreate()`，所有 kernel 和 cuBLAS 统一绑定到同一 compute stream。四个递进 commit：
> 1. **Stream 参数传递**: 所有 41 个 CUDA kernel 添加 stream 参数
> 2. **Re-capture Graph**: 每 token 重新捕获（验证正确性）
> 3. **Static Graph**: "捕获一次，永久重放"——CudaGraphManager 实现
> 4. **FlashDecoding + Pinned Memory**: 解决动态参数问题

**Q: 动态参数怎么解决？Graph 不是要求固定参数吗？**

> LLM Decode 有 4 个逐 token 变化的参数（token_id, position, start_pos, total_len）。Graph 捕获的是**内存地址**而非值，所以用**设备侧指针间接寻址**：
>
> - 在 GPU 上分配固定设备内存(`d_token`, `d_pos`, `d_start_pos`, `d_total_len`)
> - 所有 kernel 改为读取 `*d_start_pos` 而非直接接收 `start_pos` 值
> - 每 token 只需 4 次 `cudaMemcpyAsync`（pinned memory → device memory）更新值
> - Graph 拓扑不变，但 kernel 读到的值随 memcpy 更新

**Q: FlashDecoding 怎么适配 CUDA Graph？**

> FlashDecoding 的 Grid 尺寸取决于 `total_len`（每 token 变化），但 Graph 要求固定 Grid。
>
> 解决方案：**固定最大 Grid = (max_splits=32, nhead=12)**，传入 `const size_t* d_total_len`（设备内存指针）：
> - Partial kernel: 运行时从 `*d_total_len` 解析实际 `kv_len`，`kv_len <= 0` 的 block 直接 early return
> - Reduce kernel: 运行时计算 `actual_splits`，只归约有效 chunk
>
> idle block 开销可忽略（几十 ns），但拓扑固定，Graph 兼容。

**Q: FP32 -12% 回归是怎么回事？**

> Graph 上线后 FP32 性能反而下降 12%。根因：原始 `ws_token_->load()` 使用 `cudaMemcpy`（同步，default stream），在 Graph launch 的 compute stream 之外执行，两个 stream 之间产生隐式序列化。
>
> 修复：`cudaMallocHost` 分配 page-locked pinned buffer + `cudaMemcpyAsync` 在 compute stream 上执行。H2D 传输与 Graph launch 在**同一 stream** 上严格有序，消除跨 stream 同步。
>
> **实测**: capture 仅一次 4012μs，后续 avg_setup=28μs + avg_launch=103μs = 131μs/token vs 原始 1850μs，**节省 93%**。

### 综合 Q&A

**Q: 这 9 个优化你是怎么决定顺序的？**

> 1. 先做**量化**——Decode 是 bandwidth-bound，减少数据量是最直接的
> 2. 再做 **kernel fusion / merge**——减少 launch overhead 和 HBM 读写，投入小收益稳
> 3. 然后 **Prefill Batch**——prefill 一次性做完，避免 TC 空转
> 4. **FlashDecoding** + **Custom GEMV**——分别解决长序列 attention 瓶颈和 decode 带宽瓶颈
> 5. **KV Cache INT8**——正交压缩，显存+带宽双收益
> 6. **CUDA Graph**——系统级 launch overhead 消除，最后的 low-hanging fruit
>
> 每一步都先用 Roofline / bandwidth 分析确认当前瓶颈，不是拍脑袋。

**Q: 你怎么确认优化有效？测试怎么做的？**

> 1. **正确性**: A/B 对比优化前后 token 输出，500+ tokens 必须完全一致（包括 CUDA Graph 模式）
> 2. **性能**: subprocess 隔离测试（避免 CUDA 内存碎片干扰），3 次 warmup + 5 轮平均
> 3. **原则**: 每次只改一个变量，否则无法定位性能变化来源

**Q: 330× 加速的完整分解？**

> | 优化 | 累计 tok/s | 增量 |
> |------|-----------|------|
> | 原始 INT8 | 0.4 | 基线 |
> | + CachingAllocator + FP16 TC + 持久缓存 | 57.5 | 143× |
> | + Fused + QKV Merge | ~60 | +4% |
> | + Prefill Batch | ~60 (decode不变, prefill 12.9×) | prefill 加速 |
> | + FlashDecoding | ~63@4K ctx | long seq 保持 |
> | + Custom GEMV | ~76 | 1.65× decode |
> | + KV Cache INT8 | ~118 | +55% |
> | + **CUDA Graph 静态捕获** | **~132** | **+12.2%** |
>
> 最大贡献：持久化缓存 (143×)、KV Cache INT8 (+55%)、CUDA Graph (+12.2%)。
> 从 FP32 30 tok/s 基线看 = **4.4× 加速**；从 INT8 bug 基线看 = **330× 修复**。

**Q: 当前还有什么优化空间？**

> 1. **FP8 量化 (Hopper+)** — 权重体积再减半，预计 ~2× 加速
> 2. **Continuous Batching** — 多请求并发，M 增大后从 bandwidth-bound 变 compute-bound
> 3. **Speculative Decoding** — draft model 一次推测多 token，大模型验证
> 4. **Tensor Parallelism** — 多卡并行，突破单卡显存和带宽限制

## 11. 项目场景面试题

### Q: 介绍一下你的推理引擎项目的整体架构？

> 分层设计，从底到顶：
> **Layer 0**: C 函数指针表（LlaisysRuntimeAPI），统一 CPU/NVIDIA/沐曦/天数多设备接口
> **Layer 1**: Storage (RAII 管理 GPU 显存)
> **Layer 2**: CachingAllocator (multimap Best-Fit 内存池, 4GB 上限, mutex 线程安全)
> **Layer 3**: Runtime (设备管理, cudaSetDevice, Rule of Five = delete)
> **Layer 4**: Context (thread_local 线程级设备上下文, 懒初始化)
> **Layer 5**: Tensor (Meta/Storage/Offset 三要素, 零拷贝 permute/view/slice)
> **算子层**: Add/RMSNorm/Argmax/Linear/Embedding/RoPE/SwiGLU/SelfAttention (CUDA kernel)
> **模型层**: Qwen2/Llama3 推理 (KV Cache, GQA, INT8 量化)
>
> Python ctypes 调用 C 动态库(.so)，无需 pybind11。

### Q: 你在算子优化中遇到过什么性能问题？怎么解决的？

> **SwiGLU 优化踩坑**：将 float4 向量化后同时缩小 Grid 4×，结果从 68.86µs 变慢到 96.35µs。用 NCU 分析发现 Achieved Occupancy 大幅下降——Block 数减 4× 导致每 SM 只有 1-2 个 Block，不够 Warp 隐藏内存延迟。修复方案：保持 Grid = SM×8 不变，用 Grid-Stride Loop + float4，恢复到 69.02µs。
>
> **教训**：向量化 ≠ 缩小 Grid。必须保证足够的 Block 数来维持 Occupancy。

### Q: 你的 CachingAllocator 和 PyTorch 的有什么区别？

> 都是空闲块缓存。我们的用 multimap + Best-Fit + 2× 容忍度，适合推理（分配模式固定，块大小重复率高）。PyTorch 的 CUDACachingAllocator 用 Block Pool + Splitting（大块可拆小块)，更适合训练（分配模式多变，大小不固定）。
>
> PyTorch 还有 Block Coalescing（合并相邻空闲块）和 Segment 级管理，我们的版本更简洁。

### Q: 如果推理时出现 CUDA OOM，你怎么排查？

> 1. `nvidia-smi` 看总显存占用
> 2. 检查 CachingAllocator 的缓存量（是否到了 4GB 上限仍在缓存不释放）
> 3. 检查 KV Cache 增长（每 token 28KB × 28 层，4096 tokens = 112MB）
> 4. 检查是否 INT8/INT4 量化降低了权重显存
> 5. 对模型权重做显存估算：Qwen2-1.5B FP32 = 1.5B × 4B = 6GB；INT8 = 1.5GB；INT4 = 0.75GB

### Q: 你的 FlashAttention 实现的 SMEM 布局是怎么设计的？为什么 K/V 存 T 类型？

> s_q 用 float（复用次数多，精度要求高），s_k/s_v 用 T 类型（FP16/BF16 只 2B）。这样同样 48KB SMEM 下 Bc 可以更大（F16 Bc=64 vs F32 Bc=32），循环次数减半。
>
> Q 只有 1 行（Decode 时），常驻 SMEM 代价小。K/V 每个 tile 都覆盖，省一半空间影响巨大。

### Q: 你的项目是怎么支持 INT8 量化推理的？加速效果怎样？

> 用 cublasGemmEx 的 INT8 模式（CUDA_R_8I 输入 + CUDA_R_32I 累加 + CUDA_R_32F 输出）。权重离线量化为 INT8（per-channel scale），推理时 INT8 GEMM + scale 还原。
>
> Decode 性能从 FP32 的 0.4 tok/s 提升到 INT8 的 57.5 tok/s → **143× 加速**。主要收益：①权重读取量减 4×（4B→1B）②INT8 Tensor Core throughput 更高。

### Q: 如果面试官让你优化 Decode 速度，你会怎么做？

> Decode 是 Memory-Bound（AI≈0.5），瓶颈在搬权重：
> 1. **权重量化**：INT8 减 4× 读取→143× 加速（已实现）；INT4 再减 2×
> 2. **KV Cache 量化**：FP16→INT8 减 2× KV 读取
> 3. **Batching**：多请求合并增大 M → GEMV→GEMM → AI 提升 → 从 MB 变 CB
> 4. **模型并行**：多 GPU Tensor Parallelism，分摊权重
> 5. **Speculative Decoding**：小模型推测多 token → 大模型一次验证

### Q: 你在这个项目中学到了什么？最大的收获是什么？

> 1. **从底层理解 GPU 性能优化**：不只是写 CUDA kernel，而是理解 Roofline 模型判断瓶颈→针对性优化（MB 优化访存、CB 用 Tensor Core）
> 2. **系统设计思维**：CachingAllocator 的 Best-Fit 策略选择（为什么不用 First-Fit？因为碎片更大）、RAII 保证异常安全、thread_local 避免锁
> 3. **FlashAttention 的数学推导**：Online Softmax 的 correction factor 不是记公式，而是从 exp(x-m_new) = exp(x-m_old) × exp(m_old-m_new) 推导出来的
> 4. **性能直觉**：向量化不一定快（SwiGLU 踩坑）、cudaMalloc 的隐藏成本、Decode 阶段 GEMM 退化为 GEMV 变成 Memory-Bound

### 17.2 W8A16 / W4A16 量化基础

- **W** = Weight（权重），**A** = Activation（激活值/输入）
- **W8A16**: 权重 INT8 存储，激活值 FP16，实际计算 dequant 到 FP16 用 Tensor Core
- **激活值**: 每一层的中间结果(输入/输出 tensor)，每个 token 不同，动态变化
- **权重**: 模型参数，推理时固定不变，可离线量化

**INT8 对称量化 (per-channel)**:
```
scale[n] = max(|W[:, n]|) / 127.0    (每列一个 scale)
W_int8[k, n] = round(W[k, n] / scale[n])
反量化: W_fp16[k, n] = (float)W_int8[k, n] × scale[n]
```

**为什么对列（per-channel）而不是行**: GEMV output[n] = Σ_k input[k] × W[k,n]，
同一列的值加到同一个输出元素，用同一个 scale 不会跨输出混合误差。
且 scale[n] 可提到求和外: output[n] = scale[n] × Σ_k (int8_w[k,n] × input[k])

**为什么不做 W8A8**: Decode 是 memory-bound，瓶颈在读 weight 不在读 activation。
W8A16 已把 weight 压缩 4×。W8A8 需要额外的在线 activation 量化开销 + outlier 问题。

### 17.3 Custom GEMV 为什么比 cuBLAS 快

cuBLAS GEMM 对 M=1 低效的原因:
- 2D thread tile (128×128) 在 M=1 时退化为 1D，大量 padding 浪费
- Tensor Core 16×16 MMA 在 M=1 时大部分计算无效
- cuBLAS 内部 fallback 路径不如专用 kernel 优化

Custom GEMV 设计:
```
Grid: ceil(N/8) blocks, Block: 256 threads (8 warps × 32 lanes)
每个 warp 计算 1 个输出: out[n] = Σ_k W_int8[n,k] × scale[n] × x[k]

优化:
1. 输入 x 预加载到 shared memory（8 个 warp 复用）
2. char4 向量化读 INT8 权重（一次 4 bytes = 4 个 INT8）
3. 寄存器内 on-the-fly dequant（不写 FP16 缓存，直接计算）
4. Warp shuffle reduce 归约 32 个 lane 的 partial sum
效果: 直接读 INT8(1B) vs cuBLAS 读 FP16(2B) → 带宽减半 → 1.65× 加速
```

**★ GEMV 核心循环源码逐行详解**（文件: `linear_quantized_nvidia.cu` 第 260-280 行）：

```cuda
const int K4 = K / 4;  // K=1536 → K4=384 组，每组 4 个 INT8
for (int i = lane_id; i < K4; i += 32) {  // 32 线程平分 384 组
    // 一次读 4 个 INT8 权重 (向量化加载, 1 次内存事务读 4 bytes)
    char4 w4 = reinterpret_cast<const char4*>(w_row)[i];
    const int base = i * 4;

    // 从 shared memory 读 4 个 FP16 输入 (向量化 + smem 低延迟)
    __half2 x01 = *reinterpret_cast<const __half2*>(&x_smem[base]);
    __half2 x23 = *reinterpret_cast<const __half2*>(&x_smem[base + 2]);
    float2 fx01 = __half22float2(x01);  // FP16→FP32 (计算精度)
    float2 fx23 = __half22float2(x23);

    // ★ on-the-fly dequant: float(INT8) 就是反量化! scale 在循环外乘
    sum += float(w4.x) * fx01.x + float(w4.y) * fx01.y
         + float(w4.z) * fx23.x + float(w4.w) * fx23.y;
}
// 循环后: output[n] = warp_reduce_sum(sum) * scale[n]
```

**数学等价性**: `Σ (w_int8[k] × scale × x[k]) = scale × Σ (w_int8[k] × x[k])` — scale 是 per-channel 常数可提出循环。这就是 on-the-fly 的全部含义：不存 FP16 副本，直接用 INT8 累加，最后一次乘 scale。

**面试一句话**: "INT8 权重用 char4 一次读 4 个，直接 float() 转浮点做乘加累积，scale 在循环外面乘一次就完成反量化，省 2× HBM 带宽。" 



### 17.3b cuBLAS vs 自定义 Kernel 的选择规则

> **M=1 用自定义 GEMV，M>1 用 cuBLAS 的原因**：
>
> | | M=1 (Decode) | M>1 (Prefill) |
> |---|---|---|
> | **瓶颈** | Memory-bound (AI=0.5) | Compute-bound (AI=O(M)) |
> | **权重复用** | 每个元素只读 1 次 | 被 M 行复用 |
> | **Tensor Core** | 16×16 MMA 只填 1 行 = 93.75% 浪费 | 充分利用 |
> | **最优方案** | 自定义 GEMV (省带宽) | cuBLAS GEMM (用算力) |
>
> **通用规则**：
> - **Memory-bound** (GEMV、逐元素、reduce) → **手写**: 自定义数据格式 + 访存模式有大优势
> - **Compute-bound** (大矩阵 GEMM、卷积) → **用库**: cuBLAS/cuDNN 有最优 tile 调度 + TC 利用
> - **Fused kernel** (FlashAttention、FusedAddRMSNorm) → **手写**: 库无法融合多步操作减少 HBM round-trip
>
> **面试一句话**: "Memory-bound 手写省带宽，Compute-bound 用库吃算力，Fused kernel 手写减 round-trip。" 


### 17.4 FlashAttention v2 核心原理

**问题**: 标准 attention 的 scores 矩阵 O(N²) 需要物化在 HBM 中，读写 HBM 慢。

**解法**: 分块在线 softmax (Tiled Online Softmax)

```
将 KV 分成 Bc 大小的 tile，逐 tile 处理:
  m_new = max(m_old, tile_max)              ← 更新全局 max
  correction = exp(m_old - m_new)            ← 旧结果修正系数
  O_acc = O_acc × correction + Σ exp(s_t - m_new) × V[t]
  l_new = l_old × correction + Σ exp(s_t - m_new)
最终: output = O_acc / l_new
```

数学上等价于标准 softmax（不是近似），SMEM 只需 O(Bc) 而非 O(N)。

**项目三路径**:
1. **Naive Fused**: scores[total_len] 全驻 smem (< 48KB) → 短序列
2. **FlashAttention v2**: Bc tile 递推 → 长序列（Bc: FP32=32, FP16=64）
3. **FlashDecoding**: seq_len=1 时沿 KV 维切分增加 block 数 → 提高 SM 利用率

**★ FlashAttention 源码级详解**（文件: `self_attention_nvidia.cu` 第 312-453 行）：

```
Kernel 结构:
  blockIdx.x = query 位置 i,  blockIdx.y = attention head h
  一个 block 处理一个 (i, h) 对

Shared Memory 布局:
  s_q[head_dim]           — Q 行 (FP32, 加载一次所有 tile 复用)
  s_k[Bc × head_dim]      — K tile
  s_v[Bc × v_head_dim]    — V tile
  tile_scores[Bc]          — 当前 tile softmax 分数

Online Softmax 状态 (每线程寄存器):
  running_max = -INF      — 全局 max
  running_sum = 0          — 归一化因子
  o_acc[MAX_DV] = {0}    — 累积输出 (未归一化)
```

**核心循环（处理每个 KV tile）**:
```
Step 1: 加载 K/V tile → shared memory (global → smem)
Step 2: tile_scores[t] = Σ_d s_q[d] × s_k[t,d] × scale  (QK^T)
Step 3: tile_max = block_reduce_max(tile_scores)
         tile_scores[t] = exp(tile_scores[t] - tile_max)   ← safe softmax
         tile_sum = block_reduce_sum(tile_scores)
Step 4: ★ Online Softmax 更新:
         new_max = max(running_max, tile_max)
         old_correction = exp(running_max - new_max)    ← 修正旧累积
         new_correction = exp(tile_max - new_max)        ← 统一新 tile
         running_sum = running_sum × old_correction + tile_sum × new_correction
Step 5: 更新 O_acc:
         o_acc *= old_correction                          ← 缩放旧值
         o_acc += Σ_t tile_scores[t] × V[t] × new_correction  ← 加新贡献
最终: output = o_acc / running_sum                         ← 归一化
```

**correction factor 数学推导**:
```
旧 tile 在 m_old 下: exp(s - m_old)
需要统一到 m_new 下: exp(s - m_new) = exp(s - m_old) × exp(m_old - m_new)
                                      = 旧值 × old_correction
```

**面试一句话**: "Online softmax 每处理一个新 tile 就用 exp(m_old - m_new) 修正之前的累积结果，保证任何时刻 O_acc 除以 running_sum 都是正确输出。整个过程 S/P 矩阵从不写 HBM。" 

### 17.5 Fused Add+RMSNorm 设计

分离版 (2 kernel): 4R + 2W + 2次launch
融合版 (1 kernel): 3R + 2W + 1次launch → 省 1 次 hidden_size 全局读

```
grid:  (rows,)  block: (256,)
Pass 1: 读 a, b → sum=a+b → 写 residual_out + 寄存器累加 sum²
Reduce: block_reduce_sum → inv_rms = rsqrt(sum²/d + ε) → smem 广播
Pass 2: 读 residual_out (L1 cache hot) + weight → 归一化 → 写 out
优化: float4 向量化读写 (LD.128/ST.128)
```

### 17.6 GQA (Grouped Query Attention) 图解

```
Qwen2-1.5B: Q=12头, KV=2头, group_size=6

Q头 0-5  → 共享 KV头 0 (K0, V0)
Q头 6-11 → 共享 KV头 1 (K1, V1)

每个 Q 头独立计算: softmax(Qi @ Kj^T) @ Vj (j = i / group_size)
不存在跨组计算。
代码: kv_h = h / (nhead / kv_head)
好处: KV Cache 从 12×128×2=3KB/token 降到 2×128×2=0.5KB/token (减少 6×)
```

### 17.7 Memory-bound vs Compute-bound 判断方法

**Arithmetic Intensity (AI)** = FLOP / Bytes

RTX 4060 Ti 拐点:
- FP32: 22T / 288G = 76.4 FLOP/Byte
- FP16 TC: 176.5T / 288G = 613 FLOP/Byte

Decode GEMV (M=1, W_gate[1536,8960], INT8):
  FLOP = 2×1536×8960 ≈ 27.5M, Bytes = 1536×8960×1B ≈ 13.8M
  AI = 2 → 远低于 76.4 → **memory-bound**

Prefill GEMM (M=512):
  FLOP = 2×512×1536×8960 ≈ 14.1G, Bytes ≈ 37M
  AI = 381 → 高于 76.4 → **compute-bound**

### 17.8 Tensor Core FP32/FP16/TF32 关系

| 模式 | 输入 | 内部计算 | 吞吐 (4060Ti) |
|------|------|---------|---------------|
| CUDA Core FP32 | FP32 | FP32 (23-bit mantissa) | 22 TFLOPS |
| TF32 Tensor Core | FP32→TF32截断 | TF32 (10-bit mantissa) | ~88 TFLOPS |
| FP16 Tensor Core | FP16 | FP16 (10-bit mantissa) | 176.5 TFLOPS |

CUBLAS_GEMM_DEFAULT_TENSOR_OP hint 让 cuBLAS 自动使用 TF32 TC（FP32输入截断为TF32）。
但 decode 是 memory-bound，TC 吞吐差异不是决定因素，权重数据大小才是。

## 13. 量化原理与推理优化

### 24.1 为什么要量化？

Decode 阶段的 Linear 是 GEMV（M=1），算术强度 AI ≈ 0.5 FLOP/Byte → **Memory-Bound**。

```
瓶颈 = 搬运权重的字节数, 不是计算

FP32 权重: 每参数 4 字节 → Qwen2-1.5B = 6.78 GB
INT8 权重: 每参数 1 字节 → 2.37 GB → 搬运量减 2.9×
INT4 权重: 每参数 0.5 字节 → 1.73 GB → 搬运量减 3.9×

搬更少 → 等更少 → 快更多!
```

### 24.2 对称量化公式推导

**核心思路**：把连续的浮点范围 [-α, +α] 均匀映射到 [-Q_max, +Q_max] 的离散整数格子上。

```
Step 1: 确定范围
  α = max(|W|)  (absmax: 取最大绝对值)

Step 2: 每个格子的宽度 (scale)
  scale = α / Q_max
  INT8: Q_max = 127 → scale = α / 127
  INT4: Q_max = 7   → scale = α / 7

Step 3: 量化 (浮点 → 整数)
  W_int = clamp(round(W / scale), -Q_max-1, Q_max)
  clamp 到 [-128, 127] 而不是 [-127, 127]:
    scale 按 /127 算 → 保证对称性 (整数0 = 浮点0)
    clamp 用 [-128, 127] → 充分利用 INT8 的 256 个值
    (工业界标准做法, PyTorch 也这样)

Step 4: 反量化/还原
  W_approx = W_int × scale
```

#### 数值例子

```
w = 0.75, α = 1.0
scale = 1.0 / 127 ≈ 0.00787

量化:      round(0.75 / 0.00787) = round(95.33) = 95
还原:      95 × 0.00787 = 0.74765
误差:      |0.75 - 0.74765| = 0.00235 ≈ 0.3%

误差上界:  scale / 2 = α / (2 × Q_max) ← 来自 round() 舍入
```

### 24.3 量化粒度：Per-Tensor → Per-Channel → Per-Group

#### Per-Tensor（整个矩阵一个 scale）
```
1000 行矩阵:
  第 0 行最大值 = 10.0
  第 999 行最大值 = 0.01
  全局 α = 10.0 → scale = 10/127 = 0.0787

第 999 行的 0.01: round(0.01 / 0.0787) = 0 → 信息全丢!

一个异常大的行 "吃掉" 所有其他行的精度 → 不可用
```

#### Per-Channel（每行一个 scale）— INT8 标配
```
scale[n] = max(|W[n, :]|) / 127

第 0 行:   scale = 10.0/127 = 0.0787   格子够粗 (大值本身就不敏感)
第 999 行: scale = 0.01/127 = 0.0000787 格子极细!
  round(0.01 / 0.0000787) = 127 → 完美保留!

代价: 多存 N 个 FP32 scale ≈ 4KB (vs 矩阵 4MB → 可忽略)
```

#### Per-Group（每 group_size 个值一个 scale）— INT4 标配
```
INT4 只有 16 个格子 [-8, 7]:
  Per-Channel 对一行 4096 值: 4096 个值分 16 档 → 太粗!

Per-Group (group_size=128):
  4096 值 → 32 组, 每组 128 值 → 128 值分 16 档 → 精度可接受

scale 数量: N × (K/128), 用 FP16 存 → 额外存储仍很小
```

#### 粒度对比

| 粒度 | scale 数量 | 精度 | 推荐用途 |
|------|-----------|------|---------|
| Per-Tensor | 1 | 差 | 不推荐 |
| Per-Channel | N | 好 | INT8 |
| Per-Group (gs=128) | N × K/128 | 最好 | INT4 |

### 24.4 INT4 Pack 存储

两个 INT4 值打包成一个 uint8：

```
w[0] = 3,  w[1] = -2

3  的 4-bit 二进制:  0011
-2 的 4-bit 补码:    1110  (−2 + 16 = 14 = 0xE)

打包: byte = (high << 4) | (low & 0xF) = (0xE << 4) | 0x03 = 0xE3

解包:
  低: byte & 0x0F = 0x03 = 3       ✓
  高: byte >> 4   = 0x0E = 14
      14 ≥ 8 → 14 − 16 = −2       ✓

4-bit 补码规则:
  0~7:  正数, 直接用
  8~15: 负数, val - 16 → [−8, −1]
```

### 24.5 推理端优化策略（项目实现）

#### 朴素方案（0.4 tok/s）
```
每次 forward 每个 Linear:
  1. cudaMalloc 临时 buffer      ← ~1ms 同步!
  2. dequant: INT8 → FP32 全矩阵  ← 遍历所有权重
  3. cublasSgemm (FP32 GEMM)
  4. cudaFree                     ← ~1ms 同步!

一个 token = 196 次 Linear → 196 × 2ms = 392ms 纯分配开销!
```

#### 优化方案（57.5 tok/s, 143× 加速）

**优化 1: FP16 权重持久缓存**
```
static unordered_map<uintptr_t, __half*> g_weight_fp16_cache;

key = INT8 权重的 GPU 指针地址 (模型加载后地址固定不变, 天然唯一)
value = dequant 后的 FP16 权重

首次 token: find(key) MISS → cudaMalloc + dequant_kernel + cache → ~2ms
后续 token: find(key) HIT  → 直接返回 → ~100ns (hash lookup)

196 次 Linear × ~100ns = 0.02ms  vs  朴素方案 392ms
```

**优化 2: FP16 Tensor Core**
```
还原到 FP16（不是 FP32）→ cublasGemmEx FP16×FP16→FP32 累加
sm_89 FP16 Tensor Core: ~176 TFLOPS
sm_89 FP32 CUDA Core:   ~22 TFLOPS
= 8× throughput 提升

虽然 Decode 是 Memory-Bound, 但 FP16 权重 2B vs FP32 4B
→ 搬运量也减半 → 同样带宽下搬两倍
```

**优化 3: 静态 CachedBuffer（只增不缩）**
```cpp
struct CachedBuffer {
    void* ptr = nullptr;
    size_t size = 0;
    void ensure(size_t needed) {
        if (needed <= size) return;   // 够大 → 零开销
        if (ptr) cudaFree(ptr);
        cudaMalloc(&ptr, needed);
        size = needed;
    }
};
// 第一次 ensure(1024) → malloc
// 后续 ensure(1024) → skip (已经 1024 了)
// 后续 ensure(2048) → free + malloc 更大的
// 模式: 只在 size 增大时 malloc, 其余全跳过
```

#### 效果对比

| 版本 | 速度 | 原因 |
|------|------|------|
| 朴素 INT8 | 0.4 tok/s | 每次 malloc + dequant + free |
| 优化 INT8 | 57.5 tok/s | 缓存 + Tensor Core + 静态 buffer |
| FP32 baseline | ~30 tok/s | INT8 优化版比 FP32 快 1.7× |

### 24.6 dequant Kernel 核心逻辑

#### INT8 → FP16 (向量化版)
```cuda
__global__ void dequant_int8_to_fp16_vec4(__half* out, const int8_t* w,
    const float* s, size_t N, size_t K)
{
    size_t K4 = K / 4;
    for (size_t i = tid; i < N * K4; i += stride) {
        float sc = s[i / K4];              // 行号 → 取该行 scale
        char4 v = ((const char4*)w)[i];     // 一次读 4 个 INT8
        __half* d = out + i * 4;
        d[0] = __float2half(float(v.x) * sc);  // INT8 × scale → FP16
        d[1] = __float2half(float(v.y) * sc);
        d[2] = __float2half(float(v.z) * sc);
        d[3] = __float2half(float(v.w) * sc);
    }
}
// char4: CUDA 内建类型, {int8 x,y,z,w}, 一次 LD.32 读 4 字节
```

#### INT4 → FP16 (Group 解包版)
```cuda
__global__ void dequant_int4_to_fp16_group(__half* out, const uint8_t* w_packed,
    const __half* scales, size_t N, size_t K_packed, size_t num_groups, size_t gs)
{
    for (size_t i = tid; i < N * K_packed; i += stride) {
        size_t row = i / K_packed;
        size_t col_lo = (i % K_packed) * 2;      // 一个 byte → 两列

        // 每列属于哪个 group → 取对应 scale
        float s_lo = __half2float(scales[row * num_groups + col_lo / gs]);

        // 解包
        uint8_t byte_val = w_packed[i];
        int lo = byte_val & 0xF;      // 低 4 bit
        if (lo >= 8) lo -= 16;        // 4-bit 补码
        int hi = byte_val >> 4;       // 高 4 bit
        if (hi >= 8) hi -= 16;

        // 还原
        out[row * K_orig + col_lo]     = __float2half(lo * s_lo);
        out[row * K_orig + col_lo + 1] = __float2half(hi * s_hi);
    }
}
```

### 24.7 什么该量化，什么不该

| 权重类型 | 量化？ | 原因 |
|---------|--------|------|
| Linear weight | ✅ | 参数多、2D 矩阵、GEMM 主体 |
| Embedding | ❌ | 查表操作, 不做 GEMM |
| RMSNorm weight | ❌ | 1D 向量, 每层只有 d 个元素, 量化收益 ≈ 0 |
| Bias | ❌ | 1D, 元素极少 |

Qwen2-1.5B: 197 个权重被量化, 142 个跳过

### 24.8 显存计算

```
Qwen2-1.5B:
  FP32: 1.5B × 4B = 6.0 GB (放不下 8GB 显卡多模型并发)
  INT8: 1.5B × 1B + scales ≈ 1.5 GB
  INT8 + FP16 缓存: 1.5 + 3.0 = 4.5 GB (仍 < FP32!)
  INT4: 1.5B × 0.5B + scales ≈ 0.87 GB

推理中 INT8 路径总占用:
  INT8 权重:    1.5 GB
  FP16 缓存:    3.0 GB (首次 dequant 后永驻)
  KV Cache:     ~112 MB (4096 tokens)
  Activation:   ~50 MB
  总计:         ~4.7 GB < 8GB ✓
```

### 24.9 量化方法全景

#### 对称 vs 非对称量化

```
对称 (Symmetric):
  [-α, +α] → [-Q_max, +Q_max]
  scale = α / Q_max
  zero_point = 0 (整数0 = 浮点0)
  优点: 简单, GEMM 时不需要额外减 zero_point
  项目用的就是这种

非对称 (Asymmetric):
  [min, max] → [0, 2^bits - 1]
  scale = (max - min) / (2^bits - 1)
  zero_point = round(-min / scale)
  W_int = round(W / scale) + zero_point
  W_approx = (W_int - zero_point) × scale
  优点: 对偏态分布 (如 ReLU 后全正) 精度更高
  缺点: GEMM 计算时需要额外处理 zero_point → 更复杂
```

#### PTQ vs QAT

```
PTQ (Post-Training Quantization) — 训练后量化:
  模型训练好 → 直接量化权重 → 不再训练
  快速, 但精度受限
  项目用的就是 PTQ (scripts/quantize_model.py)

QAT (Quantization-Aware Training) — 量化感知训练:
  训练时插入 fake quantization 节点:
    forward: x_q = dequant(quant(x)) → 引入量化噪声
    backward: STE (Straight-Through Estimator) → 梯度直接穿过 quant
  效果最好, 但需要重新训练 (贵)
```

#### 高级量化方法

**GPTQ (逐列量化 + Hessian 误差补偿)**:
```
思想: 量化第j列产生的误差, 分摊到未量化的后续列

for j in range(K):
  1. 量化 W[:, j] → W_q[:, j]
  2. 误差 δ = W[:, j] - dequant(W_q[:, j])
  3. 补偿: W[:, j+1:] += δ × H_inv[j, j+1:] / H_inv[j,j]

  H = X^T X 是 Hessian 矩阵 (需要校准数据集计算)

效果: INT4 精度接近 FP16 (远超朴素 absmax)
代价: 量化过程慢 (需要 Hessian 逆)
```

**AWQ (Activation-Aware Weight Quantization)**:
```
观察: <1% 的权重通道对模型输出影响巨大 (salient channels)

方法:
  1. 用校准数据找"重要通道" (激活值大 → 对输出影响大)
  2. 对重要通道做等价缩放: W_imp *= s, X_imp /= s
     (等价变换不改最终结果, 但 W_imp 变大 → 量化分辨率更高)
  3. 正常量化

效果: INT4 精度媲美 GPTQ, 量化速度快得多
```

**SmoothQuant (W8A8)**:
```
目标: 同时量化权重和激活 (W8A8)

问题: 激活中存在 outlier channel (某些通道激活值 ~100×)
      → 激活量化时 outlier 通道的 scale 拉高, 其他通道精度崩

方法: Y = (X diag(s)^{-1}) (diag(s) W)
      → X ÷ s 变平滑 (激活 outlier 消除)
      → W × s 吸收难度 (权重变大但更容易量化)
      s 的选择平衡两边的量化难度

效果: W8A8 精度达到 FP16 水平
```

### intermediate 维度

```
FFN 由三个 Linear 组成 (SwiGLU 结构):

x [1, hidden=1536]
       ↓
 ┌── gate: [1536 → intermediate=8960] ──→ SiLU(gate)
 │                                             ↓
 └── up:   [1536 → intermediate=8960] ──→ up ⊙ SiLU(gate)
                                             ↓
                                  down: [8960 → 1536]
                                             ↓
                                 output [1, 1536]

intermediate = FFN 中间层维度
  经验规则: SwiGLU FFN 中 intermediate ≈ 8/3 × hidden
  Qwen2: 1536 × 8/3 ≈ 4096 → 实际用 8960 (5.8×, 更强表达)
  Llama: 2048 × 4 = 8192 (4.0×)

intermediate 越大 → FFN 表达能力越强，但参数/计算也越多
```

### Embedding tied vs not tied

```
tied:     Embedding 和 LM Head 共享同一个权重矩阵 W [vocab, hidden]
          Forward:  Embedding(id) = W[id, :]
                    LM_Head(h) = h × W^T
          省一份 vocab×hidden 参数 (151936×1536×4B ≈ 890MB)
          代表: GPT-2, BERT

not tied: Embedding 和 LM Head 各有独立权重
          自由度更高 (LM Head 可学到不同映射)
          参数多一份, 但对 1.5B 模型占比不大
          代表: Qwen2, LLaMA 3
```

### RoPE 位置编码实现细节

```
论文公式 (相邻维度配对):
  [d₀,d₁], [d₂,d₃], ..., [d₁₂₆,d₁₂₇]
  q'[2j]   = q[2j]   × cos(θⱼ) - q[2j+1] × sin(θⱼ)
  q'[2j+1] = q[2j+1] × cos(θⱼ) + q[2j]   × sin(θⱼ)

项目实现 (对半分配对, 等价但更高效):
  half_dim = head_dim / 2 = 64
  [d₀,d₆₄], [d₁,d₆₅], ..., [d₆₃,d₁₂₇]
  q'[j]           = q[j]           × cos(θⱼ) - q[j+half_dim] × sin(θⱼ)
  q'[j+half_dim]  = q[j+half_dim]  × cos(θⱼ) + q[j]          × sin(θⱼ)

  代码 (rope_nvidia.cu):
    float a = to_float(in[offset + j]);              // 前半
    float b = to_float(in[offset + j + half_dim]);   // 后半
    out[offset + j]           = from_float<T>(a * cos_val - b * sin_val);
    out[offset + j + half_dim] = from_float<T>(b * cos_val + a * sin_val);

为什么对半分比相邻好?
  前半和后半各自内存连续 → GPU 访存更高效
  in[offset + j] 和 in[offset + j + half_dim] 差固定 half_dim → 可预测
```

### MHA → MQA → GQA → MLA 注意力机制演进

#### MHA (Multi-Head Attention) — 原始 Transformer
```
每个 Q 头有独立的 K 和 V 头

num_q_heads = num_kv_heads = h

Q [seq, h, d_h], K [seq, h, d_h], V [seq, h, d_h]

KV Cache 大小: 2 × h × d_h × num_layers × seq_len × 2B (FP16)
假设 Qwen2 用 MHA (h=12):
  2 × 12 × 128 × 28 × 2B = 172KB/token
  4096 tokens → 688 MB

优点: 每头独立 KV → 注意力最灵活、质量最好
缺点: KV Cache 大 → 长序列/高并发吃不消
```

#### MQA (Multi-Query Attention) — PaLM, Gemini
```
所有 Q 头共享 1 组 KV

num_q_heads = h, num_kv_heads = 1

Q [seq, h, d_h], K [seq, 1, d_h], V [seq, 1, d_h]

KV Cache: 原来的 1/h
  Qwen2 假设用 MQA: 172KB/12 ≈ 14KB/token → 12× 节省

优点: KV Cache 极小 → 高并发部署友好
缺点: 所有头共享 KV → 表达能力下降 → 模型质量略差
```

#### GQA (Grouped-Query Attention) — Qwen2, LLaMA 3 (当前主流)
```
折中: 将 Q 头分组, 每组共享 1 套 KV

num_q_heads = h, num_kv_heads = g (1 < g < h)
group_size = h / g

Qwen2: h=12, g=2 → group_size=6
  Q头 0-5  共享 → KV头 0
  Q头 6-11 共享 → KV头 1

KV Cache: MHA 的 g/h = 2/12 = 1/6
  4096 tokens: 688/6 ≈ 115 MB

KV 头映射: kv_head_idx = q_head_idx / (num_heads / num_kv_heads)

self_attention 中: 相同 KV 被多个 Q 头复用 (broadcast)

实测: GQA 质量与 MHA 几乎无差, 是当前主流方案
```

#### MLA (Multi-head Latent Attention) — DeepSeek-V2/V3/R1
```
最激进的 KV Cache 压缩方案

核心: 不存 K/V, 存一个低维"潜在向量" c

  c = X × W_down_kv  → c [seq, c_dim]  (c_dim << kv_h × head_dim)
  K = c × W_up_k     → K [seq, h, d_h] (在线还原, 不缓存)
  V = c × W_up_v     → V [seq, h, d_h]

KV Cache 只存 c [seq, c_dim]:
  DeepSeek-V2: c_dim=512 vs MQA: 2×128=256
  但 MLA 只存一个 c 而非分开的 K+V → 实际更省

代价:
  每次 Attention 需额外乘 W_up_k, W_up_v 还原 → 多了计算
  RoPE 不能直接加在 c 上 → 需要独立的位置向量 q_rope, k_rope
  需要 absorbed attention 把 W_up 吸收到 Q/K 投影矩阵中

适用: 236B 级别模型, DeepSeek 系列
注意: DeepSeek-R1-Distill-Qwen-1.5B 不用 MLA, 它是 Qwen2 架构!
```

#### 四种注意力机制对比

| 方案 | num_kv_heads | KV Cache / token / layer (FP16) | 代表模型 |
|------|-------------|--------------------------------|---------|
| MHA | = num_heads | 2 × h × d_h × 2B | GPT-3, BERT |
| MQA | 1 | 2 × 1 × d_h × 2B | PaLM, Gemini |
| GQA | g (1 < g < h) | 2 × g × d_h × 2B | Qwen2, LLaMA 3 |
| MLA | N/A (存 latent) | c_dim × 2B | DeepSeek-V2/V3 |

### KV Cache 优化方法

#### 1. GQA — 减少 KV 头数 (架构级)
已详述。效果: h=12, g=2 → KV Cache 缩小 6×

#### 2. KV Cache 量化
```
FP16 → INT8: KV Cache 大小减半
  精度损失可控 (KV 值分布规律)
  搬运量减少 → Decode 速度提升
```

#### 3. PagedAttention (vLLM)
```
问题: 预分配 max_seq_len 的 KV Cache → 实际用一小部分 → 浪费!
      多请求各自预分配 → 显存碎片严重

PagedAttention:
  KV Cache 分成 Page (如 16 tokens/page)
  Block Table (类似 OS 页表) 管理物理 Page
  Page 按需分配, 用完释放

  显存利用率: ~38% → ~98%
  同一 GPU 可服务 ~2.5× 更多并发请求

类比: OS 虚拟内存 → 物理页帧映射
```

#### 4. Sliding Window Attention
```
只保留最近 W 个 token 的 KV Cache:
  K_cache = K_cache[max(0, t-W) : t]

Mistral: W=4096 → KV Cache 永远不超过固定大小
适合长序列 → 但无法关注超过 W 距离前的信息
```

#### 5. Token Pruning / Eviction
```
根据注意力分数移除不重要的 KV:
  H2O (Heavy Hitter Oracle): 保留注意力得分最高的 token
  StreamingLLM: 只保留最初几个 + 最近几个 token

适合超长序列推理, 但可能丢失关键上下文
```

### 采样解码: Temperature / Top-K / Top-P

```
LLM 输出 logits [vocab_size], 需要选下一个 token

采样管线 (qwen2.cpp 的 sample_token() 完整实现):

步骤①: 温度缩放
  logits[i] /= T
  T>1 → 分布更平(随机), T<1 → 分布更尖(确定), T=0 → argmax

步骤②: 数值稳定 Softmax
  p[i] = exp(logits[i] - max) / Σexp(logits[j] - max)

步骤③: Top-K 截断
  排序后只保留概率最高的 K 个 token

步骤④: Top-P (Nucleus) 截断
  累积概率达到 P 就停
  自适应: 模型确信时保留少, 不确信时保留多

步骤⑤: 重归一化
  截断后概率和恢复为 1

步骤⑥: Multinomial 采样
  生成 [0,1) 随机数, 逆 CDF 采样

infer()  vs infer_ex():
  infer():    GPU argmax (无需拷贝 logits)
  infer_ex(): logits D2H → CPU sampling (灵活)
  为什么 CPU? vocab ~151K 排序 CPU 秒完成, D2H 只需搬 600KB
```

### Prefill vs Decode
```
Prefill (首次处理 prompt):
  seq_len = prompt 长度 (如 50)
  Linear: [50, 1536] × [1536, 1536] → 大 GEMM → Compute-Bound

Decode (逐 token 生成):
  seq_len = 1
  Linear: [1, 1536] × [1536, 1536] → GEMV → Memory-Bound!
  瓶颈: 权重读取 (每 token 读完整权重) + KV Cache 读取
```

### KV Cache 显存计算
```
Qwen2-1.5B (GQA 12Q/2KV):
  每 token 每层: 2 heads × 128 dim × 2 (K+V) × 2B = 1024 B
  28 层: 28 KB/token
  1024 tokens: 28 MB
  4096 tokens: 112 MB

如果 MHA (12Q/12KV):
  4096 tokens: 672 MB → 6× 更多!
```

## 18. AI Infra 面试八股文

> 本节合并了所有 AI Infra 方向的面试八股题。


### Q: FlashAttention 的核心原理是什么？相比标准 Attention 的优势？

> 标准 Attention 将 N×N score 矩阵写回 HBM，空间 O(N²)，N=4096 时 64MB（FP32）。
>
> FlashAttention 将 KV 按 Bc 大小分 tile，在 SRAM(SMEM) 上逐 tile QK^T→softmax→×V，用 Online Softmax 逐 tile 更新。SMEM=O(Bc×d) 常数。
>
> **优势**：①显存 O(N) 不是 O(N²) ②减少 HBM 读写→实测快 2-4× ③支持超长序列

### Q: Online Softmax 怎么实现？correction factor 是什么？

> 逐 tile 维护 running_max/sum/o_acc。处理新 tile 后 max 可能更新 → 旧的 exp 值基于旧 max，全错了！
>
> **correction factor** = `exp(old_max - new_max)`。因为 `exp(x - m_new) = exp(x - m_old) × exp(m_old - m_new)`，所以旧累积值 ×correction 就统一到了新 max 基准。
>
> 更新公式：`old_corr = expf(running_max - new_max); running_sum = running_sum × old_corr + tile_sum × new_corr; o_acc = o_acc × old_corr + tile_ov × new_corr`。

### Q: FlashAttention v1 和 v2 的核心区别？v3 呢？

> **v1**：外 KV 内 Q 循环 → running_max/sum/o_acc 每处理一个 Q tile 后写回 HBM → 慢。
> **v2**：翻转为外 Q 内 KV → 状态**始终在寄存器**不写 HBM → ~2× faster。
> **v3**：面向 H100(sm_90)，Warp Specialization + FP8 + 异步 WGMMA。sm_89 不支持。

### Q: GQA 的原理和收益？

> 多 Q 头共享 KV 头。Qwen2: 12Q/2KV，group_size=6。映射 `kv_h = h / group_size`。
>
> KV Cache 缩小 6×（每 token 28KB→按 MHA 算 168KB）。4096 tokens：112MB vs 672MB。

### Q: Softmax 计算时为什么要减 max？

> 防 exp 上溢。`exp(89) ≈ FP32 max`，`exp(90) = inf`。减 max 后最大值变 0，`exp(0)=1`。
>
> 数学等价：`softmax(x) = exp(x-m)/Σexp(x-m)`，分子分母同乘 `e^{-m}` 约掉。

### Q: 你的框架怎么支持多设备？

> C 函数指针表（LlaisysRuntimeAPI，12 个函数指针）。每设备实现一套 static 结构体。`getRuntimeAPI(dev)` 用 O(1) 数组索引。
>
> 优势：C ABI→ctypes 直调、一次间接寻址 vs virtual 两次、函数表 static const→编译器可优化。

### Q: Prefill 和 Decode 各自的性能瓶颈？

> **Prefill**：seq_len>1→大 GEMM→Compute-Bound→用 Tensor Core。
> **Decode**：seq_len=1→GEMV→Memory-Bound→瓶颈在读权重和 KV Cache→量化(INT8/INT4)减少读取量→项目 INT8 加速 143×。

### Q: KV Cache 优化方法有哪些？

> ①GQA 减 KV Head 数 ②量化(FP16→INT8/INT4) ③PagedAttention 按需分页消灭碎片 ④MQA（极端，所有 Q 共享 1 组 KV）⑤Sliding Window 只保留最近 N 个

### Q: 算子融合的原理和收益？

> 多算子各自 launch kernel → 中间结果写回 HBM 再读取。融合后中间结果留在寄存器/SMEM。
>
> 项目 SelfAttention 将 QK^T→Mask→Softmax→×V 四步融合为 1 个 kernel。score 全程在 SMEM。不融合则 score 矩阵每步都写回读回→4× HBM 流量。
> 收益：减少 HBM 读写 + 减少 kernel launch 开销(~5-15µs/次)。

### Q: 你的项目中 FlashAttention 和 Naive Attention 是怎么选择的？

> 运行时检查 `naive_smem = (total_len + 8 + head_dim) × 4B`。如果 ≤48KB → Naive Fused（短序列更快，无 Online Softmax 开销）。>48KB → FlashAttention v2（支持任意长度，SMEM=O(Bc) 常数约 33KB）。


### Q: 量化的核心原理是什么？为什么量化能加速 LLM 推理？

> 量化将浮点权重映射到低位整数（如 INT8/INT4），**减小权重体积**。LLM Decode 阶段的 Linear 是 GEMV（M=1），算术强度 AI ≈ 0.5 FLOP/Byte，是典型的 **Memory-Bound**——瓶颈在搬运权重的字节数，不在计算。
>
> INT8 将每个参数从 4 字节缩到 1 字节 → 搬运量减 4×。在 RTX 4060 Ti 上项目实测 INT8 从 0.4→57.5 tok/s（143× 加速，最终 +KV8+Graph 达 132 tok/s），主要收益来自 ①权重搬运量减少 ②FP16 Tensor Core 更高吞吐。

### Q: 对称量化和非对称量化有什么区别？你的项目用的是哪种？

> **对称量化**：`scale = max(|W|) / Q_max`，零点固定为 0（整数 0 = 浮点 0.0）。优点是简单，GEMM 时不需要额外减去 zero_point。
>
> **非对称量化**：`scale = (max - min) / (2^bits - 1)`，有 zero_point 参数。对偏态分布（如 ReLU 后全正）精度更高，但计算时需要额外处理 zero_point。
>
> 项目用**对称量化**，因为 Transformer 的 Linear 权重分布近似零均值对称，absmax 足够且实现更简单。

### Q: Per-Tensor、Per-Channel、Per-Group 量化有什么区别？分别适用什么场景？

> **Per-Tensor**（整个矩阵一个 scale）：一个异常大的行会拉高全局 scale → 其他行精度崩塌。不推荐。
>
> **Per-Channel**（每行一个 scale）：每行独立 scale，互不影响。额外存 N 个 FP32 scale（~4KB vs 矩阵 ~4MB 可忽略）。INT8 标配。
>
> **Per-Group**（每 group_size 个元素一个 scale）：粒度更细，精度最高。INT4 必须用，因为 16 个格子对一整行太粗。项目 INT4 用 group_size=128。
>
> 粒度越细精度越高，但 scale 存储和计算开销越大。实际中 INT8 Per-Channel 和 INT4 Per-Group(128) 是工业界标准配置。

### Q: INT4 的 pack/unpack 是怎么实现的？

> 两个 INT4 值打包成一个 uint8：`byte = (high_nibble << 4) | (low_nibble & 0xF)`。
>
> 解包：低 4 bit `lo = byte & 0x0F`，高 4 bit `hi = byte >> 4`。4-bit 补码还原：值 ≥ 8 则减 16（即 8→−8, 14→−2, 15→−1）。
>
> 存储量减半：原 K 列 int8 → K/2 列 uint8。

### Q: 你项目的量化推理 143× 加速具体是怎么实现的？瓶颈在哪？

> 三个优化叠加：
>
> ①**FP16 权重持久缓存**：权重在推理过程中不变，首次 dequant INT8→FP16 后存入 `unordered_map<uintptr_t, __half*>`，后续 196 次 Linear/token 全部 hash lookup 命中（~100ns vs dequant ~2ms），消灭了重复反量化开销。
>
> ②**FP16 Tensor Core**：还原到 FP16 而不是 FP32，用 `cublasGemmEx` 的 FP16 Tensor Core 路径（sm_89: ~176 TFLOPS vs FP32 ~22 TFLOPS），同时 FP16 权重只有 FP32 一半大小，搬运量也减半。
>
> ③**静态 CachedBuffer**：输入 FP32→FP16 转换复用同一个只增不缩的 buffer，消除每次 `cudaMalloc/cudaFree` 的同步开销（每次 ~1ms × 196 次 = 196ms）。
>
> 朴素版瓶颈在 cudaMalloc/cudaFree 的同步等待，不是 dequant 本身。

### Q: 量化推理的完整流程是什么？从离线量化到在线推理？

> **离线阶段** (`scripts/quantize_model.py`):
> ```
> model.safetensors (FP32, 3GB)
>   → per-channel absmax: scale[n] = max(|W[n,:]|) / 127
>   → W_int8[n,k] = clamp(round(W[n,k] / scale[n]), -128, 127)
>   → 保存: quantized_weights.npz (INT8 权重 ~0.75GB + scale 向量)
>   注: 只量化 2D Linear 权重, Embedding/RMSNorm/Bias 不量化
> ```
>
> **在线推理加载**: cudaMemcpy 将 INT8 权重 + scale 搬到 GPU 显存
>
> **每次 Linear forward 的分发逻辑** (`linear_quantized_nvidia.cu` 第 460-530 行):
> ```
> if (M == 1)  → Decode 路径:
>     int8_gemv_kernel(W_int8, x, scale, out)
>     ★ 直接读 INT8 → float() 隐式转换 → 累加 → 乘 scale
>     ★ on-the-fly: 不存 FP16 副本, 省 2× 带宽
>
> else (M > 1) → Prefill 路径:
>     fp16_weight = get_or_create_fp16_weight(W_int8, scale)
>       第一次: INT8 → FP16 反量化 → 缓存到 unordered_map
>       后续: hash lookup 命中 (~100ns)
>     cublasGemmEx(fp16_weight, x_fp16, out, Tensor Core)
>     ★ persistent cache: 143× 优化的核心
> ```
>
> **面试一句话**: "离线 per-channel absmax 量化存 INT8+scale，在线推理 M=1 走 GEMV on-the-fly 反量化省带宽，M>1 走 FP16 持久缓存 + Tensor Core 吃算力。" 

### Q: 为什么用 GPU 指针地址做权重缓存的 key？

> 模型加载后，每个权重矩阵在 GPU 上的地址是固定不变的（CachingAllocator 分配后不迁移）。不同权重矩阵的地址天然不同 → `reinterpret_cast<uintptr_t>(ptr)` 就是唯一标识。
>
> 比用字符串名称（如 "model.layers.0.self_attn.q_proj.weight"）做 key 更快——uintptr_t 比较是一次整数比较 O(1)，字符串比较是 O(n)。

### Q: PTQ 和 QAT 有什么区别？

> **PTQ（Post-Training Quantization）**：模型训练好后直接量化权重，不再训练。快速，但精度受限。项目用的就是 PTQ。
>
> **QAT（Quantization-Aware Training）**：训练时插入 fake quantization 节点模拟量化噪声。forward 时 `x_q = dequant(quant(x))`，backward 时用 STE（Straight-Through Estimator）让梯度直接穿过量化操作。效果最好但需要重新训练（贵）。

### Q: GPTQ 的核心思想是什么？

> 逐列量化 + Hessian 误差补偿。量化第 j 列产生的误差 δ，通过 Hessian 逆矩阵分摊到未量化的后续列：`W[:, j+1:] += δ × H_inv[j, j+1:] / H_inv[j,j]`。
>
> H = X^T X 是 Hessian 矩阵（需要校准数据集）。效果：INT4 精度远超简单 absmax，接近 FP16。代价：量化过程需要计算 Hessian 逆，速度较慢。

### Q: AWQ 和 GPTQ 的区别？

> **GPTQ**：修改量化后的权重值（误差补偿）。
>
> **AWQ**：修改量化前的等价变换。找到 <1% 的"重要通道"（激活值大→对输出影响大），对其做缩放 W_imp × s, X_imp ÷ s（等价变换不改计算结果）。缩放后重要通道的权重变大 → 量化分辨率更高 → 精度更好。
>
> AWQ 比 GPTQ 量化速度快得多（不需要 Hessian），INT4 精度相当。

### Q: SmoothQuant 解决什么问题？

> 解决**激活量化**的 outlier 问题。某些通道激活值是其他通道的 100×，per-tensor 量化时这几个 outlier 通道把其他通道的精度吃掉。
>
> 方法：Y = (X ÷ s)(s × W)，把激活的难度"平滑"到权重上。s 的选择平衡两边的量化难度。效果：W8A8（权重和激活都量化为 INT8）精度达到 FP16 水平。

### Q: Embedding 和 RMSNorm 为什么不量化？

> **Embedding**：查表操作（按 token_id 取一行），不做 GEMM，量化不减少计算/传输瓶颈。
>
> **RMSNorm weight**：1D 向量，每层只有 hidden_dim=1536 个值（6KB），量化收益几乎为零。而且 RMSNorm 在归一化时需要较高精度（涉及 rsqrtf），量化可能损害精度。
>
> Qwen2-1.5B: 197 个 Linear weight 被量化, 142 个 Embedding/Norm/Bias 跳过。

### Q: 量化后模型的显存占用怎么算？

> Qwen2-1.5B 推理时 INT8 路径总占用：
> - INT8 权重原始存储: ~1.5 GB
> - FP16 缓存（首次 dequant 后永驻）: ~3.0 GB
> - KV Cache (4096 tokens, GQA 2 head): ~112 MB
> - Activation buffer: ~50 MB
> - 总计: ~4.7 GB < 8GB RTX 4060 Ti ✓
>
> 对比 FP32: 6.0 GB 纯权重就接近占满。

### Q: MHA、MQA、GQA 有什么区别？你的项目用的是哪种？

> **MHA** (Multi-Head Attention): 每个 Q 头有独立 K/V 头, `num_kv_heads == num_heads`, KV Cache 最大但质量最好。**MQA** (Multi-Query Attention): 所有 Q 头共享 1 组 K/V, `num_kv_heads == 1`, KV Cache 最小但表达力下降。**GQA** (Grouped-Query Attention): 折中方案, Q 头分组共享 KV, `1 < num_kv_heads < num_heads`, 实测质量接近 MHA。
>
> 项目中 Qwen2-1.5B 用 **GQA**: `num_heads=12, num_kv_heads=2`, 6 个 Q 头共享 1 组 KV, KV Cache 缩小 6×。LLaMA-3.2-1B 也用 GQA: `num_heads=32, num_kv_heads=8`, 4 个 Q 头共享 1 组 KV。
>
> **实现细节**: `self_attention` 算子内部做 KV broadcast, 相同 KV 被多个 Q 头复用。

### Q: 什么是 MLA？和 GQA 有什么区别？

> **MLA** (Multi-head Latent Attention) 是 DeepSeek-V2/V3 发明的注意力机制。核心思想: **不存 K/V, 存一个低维潜在向量 c**。推理时从 c 在线还原 K/V: `c = X × W_down`, `K = c × W_up_k`, `V = c × W_up_v`。KV Cache 只存 c_dim 大小的向量, 压缩比甚至超过 MQA。
>
> 对比 GQA: GQA 减少 KV 头数, MLA 直接压缩 KV 的维度。代价是推理时多了 W_up 矩阵乘, 且 RoPE 不能直接加在 c 上, 需要独立位置向量。
>
> **注意**: DeepSeek-R1-Distill-Qwen-1.5B 不用 MLA, 它是 Qwen2 架构 (GQA), 只是权重蒸馏自 DeepSeek-R1。

### Q: RoPE 的实现有几种方式？项目中用的是哪种？

> RoPE 论文用**相邻维度配对**: 对 `(d₂ⱼ, d₂ⱼ₊₁)` 做二维旋转。项目实现用**对半分 (half_dim split)**: 对 `(dⱼ, dⱼ₊half_dim)` 做旋转, 其中 `half_dim = head_dim/2`。数学上**完全等价**, 只是维度排列不同。
>
> 对半分的优势: 前半和后半各自内存连续, GPU 访存更高效。代码中 `in[offset+j]` 和 `in[offset+j+half_dim]` 差固定 `half_dim` → 访问模式可预测, 缓存友好。

### Q: 什么是 PagedAttention？为什么 vLLM 用它？

> **问题**: 传统 KV Cache 预分配 max_seq_len 大小的连续内存, 但实际请求长度各异, 导致显存利用率仅 ~38%。多个并发请求各自预分配 → 显存碎片严重, 能服务的请求数大幅下降。
>
> **PagedAttention**: 将 KV Cache 分成固定大小的 Page (如 16 tokens/page), 用 Block Table (类似 OS 页表) 管理物理 Page。按需分配, 用完释放。显存利用率提升到 ~98%, 同一 GPU 可服务 ~2.5× 更多并发请求。
>
> 类比 OS: 虚拟地址空间→物理页帧映射, 解决内存碎片 + 提高利用率。

### Q: Temperature、Top-K、Top-P 各自作用？它们的执行顺序是？

> **Temperature**: 缩放 logits, `logits /= T`。T>1 更随机, T<1 更确定, T→0 等效 argmax。
> **Top-K**: 排序后只保留概率最高的 K 个 token, 其余置零。`top_k=1` = argmax。
> **Top-P** (Nucleus): 按概率从高到低累加, 累积概率达到 P 就截断。**自适应**: 模型确信时保留少, 不确信时保留多。
>
> **项目执行顺序**: ① Temperature 缩放 → ② Softmax → ③ Top-K 截断 → ④ Top-P 截断 → ⑤ 重归一化 → ⑥ Multinomial 采样。Top-K + Top-P **组合使用**(先 K 后 P)。
>
> `infer()` 用 GPU argmax, `infer_ex()` 将 logits D2H 到 CPU 做采样(vocab ~151K 的排序 CPU 秒完成, D2H 仅搬 600KB)。

### Q: 你的项目权重加载流程是怎样的？

> **三层架构**: Python (safetensors 加载 + 名称映射) → ctypes 绑定 (类型转换) → C++ (权重分发)。
>
> **具体流程**: ① 读 `config.json` 填充 `LlaisysQwen2Meta` 结构体 → ② 调 `llaisysQwen2ModelCreate()` 创建 C++ 模型 → ③ `load_file("model.safetensors")` 加载权重到 numpy/torch → ④ 按名称映射: `"model.layers.{i}.self_attn.q_proj.weight"` → `weights.attn_q_w[i]` → ⑤ C++ `distribute_weights()` 将权重分发到 Attention/MLP 子模块, 区分 FP32/INT8/INT4 三条路径。


### Q: 你的项目怎么支持多种 GPU 设备？

> 三层抽象: ① **LlaisysRuntimeAPI** C 函数指针表定义 12 个统一接口 (malloc/free/memcpy/stream 等) → ② **getRuntimeAPI(device_type)** switch 路由到具体设备实现 → ③ 每种设备实现各自的 `static const LlaisysRuntimeAPI` 结构体。
>
> 算子层也做分发: 每个算子 `op.cpp` 根据 tensor 所在设备 `switch(deviceType())` 路由到 `nvidia::add()` / `metax::add()` 等设备特定实现。
>
> 编译期隔离: `#ifdef ENABLE_NVIDIA_API` 宏控制, 未启用设备代码不编译。xmake 条件编译 + 按需链接。

### Q: 国产 GPU 代码怎么和 NVIDIA CUDA 复用？

> 沐曦 MACA SDK 和天数 TOPSRIDER SDK 提供 **CUDA 兼容 API**: mxcc/topscc 编译器自动将 `cudaMalloc` 映射到 `macaMalloc`/`topsMalloc`, `cublasSgemm` 映射到对应 BLAS。.cu 文件写标准 CUDA 语法, 三种编译器各自编译。
>
> 差异通过 `compat.cuh` 隔离: 不同的 namespace、错误检查函数名、以及可能不同的 Warp Size (C500 可能 128 而非 32)。纯 elementwise 算子 (Add/Embedding) 无需适配; 含 warp reduce 的算子 (RMSNorm/Argmax) 需要调整归约轮数和 shared memory 布局。

### Q: 为什么用 C 函数指针表而不是 C++ 虚函数做设备抽象？

> 四个原因: ① **C ABI**: Python ctypes 可直接调用, 无 C++ name mangling; ② **一次间接寻址**: 函数指针 `[base+offset]` 一次跳转, 虚函数需先读 vptr 再读 vtable, 两次间接; ③ **编译隔离**: 不同设备用不同编译器 (nvcc/mxcc), 不需共享 vtable 布局; ④ **零对象开销**: 纯 C 结构体, 无构造析构和虚表指针。
>
> 项目中: 设备 API 层用函数指针表 (热路径), Allocator 层保留 virtual (非热路径)。


### Q: GPU 有哪些内存层次？延迟和大小分别是？

> Register (~1 cycle, 255/线程) → Shared Memory (~20-30 cycle, 48-100KB/SM, Block 共享) → L1 Cache (~30 cycle, 与 SMEM 共享 128KB SRAM) → L2 Cache (~200 cycle, 32MB, 全 GPU) → Global Memory/GDDR (~400 cycle, 8GB, 288 GB/s)。
>
> **关键**：HBM/GDDR 就是 Global Memory 的物理介质。Local Memory 物理上在 Global Memory 中（register spill 慢的原因）。L1 和 Shared Memory 共享同一块 SRAM。
>
> **项目中各层次的具体利用**：
> - **Register**: GEMV 的 `sum` 累加器、FlashAttention 的 `o_acc[]`/`running_max`/`running_sum` → 零延迟累积。
> - **Shared Memory**: GEMV 用 smem 存输入向量 x[K]（8 个 warp 复用，省 8× HBM 带宽）；FlashAttention 用 smem 存 Q/K/V tile + scores（S/P 矩阵从不写 HBM）。
> - **Coalesced Access**: GEMV 用 `char4` 向量化 → 32 线程 × 4 bytes = 128 bytes 合并成一个事务 → 带宽利用率最大化。
> - **优化思路总结**: 数据复用高 → shared memory；只用一次 → coalesced access 直读 HBM；累积变量 → register。核心目标：让 kernel 成为 compute-bound 而不是 memory-bound。
>

### Q: Decode 阶段 Linear 算子是 Compute-Bound 还是 Memory-Bound？

> **Memory-Bound**。计算: Decode 时 M=1, `AI = 2×1×N×K / (N×K×4B) = 0.5 FLOPs/Byte`。RTX 4060 Ti 拐点 = 22.1 TFLOPS / 288 GB/s ≈ 76.7 FLOPs/Byte。0.5 << 76.7 → 远在 Memory-Bound 区域。每个权重元素只用一次就扔 → 算力闲置, 带宽是瓶颈。Batch 增大可缓解: batch=128 时 AI≈64, 接近拐点。

### Q: 8GB 显存如何部署 7B 模型？
> **必须 INT4 量化**: 7B×0.5B=3.5GB (vs FP16 14GB 放不下)。剩余 ~4GB 给 KV Cache + 激活。KV Cache (假设 28 层, 4 KV heads, d=128): 每 token 56KB, 3GB 余量支持 ~8K tokens。优化: ① W4A16 量化 ② FP16/INT8 KV Cache ③ PagedAttention (显存利用率 38%→98%) ④ Continuous Batching ⑤ max_seq_len 限制。


### Q: Batch 推理是怎么加速 Decode 的？

> Decode 时 seq_len=1，Linear 是 GEMV (AI=0.5, Memory-Bound)。如果同时处理 B 个请求，变成 `[B, hidden] × [hidden, hidden]`，即 GEMM。B=32 时 AI=16，B=128 时 AI=64 → 跨过拐点变成 Compute-Bound → Tensor Core 发挥作用。
>
> **代价**: 每个请求的 KV Cache 不同 → KV Cache 显存 ×B → 需要 PagedAttention 管理。

### Q: Tensor Parallelism 和 Pipeline Parallelism 的区别？

> **TP**: 一层内的权重拆分到多个 GPU。如 Linear[1536, 1536] 拆成两半 [1536, 768] × 2。需要 AllReduce 通信。适合层内计算密集。
> **PP**: 不同层放不同 GPU。GPU0 跑 Layer 0-13，GPU1 跑 Layer 14-27。需要 micro-batch 流水线避免 bubble。适合层数多。

### Q: 什么是 KV Cache 的 PagedAttention？

> vLLM 提出。将 KV Cache 按固定大小(如 16 tokens)的 **Page** 分配。请求的 KV Cache 不必连续存储——用 Block Table (类似 OS 页表) 记录物理 Page 位置。
>
> **解决的问题**: 预分配 max_seq_len 大小的 KV Cache → 大量浪费(平均利用率 ~38%)。PagedAttention 按需分页 → 利用率 ~98% → 同一 GPU 可服务 ~2.5× 更多请求。

### Q: INT8 量化的误差怎么控制？

> **Per-channel quantization**: 每个输出 channel 独立计算 scale = max(abs(W_col)) / 127。比 per-tensor 精度高很多。
>
> **Outlier channels**: 少数 channel 的权重值特别大（~5-10×），per-channel scale 可以适配。如果 per-tensor 则这几个 channel 的 scale 拉高其他所有 channel → 精度劣化。
>
> **校准 (Calibration)**: 跑少量输入统计每层激活值 range → 确定激活 scale。权重 scale 离线确定。

### Q: 混合精度推理 (Mixed Precision) 是什么？

> 模型权重和激活存 FP16/BF16 (省显存省带宽)，矩阵乘用 FP16 Tensor Core (高吞吐)，但**累加器** (accumulator) 用 FP32 (防精度损失)。
>
> cuBLAS 的 `cublasGemmEx(..., CUDA_R_16F, CUDA_R_16F, CUDA_R_32F, CUBLAS_COMPUTE_32F)` 就是这种模式: 输入 FP16 × FP16 → 累加 FP32 → 输出 FP32。
>
> 项目中 RMSNorm/Softmax 等算子也是: load FP16 → to_float() → FP32 计算 → from_float() → store FP16。

### Q: 为什么 Decode 阶段需要读完整权重？能不能只读一部分？

> 每个 Linear 算 `y = W × x`，x 是 [1, hidden]，W 是 [hidden, out]。计算 y 的每个元素需要 W 的整行 → 必须读完所有权重。
>
> **优化方向**: 量化 (INT8/INT4 减少每个权重的字节数)、稀疏化 (跳过零权重，但需要硬件支持)、模型蒸馏 (用更小的模型)。




### Q: FlashAttention 的核心算法是什么？为什么能省显存？

> **核心**: Online Softmax + Tiling。不存完整 S=QK^T 矩阵（N×N 大小），而是按 Block 分块计算，边算边更新 softmax 的统计量 (max, sum)。
>
> **传统 Attention**: 显存 O(N²) — 存完整 S 和 P=softmax(S) 矩阵
> **FlashAttention**: 显存 O(N) — 只在 SMEM 中存一个 Tile
>
> **算法流程 (单个 Query Block)**:
> ```
> 初始化: m = -inf (running max), l = 0 (running sum), O = 0 (running output)
> for each KV block j:
>     S_ij = Q_i × K_j^T            // 在 SMEM 中计算 (Br×Bc tile)
>     m_new = max(m, rowmax(S_ij))   // 更新 running max
>     P_ij = exp(S_ij - m_new)       // 安全 softmax (减 max 防溢出)
>     l_new = exp(m - m_new) * l + rowsum(P_ij)  // 更新 running sum
>     O = (exp(m - m_new) * l / l_new) * O + (1/l_new) * P_ij × V_j  // 修正旧输出 + 加新贡献
>     m = m_new; l = l_new
> ```
>
> **关键点**: `exp(m - m_new)` 是修正因子 — 当新 block 的 max 更大时，需要把之前累积的 O 按比例缩小。这就是 **Online Softmax** 的精髓。
>
> **项目中**: FlashAttention kernel 的 Decode 路径就是这个算法 (seq_len=1 时 inner loop 只跑一轮)。


### Q: FlashAttention "O(N²)→O(N) 空间复杂度"具体指什么？（面试追问）

> **O(N²)** 指传统 Attention 需要在 HBM 中显式存储:
> - S = QK^T → [N, N] 矩阵
> - P = softmax(S) → [N, N] 矩阵
> 两个矩阵共 2N² 个浮点数。
>
> **O(N)** 指 FlashAttention 只需额外存储每行 Query 的两个统计量:
> - m_i (running max): N 个标量
> - l_i (running sum): N 个标量
> 共 2N 个浮点数。计算中的 S tile 在 SMEM 中（Br×Bc 大小），不占 HBM。
>
> **单线程 O(1) vs 全局 O(N)**: 你的代码中 `running_max` / `running_sum` 在每个线程的寄存器里（O(1)），但总共有 N 行各需要一份 → 全局额外空间 = O(N)。
>
> 这是 FlashAttention 论文原文的表述: "requires O(N) additional memory beyond inputs and output"。


### Q: GQA / MQA / MHA 有什么区别？

> | 类型 | 全称 | Q/K/V Head 数 | KV Cache 大小 | 准确度 |
> |------|------|-------------|-------------|--------|
> | **MHA** | Multi-Head Attention | Q=H, K=H, V=H | 基准 | 最高 |
> | **MQA** | Multi-Query Attention | Q=H, K=**1**, V=**1** | **1/H** | 较低 |
> | **GQA** | Grouped-Query Attention | Q=H, K=**G**, V=**G** (G<H) | **G/H** | 接近 MHA |
>
> **原理**: 多个 Q Head 共享同一组 K/V Head。G=1 时退化为 MQA, G=H 时退化为 MHA。
>
> ```
> MHA (H=8):  Q: [h0 h1 h2 h3 h4 h5 h6 h7]
>             K: [h0 h1 h2 h3 h4 h5 h6 h7]  // 8 个独立 KV head
>
> GQA (H=8, G=2):  Q: [h0 h1 h2 h3 | h4 h5 h6 h7]
>                  K: [    g0      |     g1      ]  // 4个Q共享1个KV head
>
> MQA (H=8, G=1):  Q: [h0 h1 h2 h3 h4 h5 h6 h7]
>                  K: [          g0              ]  // 8个Q共享1个KV head
> ```
>
> **项目关联**: Qwen2-1.5B 用 GQA (H=12, G=2); LLaMA3.2-1B 用 GQA (H=32, G=8)。代码中 `n_kv_heads` 控制 K/V 的 head 数。

### Q: BPE Tokenizer 是怎么工作的？

> **BPE** (Byte Pair Encoding) = 从字符级开始，反复合并最高频的字符对。
>
> **训练过程** (离线):
> 1. 初始词汇表 = 所有单字符 (256 bytes)
> 2. 统计所有相邻 token 对的出现次数
> 3. 合并出现最多的对 → 作为新 token 加入词汇表
> 4. 重复 2-3 直到词汇表大小达到预设 (如 151936 for Qwen2)
>
> **编码过程** (在线):
> ```
> "lowest" → ['l','o','w','e','s','t']
>          → ['lo','w','e','s','t']   (合并 l+o)
>          → ['low','e','s','t']      (合并 lo+w)
>          → ['low','est']            (合并 e+st)
>          → ['lowest']               (合并 low+est)
> ```
>
> **为什么用 BPE**:
> - 词汇表大小可控 (vs word-level 可能几十万)
> - 支持未登录词 (拆成 byte-level 子词)
> - 常见词一个 token，罕见词拆成多个 subword
>
> **项目关联**: tokenizer.json 存储 BPE 合并规则 + 词汇表。推理时先用 Tokenizer 把文本 → token IDs → 送入 Embedding 层。

### Q: Prefill 和 Decode 为什么要分离？

> **Prefill**: 处理完整 prompt, seq_len 可能几百~几千 → **Compute-Bound** (大矩阵乘)
> **Decode**: 每次只生成 1 token, seq_len=1 → **Memory-Bound** (GEMV)
>
> **分离的原因**: 两个阶段适合**不同的 kernel 配置和优化策略**:
>
> | | Prefill | Decode |
> |---|---------|--------|
> | 瓶颈 | Compute | Memory Bandwidth |
> | 矩阵形状 | [B, S, H] × [H, H] (GEMM) | [B, 1, H] × [H, H] (GEMV) |
> | 优化方向 | Tensor Core, Tile 大 | 向量化加载, Batch 合并 |
> | FlashAttention | seq_len 长, O(N²) 计算 | seq_len=1, 退化为向量点积 |
>
> **vLLM 做法**: Prefill 和 Decode 可能交替执行 (同一 batch 中有些请求在 Prefill, 有些在 Decode → chunked prefill)。
>
> **项目中**: LLAISYS 目前不分离 — Prefill 和 Decode 共用同一个 SelfAttention kernel，通过 `past_len` 区分。

### Q: AllReduce 是什么？Tensor Parallelism 为什么需要它？

> **AllReduce**: 分布式通信原语。每张卡有一个 tensor，执行后**所有卡**都得到所有 tensor 的**求和结果**。
>
> ```
> 执行前:  GPU0=[1,2]  GPU1=[3,4]  GPU2=[5,6]
> AllReduce(sum):
> 执行后:  GPU0=[9,12] GPU1=[9,12] GPU2=[9,12]  // 每张卡都有完整的和
> ```
>
> **TP (Tensor Parallelism) 中的使用**:
> ```
> Linear: Y = X × W,  W 按列拆分到 2 张卡
> GPU0: Y0 = X × W0  (W0 是 W 的左半)
> GPU1: Y1 = X × W1  (W1 是 W 的右半)
> → Y = [Y0, Y1] 拼接? 不行 — 后面的 Linear 需要完整输入
> → 实际: 行拆分后的第二个 Linear 直接 AllReduce 求和
> ```
>
> **通信库**: NVIDIA NCCL (最常用)，使用 NVLink/PCIe 在 GPU 间传输。
> **开销**: AllReduce 的通信量 = 2 × (n-1)/n × tensor_size (Ring AllReduce)。GPU 越多，通信开销越大 → 通信与计算的 overlap 很重要。

### Q: 数据并行 vs 模型并行 vs 流水线并行？

> | 并行方式 | 怎么拆 | 通信 | 适用场景 |
> |----------|--------|------|---------|
> | **数据并行 (DP)** | 每张卡完整模型副本，数据拆到不同卡 | AllReduce 梯度 (训练) | 模型放得下单卡 |
> | **张量并行 (TP)** | **一层内**的权重拆到多卡 | AllReduce 中间结果 (每层 2 次) | 模型太大单卡放不下 |
> | **流水线并行 (PP)** | **不同层**放不同卡 | 层间传递 activation | 层数多 + 通信慢 |
>
> **训练 vs 推理**:
> - 训练: 通常 DP + TP + PP 混合 (Megatron-LM 的 3D 并行)
> - 推理: 主要用 TP (同机多卡，NVLink 带宽高)。DP 用于多请求负载均衡。PP 少用 (延迟高)。
>
> **面试追问**: 什么是 Sequence Parallelism (SP)? → TP 中 LayerNorm/Dropout 不涉及权重拆分的部分，按 sequence 维度拆分，减少 activation 显存。

### Q: AWQ 和 GPTQ 有什么区别？

> 两者都是 Post-Training Quantization (训练后量化)，但策略不同:
>
> | | GPTQ | AWQ |
> |---|------|-----|
> | 核心思想 | 逐列量化 + OBS (Optimal Brain Surgeon) 补偿量化误差 | 保护重要权重 (activation-aware)，对重要权重乘以大 scale 后量化 |
> | 需要校准数据 | ✅ 计算 Hessian | ✅ 统计激活分布 |
> | 速度 | 较慢 (逐层 Hessian 求逆) | 较快 |
> | 精度 | 高 (逐列误差补偿) | 高 (保护重要通道) |
> | 生态 | AutoGPTQ + vLLM/TGI | AutoAWQ + vLLM |
>
> **AWQ 核心观察**: 只有 ~1% 的权重通道对模型输出影响很大 (因为对应的输入激活值很大)。量化时给这些通道一个更大的 scale → 量化误差更小。
>
> **项目关联**: 你的 INT8/INT4 量化用的是简单的 per-channel absmax 量化。GPTQ/AWQ 是更高级的方法，精度更高。

### Q: 什么是 KV Cache 的显存占用估算？

> 公式: `KV_Cache_bytes = 2 × B × L × S × H × dtype_size`
> - 2: K 和 V 各一份
> - B: batch size
> - L: 层数
> - S: 序列长度
> - H: hidden_size / n_heads × n_kv_heads (GQA 下)
> - dtype_size: FP16=2B, INT8=1B
>
> **Qwen2-1.5B 估算 (B=1, S=2048)**:
> ```
> n_layers=28, hidden=1536, n_kv_heads=2, head_dim=128
> KV per layer = 2 × 1 × 2048 × (2 × 128) × 2B = 2 MB
> Total = 28 × 2 MB = 56 MB
> ```
> → 1 个请求 56MB，10 个请求 560MB，100 个请求 5.6 GB → KV Cache 是 Decode 显存的大头。
>
> **面试追问**: 怎么减少 KV Cache 显存？→ GQA (减少 KV heads)、量化 KV Cache (INT8)、PagedAttention (减少碎片)、MLA (压缩 KV)。

### Q: 什么是 Continuous Batching 的 Scheduler 怎么工作？

> **传统 Static Batching**: 一组请求组成 batch，最长请求结束后整个 batch 才结束 → 短请求等长请求 → GPU 利用率低。
>
> **Continuous Batching (Iteration-Level Scheduling)**:
> ```
> Step 1: [A(decode), B(decode), C(prefill)]  // A 生成了 EOS → 退出
> Step 2: [D(prefill), B(decode), C(decode)]   // D 插入空位
> Step 3: [D(decode),  B(decode), C(decode)]   // B 到达 max_tokens → 退出
> Step 4: [D(decode),  E(prefill), C(decode)]  // E 接替
> ```
>
> **Scheduler 每步决策**:
> 1. 检查哪些请求已完成 (EOS / max_tokens) → 移出 batch
> 2. 空出的位置 → 从 waiting queue 中取新请求做 prefill
> 3. 估算 KV Cache 显存够不够放新请求
> 4. 组好新 batch → 执行一步推理
>
> **vLLM 的 Scheduler 还支持 Preemption**: 显存不够时把低优先级请求的 KV Cache swap 到 CPU → 腾出空间给高优先级请求。
