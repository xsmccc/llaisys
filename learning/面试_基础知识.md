## 1. 类型系统与浮点数底层

### 自定义半精度类型
```cpp
struct fp16_t { uint16_t _v; };  // 16 bit 存储，不重载运算符
struct bf16_t { uint16_t _v; };  // 16 bit 存储
```
设计原因: 这些类型只用于**存储和传输**。所有计算在 GPU 上用 CUDA 原生类型 `__half` / `__nv_bfloat16` 完成，避免 CPU 端不必要的运算符重载。

### do-while(0) 宏保护
```cpp
#define EXCEPTION_UNSUPPORTED_DATATYPE(dtype) \
    do { throw std::runtime_error("unsupported: " + std::to_string(dtype)); } while(0)
```
do-while(0) 包装多语句宏 → 保证在 if/else 中安全使用（不加则 else 可能与错误的 if 配对）。

### IEEE 754 浮点数底层结构
```
FP32:  [1 符号][8 指数][23 尾数]  = 32 bit
       value = (-1)^S × 2^(E-127) × (1 + M/2^23)
       精度: 23 × log10(2) ≈ 7.2 位十进制
       最大值: 2^127 × (2 - 2^-23) ≈ 3.4 × 10^38
       最小正数: 2^(-126) ≈ 1.18 × 10^-38

FP16:  [1 符号][5 指数][10 尾数]  = 16 bit
       value = (-1)^S × 2^(E-15) × (1 + M/2^10)
       精度: 10 × 0.301 ≈ 3.3 位十进制
       最大值: 2^15 × (2 - 2^-10) = 65504
       最小正数: 2^(-14) ≈ 6.1 × 10^-5

BF16:  [1 符号][8 指数][7 尾数]  = 16 bit
       精度: 7 × 0.301 ≈ 2.4 位十进制
       范围: 和 FP32 完全一样（8 位指数 → bias=127）
```

#### 为什么 AI 框架统一用 FP32 计算再转回？
```
FP16 下: exp(12) = 162755 → 超过 65504 → inf! 计算炸了
FP32 下: exp(12) = 162755 → 远小于 3.4×10^38 → 安全

所以所有涉及 exp/sin/cos 的运算必须上转 FP32:
  Load FP16 → to_float() → FP32 计算 → from_float() → Store FP16
```

#### 精度对比实例
```
数值 3.14159265...
FP32: 3.1415927  (前 7 位准)
FP16: 3.140625   (前 3 位准, 第4位错)
BF16: 3.125      (前 2 位准, 第3位错)
```

### dsize() 编译期分支
```cpp
template<typename T>
constexpr size_t dsize() {
    if constexpr (std::is_same_v<T, float>) return 4;
    if constexpr (std::is_same_v<T, fp16_t>) return 2;
    // if constexpr: C++17, 编译时决定分支，未选中的分支不编译
    // vs 普通 if: 运行时判断，所有分支都编译
}
```

## 2. Storage 与 RAII 资源管理

### RAII 原理
**Resource Acquisition Is Initialization** — 把资源生命周期绑定到对象生命周期。

### Storage 类设计
```cpp
class Storage {
    void* ptr_;
    size_t size_;
    std::shared_ptr<Allocator> allocator_;

    Storage(size_t size, std::shared_ptr<Allocator> alloc)
        : ptr_(alloc->allocate(size))    // 构造 = 获取资源
        , size_(size)
        , allocator_(alloc) {}

    ~Storage() { allocator_->free(ptr_); }  // 析构 = 释放资源

    friend class Tensor;  // 只有 Tensor 能创建 Storage
private:
    Storage(...);         // 外部无法直接 new Storage
};
```

#### 为什么 RAII 能防泄漏？
```cpp
void foo() {
    Storage s(1024, alloc);  // 构造：分配 1024B GPU 内存
    do_something();           // 如果这里抛异常...
                              // C++ 保证：栈展开时 s 的析构器仍会被调用!
}                             // 正常退出: s 析构，释放 GPU 内存
```
无论正常退出还是异常退出，析构器**总会被调用** → 不可能泄漏。

## 3. Allocator 与虚函数机制

### 抽象基类
```cpp
class MemoryAllocator {
    virtual void* allocate(size_t size) = 0;  // 纯虚函数
    virtual void free(void* ptr) = 0;
    virtual ~MemoryAllocator() = default;     // 虚析构必须有!
};
```

### NaiveAllocator
每次直接 `cudaMalloc`/`cudaFree`，每次 ~0.5-1ms 同步。推理一个 token 200 次分配 → 100ms 纯开销 → 不可接受。

### vtable / vptr 底层机制

#### 对象内存布局
```
NaiveAllocator 对象:
┌─────────┐  offset 0
│  vptr    │ ──→ NaiveAllocator::vtable
└─────────┘

CachingAllocator 对象:
┌─────────────┐  offset 0
│  vptr        │ ──→ CachingAllocator::vtable
├─────────────┤  offset 8
│  free_blocks │  (multimap)
├─────────────┤
│  mtx_        │  (mutex)
└─────────────┘

NaiveAllocator::vtable (编译器生成,只存在一份):
┌──────────────────────────┐
│ &NaiveAllocator::allocate │  slot 0
├──────────────────────────┤
│ &NaiveAllocator::free     │  slot 1
├──────────────────────────┤
│ &NaiveAllocator::~dtor    │  slot 2
└──────────────────────────┘

CachingAllocator::vtable:
┌────────────────────────────┐
│ &CachingAllocator::allocate │  slot 0 (覆盖)
├────────────────────────────┤
│ &CachingAllocator::free     │  slot 1 (覆盖)
├────────────────────────────┤
│ &CachingAllocator::~dtor    │  slot 2 (覆盖)
└────────────────────────────┘
```

#### 虚函数调用的汇编级过程
```cpp
MemoryAllocator* alloc = new CachingAllocator();
alloc->allocate(1024);

// 实际发生（等价伪代码）:
void** vtbl = *(void**)alloc;         // 1. 读 vptr (对象前8字节)
auto fn = (void*(*)(size_t))vtbl[0];  // 2. 查 vtable slot 0 (allocate)
fn(1024);                              // 3. 间接调用 CachingAllocator::allocate

// x86-64 汇编:
//   mov rax, [rdi]       ; rdi=this → 读 vptr
//   call [rax]           ; 间接调用 vtable[0]
//
// 开销: 2 次内存间接寻址 (~2-5ns) vs 直接调用 (~1ns)
```

#### 项目中避免虚函数的方式
```cpp
// 用 C 函数指针表：
struct LlaisysRuntimeAPI {
    void* (*malloc)(size_t);    // 直接存函数指针
};
api->malloc(1024);  // 1 次间接寻址 → 比 virtual 少 1 次
```

### CachingAllocator 完整工作流程

#### 分配流程
```
请求 1000 字节:
1. lock_guard(mtx_) 加锁
2. multimap 状态: {512→p1, 900→p2, 1200→p3, 2048→p4}
3. lower_bound(1000) → 找到 {1200, p3} (≥1000 的最小)
4. 检查 2× 容忍: 1200 ≤ 2×1000=2000? → Yes
5. 从 multimap 移除 {1200, p3}
6. 返回 p3 (浪费 200B, 但免去 cudaMalloc)

如果 lower_bound 找不到, 或找到的 > 2×size:
7. 调 cudaMalloc(1000) → 新分配 (~1ms!)
```

#### 释放流程
```
释放 p3 (size=1200):
1. lock_guard(mtx_) 加锁
2. 查 ptr→size 映射 → 1200
3. 总缓存量 + 1200 > 4GB?
   Yes → cudaFree(p3), 真正释放
   No  → multimap.insert({1200, p3}), 回收到池子
```

#### lower_bound vs upper_bound
- `lower_bound(x)`: ≥ x 的第一个 → Best-Fit 用这个
- `upper_bound(x)`: > x 的第一个

#### 为什么用 multimap 不用 map？
map 的 key 唯一 → 不允许两个大小相同的空闲块。但实际场景中很多 tensor 大小一样（如 Linear 权重），需要多个同 size 的池 → multimap。

## 4. Runtime 与多设备架构

### 函数指针表 vs C++ virtual
```
C++ virtual (不用):
  每次调用: 读 vptr → 查 vtable[slot] → 间接 call
  跨语言: ❌ (C ABI 不兼容 vtable)

C 函数指针表 (项目用):
  每次调用: 读函数指针 → 直接 call
  跨语言: ✅ (纯 C struct, 任何语言可调用)
  项目中 Python ctypes 直接调用 C 接口
```

### getRuntimeAPI 实现
```cpp
LlaisysRuntimeAPI const* getRuntimeAPI(Device dev) {
    static LlaisysRuntimeAPI const* apis[] = {
        get_nvidia_runtime_api(),   // 编译时链接 CUDA 实现
        get_metax_runtime_api(),    // 编译时链接沐曦实现
        get_tianshu_runtime_api(),
    };
    return apis[dev];  // O(1) 数组索引
}
// static 数组: 程序生命周期只初始化一次
// 每个 get_xxx() 返回指向 static 结构体的指针
```

### Rule of Five 底层
```cpp
class Runtime {
    // 管理 CUDA context/device 等不可共享的资源
    Runtime(const Runtime&) = delete;             // 禁止拷贝
    Runtime& operator=(const Runtime&) = delete;  // 禁止拷贝赋值
    Runtime(Runtime&&) = delete;                  // 禁止移动
    Runtime& operator=(Runtime&&) = delete;       // 禁止移动赋值
    ~Runtime();                                    // 析构释放设备
};
// 为什么全部 delete? CUDA Context 全局唯一，不能有第二份
```

## 5. Context 上下文 (Layer 4)

### thread_local
- 每个线程拥有独立的变量副本
- 用于 Context（设备上下文），每个推理线程绑定不同设备
- vs static: static 全局唯一, thread_local 每线程一份

### 懒初始化 (Lazy Initialization)
- Context 的 allocator 等资源不在构造时创建
- 首次使用时才 new → 避免不需要的开销
- `if (!allocator_) allocator_ = new CachingAllocator(...);`
- 创建 Runtime 要 cudaMalloc + cudaStreamCreate，开销大；延迟到首次 setDevice 时才创建

### 必须先 activate 再 delete
- activate: 设置 CUDA 设备 (`cudaSetDevice`)
- CUDA 函数必须在正确设备上调用
- 析构释放显存时也需要设备激活，否则释放到了错误设备的显存

## 6. Tensor 张量 (Layer 5)

### 三要素：Meta + Storage + Offset
- **Meta**: shape, strides, dtype（描述"怎么解读"内存）
- **Storage**: 实际数据（GPU/CPU 上的一块内存，shared_ptr 管理）
- **Offset**: 起始偏移（零拷贝 slice 需要）

### Stride 计算
```
shape = [2, 3, 4] 的 3D tensor:
stride[2] = 1          (最内层，相邻元素)
stride[1] = shape[2] × stride[2] = 4
stride[0] = shape[1] × stride[1] = 12
strides = [12, 4, 1]
```
一般规则：`stride[i] = stride[i+1] × shape[i+1]`

### 元素地址公式
```
addr(i,j,k) = base + offset + (i×stride[0] + j×stride[1] + k×stride[2]) × elem_size
```

### 零拷贝操作（不分配新内存！）
- **permute**: 只调换 stride 顺序，不移动数据
- **view/reshape**: 只修改 shape（要求 contiguous）
- **slice**: 修改 offset + shape

### contiguous 判定
```
stride[n-1] = 1
stride[i] = stride[i+1] × shape[i+1]  (i = n-2, ..., 0)
不满足 → 不连续 → view 会失败, 需要先 contiguous() 拷贝到连续内存
```

### to() 设备迁移
- CPU→GPU: `cudaMemcpy(HostToDevice)` + 新 Storage
- GPU→CPU: `cudaMemcpy(DeviceToHost)` + 新 Storage
- 必须先 contiguous()（cudaMemcpy 只能拷贝连续内存）

## 7. 智能指针与移动语义底层

### shared_ptr 控制块
```
shared_ptr<T> sp 内部:
┌─────────────┐
│ T* ptr_      │ → 指向管理的对象
├─────────────┤
│ ControlBlock*│ → 指向控制块
└─────────────┘

ControlBlock (堆上分配):
┌───────────────────┐
│ atomic<int> strong │ → 强引用计数 (=0 时销毁对象)
├───────────────────┤
│ atomic<int> weak   │ → 弱引用计数 (=0 时销毁控制块)
├───────────────────┤
│ Deleter            │ → 自定义删除器
└───────────────────┘

make_shared 优化: 对象和控制块一次 malloc 连续分配
  → 1 次 malloc vs new+shared_ptr 的 2 次 malloc

make_shared 的 weak_ptr 陷阱:
  对象和控制块在一块内存中 → 必须一起释放
  即使强引用=0 (对象已析构), 只要还有 weak_ptr 存活
  → 对象的内存也不会归还给 OS
  大对象 + 长寿命 weak_ptr → 内存浪费
  → 缓存友好（同一 cache line）
```

#### 引用计数示例
```cpp
auto a = make_shared<Storage>(1024, alloc);  // strong=1
auto b = a;                                   // strong=2 (atomic++)
auto c = a;                                   // strong=3
b.reset();                                    // strong=2 (atomic--)
// a, c 析构时 → strong=0 → ~Storage() → allocator_->free(ptr_)
```

### std::move 底层原理

#### move 本身做了什么？
```cpp
template<typename T>
T&& move(T& arg) {
    return static_cast<T&&>(arg);  // 就这一行! 只做类型转换!
}
```
**std::move 不移动任何东西！** 只是把左值引用 `T&` 转成右值引用 `T&&`。真正的"移动"发生在**移动构造函数**里。

#### 移动构造的实际过程
```cpp
class String {
    char* data_;
    size_t size_;

    // 拷贝构造 O(n): 分配新内存 + 逐字节复制
    String(const String& other)
        : data_(new char[other.size_])
        , size_(other.size_) {
        memcpy(data_, other.data_, size_);  // O(n) 复制!
    }

    // 移动构造 O(1): 偷走指针
    String(String&& other) noexcept
        : data_(other.data_)        // 偷走指针 (O(1)!)
        , size_(other.size_) {
        other.data_ = nullptr;      // 源对象置空
        other.size_ = 0;            // 被掏空了
    }
};

String a("hello world");
String b = std::move(a);  // 调用移动构造
// a.data_ = nullptr (被掏空)
// b.data_ = 指向 "hello world" (偷到了)
// 没有发生 memcpy!
```

#### 项目中的 move 使用
```cpp
// unique_ptr 只能 move 不能 copy
auto ctx = std::make_unique<Context>(device);
auto ctx2 = ctx;              // ❌ 编译错误! 拷贝 = delete
auto ctx2 = std::move(ctx);   // ✅ ctx 转移所有权给 ctx2, ctx 变 null
```

## 8. call_once 与单例模式

### call_once 底层实现原理
```cpp
cublasHandle_t get_cublas_handle() {
    static cublasHandle_t handle;
    static std::once_flag flag;
    std::call_once(flag, []() {
        cublasCreate(&handle);  // 只执行一次
    });
    return handle;
}
```

#### once_flag 内部
```
once_flag 本质是一个 atomic 状态:
  0: 未初始化
  1: 正在初始化 (某线程在执行)
  2: 已完成

call_once 执行流程:
  线程 A: CAS(flag, 0→1) 成功 → 执行 lambda → flag=2
  线程 B: CAS(flag, 0→1) 失败 → 自旋等待 → flag==2 后返回
  后续所有调用: 读 flag==2 → 直接返回 → ~1ns (atomic load)
```

### Meyers Singleton
```cpp
CublasHandle& get_handle() {
    static CublasHandle instance;  // C++11 保证线程安全初始化
    return instance;
}
// 编译器内部用类似 call_once 的机制保证只初始化一次
```

## 9. Template 特化与 if constexpr

### 模板全特化
```cpp
// 主模板 (fallback → 编译报错)
template<typename T> size_t dsize() { static_assert(sizeof(T)==0, "unsupported"); }

// 全特化
template<> size_t dsize<float>()    { return 4; }
template<> size_t dsize<fp16_t>()   { return 2; }
template<> size_t dsize<bf16_t>()   { return 2; }
```
编译器在编译时根据 T 的实际类型选择对应的特化版本。不匹配任何特化 → 主模板 → static_assert 报错。

### if constexpr (C++17)
```cpp
template<typename T>
size_t dsize() {
    if constexpr (std::is_same_v<T, float>)  return 4;
    if constexpr (std::is_same_v<T, fp16_t>) return 2;
    // 编译时决定走哪个分支, 其他分支完全不编译 → 零运行时开销
    // vs 普通 if: 运行时判断, 所有分支都编译(即使 T 不匹配)
}
```

## 10. C++ 面试八股文

> 本节合并了所有 C++ 方向的面试八股题，按主题分组。


### Q: 什么是 RAII？在你的项目中怎么用的？

> RAII（Resource Acquisition Is Initialization）——资源获取即初始化。核心思想是将资源的生命周期绑定到 C++ 栈对象的生命周期：构造函数获取资源，析构函数释放资源。由于 C++ 保证栈展开（无论正常退出还是异常抛出）时一定调用析构器，所以 RAII 能保证资源不泄漏。
>
> 项目中三处典型应用：
> 1. **Storage**：构造时通过 CachingAllocator 分配 GPU 显存，析构时调 `allocator_->free(ptr_)` 释放。即使推理过程中抛异常，显存也不会泄漏。
> 2. **lock_guard**：CachingAllocator 每个公有方法入口用 `std::lock_guard<std::mutex>` 加锁，函数结束自动解锁。
> 3. **shared_ptr**：多个 Tensor 共享同一个 Storage，引用计数归零时自动调 Storage 析构器释放 GPU 内存。

### Q: 虚函数的底层实现原理是什么？虚函数调用的开销有多大？

> 编译器为每个含虚函数的类生成一张 **vtable**（虚函数表），是一个函数指针数组，存在全局只读数据段（.rodata），**每个类一份**。每个对象的内存起始处有一个隐藏的 **vptr**（8 字节，64 位系统），指向所属类的 vtable。
>
> 虚函数调用过程（等价汇编 `mov rax, [rdi]; call [rax+offset]`）：
> 1. 从对象前 8 字节读出 vptr
> 2. 从 vtable 中按 slot 编号取出函数指针
> 3. 通过该指针间接调用
>
> **开销**：两次间接内存访问，约 2-5ns；更重要的是编译器**无法内联**虚函数调用，在热路径上影响显著。
>
> **项目实践**：设备 API 层（LlaisysRuntimeAPI）用 **C 函数指针表**替代 virtual——只需一次间接寻址，且 C 结构体是 C ABI，Python ctypes 可以直接调用。Allocator 层保留 virtual，因为不在推理热路径上。

### Q: vtable 每个对象一份还是每个类一份？vptr 呢？

> vtable 是**每个类一份**，存在全局只读数据段，编译期生成。同一类的所有对象共享同一张 vtable。vptr 是**每个对象一份**，占 8 字节（64 位系统），在构造函数中由编译器隐式设置。

### Q: 为什么基类析构函数要加 virtual？不加会怎样？

> 通过基类指针 `delete` 子类对象时，不加 `virtual` 只调基类析构，子类析构不执行 → 子类持有的资源泄漏。这是**未定义行为**。加了 `virtual` 后，`delete` 时通过 vtable 找到子类析构函数正确释放。
>
> 项目中 `MemoryAllocator` 基类用 `virtual ~MemoryAllocator() = default;`，确保 `shared_ptr<MemoryAllocator>` 释放 CachingAllocator 时正确调用子类析构。

### Q: override 关键字的作用？

> 告诉编译器"我在覆盖基类的虚函数"。如果签名不匹配（参数类型/返回类型写错），编译直接报错。不加 override 签名写错会变成一个独立的新函数，不会覆盖基类虚函数也不报错，导致 bug 难以发现。

### Q: std::move 到底做了什么？移动构造和拷贝构造的区别？

> `std::move` 本身**不移动任何东西**，它只是 `static_cast<T&&>`，将左值转为右值引用，使编译器选择**移动构造/赋值**的重载。
>
> **拷贝构造**：`String(const String&)` — 申请新内存 + memcpy，O(n)。
> **移动构造**：`String(String&&) noexcept` — 偷走 `other.data_` 指针，O(1)，源对象置空。
>
> 移动后源对象处于 **valid but unspecified state**——可以析构和赋值，但值不确定。
>
> 项目中 `unique_ptr<Context>` 只能 move 不能 copy，因为 CUDA Context 是独占资源。

### Q: Rule of Five 是什么？你的项目哪里用到了？

> C++11 的 5 个特殊成员函数：拷贝构造、拷贝赋值、移动构造、移动赋值、析构。如果自定义了其中一个，就必须考虑全部五个——要么全部 `= delete`（禁止），要么全部自定义。否则默认浅拷贝会导致 **double free**。
>
> 项目中 **Runtime** 和 **Context** 管理 CUDA Context/Stream，全部 `= delete`。**Storage** 通过 shared_ptr 管理，拷贝实际是引用计数 +1。

### Q: shared_ptr 引用计数怎么实现线程安全的？make_shared 有什么优化？

> 引用计数存在堆上的**控制块**中，使用 `std::atomic<int>`。拷贝时 `fetch_add(1)`，析构时 `fetch_sub(1)`，x86 上用 `lock xadd` 指令（~10ns/次）。引用计数归零时调析构函数。
>
> **make_shared**：一次 malloc 连续分配对象和控制块（vs `new T + shared_ptr` 的 2 次 malloc）→ 省一次分配、缓存更友好。
>
> **注意**：引用计数本身线程安全，但多线程同时读写**同一个 shared_ptr 变量**不安全。


### Q: fetch_sub 返回旧值是什么意思？析构时为什么判断 == 1？（面试追问）

> `std::atomic<int>::fetch_sub(1)` **原子地**执行减 1，但返回的是**操作前的旧值**。
>
> ```cpp
> // shared_ptr 析构时：
> if (control_block->strong_count.fetch_sub(1) == 1) {
>     // 旧值是 1 → 说明减之前只剩 1 个 → 减完后变 0 → 我是最后一个
>     delete managed_object;
> }
> ```
>
> **为什么判旧值 == 1 而不是新值 == 0？**
> 因为 `fetch_sub` 返回旧值（C++ 标准定义）。判 `== 1` 等价于"减完后 == 0"。
>
> **为什么不先 load 再判断？**
> 因为 load + sub 不是单条原子操作，中间可能被其他线程打断。`fetch_sub` 是单条原子指令（x86 上编译为 `lock xadd`），读+减+返回旧值一步完成。


### Q: thread_local 和 static 有什么区别？为什么不用全局 static Context？

> `static` 全局唯一；`thread_local` 每线程独立副本。项目 Context 管理 CUDA 设备绑定，如果 static 共享，多线程 setDevice 竞争修改 → **数据竞争（UB）**。thread_local 每线程独立，天然安全无需锁。

### Q: call_once 的实现原理？和 static 局部变量有什么关系？

> once_flag 内部 atomic 状态(0→1→2)。首次 CAS(0→1) 成功→执行→flag=2。后续 atomic load 读到 2 直接返回(~1ns)。C++11 static 局部变量初始化也线程安全（编译器内部用类似机制），但 call_once 更灵活——可以在 lambda 中做复杂初始化。

### Q: 拷贝构造函数为什么参数是 const T&？

> 如果 `T(T other)` 按值传参→传参时需要拷贝→调拷贝构造→**无限递归**。用引用 `T&` 能工作但不能接受 const 对象。`const T&` 是标准签名：不拷贝参数、不修改原对象、能接受 const 和非 const。

### Q: map vs multimap vs unordered_map 区别？

> | | map | multimap | unordered_map |
> |---|---|---|---|
> | 底层 | 红黑树 | 红黑树 | 哈希表 |
> | 有序 | 是 | 是 | 否 |
> | 重复 key | 否 | 是 | 否 |
> | 查找 | O(log n) | O(log n) | O(1) 平均 |
> | lower_bound | 有 | 有 | 无 |
>
> 项目 CachingAllocator 用 multimap：需要有序(lower_bound 做 Best-Fit)且允许同 size 多个空闲块。

### Q: if constexpr 和普通 if 有什么区别？

> `if constexpr`（C++17）在**编译时**决定分支，未选中的分支**完全不编译**——即使其中有语法错误也不会报错。普通 if 是运行时判断，所有分支都编译。项目 dsize<T>() 用 if constexpr 根据类型返回不同字节数，零运行时开销。

### Q: 什么是 ULL 后缀？为什么 `4 * 1024 * 1024 * 1024` 会溢出？

> ULL = unsigned long long（64 位无符号整数）。不加后缀时字面量默认是 int（32 位，最大约 2^31-1 ≈ 21 亿）。`4 × 1024³ = 2³² = 4294967296` 超出 int 范围，整数溢出变为 0（未定义行为）。加 `4ULL` 后所有计算在 64 位下进行。
>
> 项目中 CachingAllocator 的 `MAX_CACHE_BYTES = 4ULL * 1024 * 1024 * 1024;` 就必须加 ULL。

### Q: const 和 constexpr 有什么区别？

> `const`：运行时常量，初始化后不可修改，可以用变量初始化。
> `constexpr`：编译时常量，必须在编译期就能确定值。`constexpr` 函数在编译期就能求值 → 零运行时开销。
>
> 项目中 `constexpr size_t dsize<float>() { return 4; }` — 编译时直接替换为 4。

### Q: volatile 关键字的作用？CUDA 中用吗？

> `volatile` 告诉编译器: 每次访问都必须从内存读，不能用寄存器缓存值。因为值可能被外部因素（硬件/另一线程）修改。
>
> CUDA 中极少用——GPU 的内存一致性通过 `__syncthreads()`、`atomicXxx()`、`__threadfence()` 来保证。但在某些旧写法的归约中会看到 `volatile` 用于 Warp 级归约（现代用 `__shfl_down_sync` 替代）。

### Q: delete 和 free 的区别？

> `delete` = 调析构函数 + 释放内存（C++）。`free` = 只释放内存（C）。
> `new/delete` 配对，`malloc/free` 配对，混用是**未定义行为**。
>
> GPU 上: `cudaMalloc/cudaFree`（C API，不涉及构造/析构）。项目 CachingAllocator 封装了 cudaMalloc/cudaFree。

### Q: 什么是内存对齐？为什么重要？

> CPU/GPU 要求数据地址是类型大小的整数倍。float(4B) 起始地址必须是 4 的倍数。未对齐访问可能导致性能下降甚至硬件异常。
>
> GPU 特别敏感: float4(16B) 必须 16B 对齐才能用 LD.128 指令。项目的 float4 向量化隐含假设 tensor 数据是 16B 对齐的（cudaMalloc 保证至少 256B 对齐）。

### Q: 智能指针的循环引用怎么解决？

> 两个 shared_ptr 互相指向 → 引用计数永远不到 0 → 内存泄漏。解决: 其中一方改用 `weak_ptr`。weak_ptr 不增加 strong count，不影响对象销毁。
>
> 项目中不存在循环引用问题——Storage←Tensor 是单向引用。

### Q: 什么是 SFINAE？

> Substitution Failure Is Not An Error。模板实参替换失败时，编译器不报错，只是从候选集中排除该模板。用于编译期根据类型特征选择不同实现。
>
> 项目中 `if constexpr` 达到类似效果，是更现代的写法。



### Q: vector 底层实现？扩容机制是什么？

> vector 内部 3 个指针: `start`(数据起始)、`finish`(已用末尾)、`end_of_storage`(空间末尾)。
> `size() = finish - start`，`capacity() = end_of_storage - start`。
>
> **扩容流程**（push_back 且 size == capacity 时）:
> 1. 分配 2× 旧容量的新内存（GCC 一般 2 倍，MSVC 1.5 倍）
> 2. 将旧元素**移动**（C++11 后有 noexcept 移动构造则 move，否则 copy）到新内存
> 3. 销毁旧元素，释放旧内存
> 4. 更新三个指针
>
> **面试追问**:
> - 为什么 2 倍？均摊 O(1)。n 次 push_back 总共拷贝 n + n/2 + n/4 + ... ≈ 2n = O(n)，每次均摊 O(1)。
> - 1.5 倍 vs 2 倍？1.5 倍可以复用之前释放的内存（1+1.5+2.25>4, 前几次的内存拼起来能放下新的），2 倍永远不能复用。
> - `reserve(n)` 预分配，避免多次扩容。`shrink_to_fit()` 释放多余容量。


### Q: vector 扩容的均摊 O(1) 怎么算？（面试追问补充）

> 假设初始 capacity=1，连续 push_back 16 次：
> ```
> push #1:  cap 1→2,  拷贝 1 个旧元素
> push #2:  不扩容
> push #3:  cap 2→4,  拷贝 2 个旧元素
> push #5:  cap 4→8,  拷贝 4 个旧元素
> push #9:  cap 8→16, 拷贝 8 个旧元素
> push #10-16: 不扩容
>
> 总拷贝 = 1+2+4+8 = 15 ≈ n-1 = O(n)
> 总 push = 16 = n
> 均摊 = O(n)/n = O(1)
> ```
>
> **1.5 倍为什么能复用旧内存？**
> 连续扩容: 1 → 1.5 → 2.25 → 3.375 → 5.06，前几次释放的内存 = 1+1.5+2.25 = 4.75 > 当前需要的 3.375 → 旧块拼起来可以放下新块。2 倍做不到: 1+2+4=7 < 8 → 永远不能复用。

### Q: 面试级简化版 vector 实现（手写代码）

> ```cpp
> template<typename T>
> class MyVector {
>     T* data_ = nullptr;
>     size_t size_ = 0, cap_ = 0;
> public:
>     MyVector() = default;
>     ~MyVector() {
>         for (size_t i = 0; i < size_; i++) data_[i].~T();
>         ::operator delete(data_);
>     }
>     void push_back(const T& val) {
>         if (size_ == cap_) {
>             size_t new_cap = cap_ == 0 ? 1 : cap_ * 2;
>             T* new_data = static_cast<T*>(::operator new(new_cap * sizeof(T)));
>             for (size_t i = 0; i < size_; i++) {
>                 new (new_data + i) T(std::move(data_[i]));  // placement new + move
>                 data_[i].~T();
>             }
>             ::operator delete(data_);
>             data_ = new_data;
>             cap_ = new_cap;
>         }
>         new (data_ + size_) T(val);  // placement new
>         ++size_;
>     }
>     size_t size() const { return size_; }
>     T& operator[](size_t i) { return data_[i]; }
> };
> ```
>
> **要点**: `::operator new/delete` 只分配/释放裸内存。`placement new` 在指定地址构造对象。`std::move` 触发移动构造避免深拷贝。


### Q: map 和 unordered_map 的区别？底层分别是什么？

> | | map | unordered_map |
> |---|-----|---------------|
> | 底层 | 红黑树 (self-balancing BST) | 哈希表 (拉链法) |
> | 有序 | ✅ key 有序遍历 | ❌ 无序 |
> | 查找 | O(log n) | 平均 O(1)，最差 O(n) |
> | 插入 | O(log n) | 平均 O(1) |
> | 内存 | 每节点 3 指针 + color | 桶数组 + 链表节点 |
> | 适用 | 需要有序遍历 / 范围查询 | 只需要 key-value 快速查找 |
>
> **面试追问**: 项目中 CachingAllocator 用的 `multimap`（红黑树），因为需要 `lower_bound` 找 ≥ 请求 size 的最小空闲块 — 哈希表做不了范围查询。

### Q: 左值和右值是什么？右值引用有什么用？

> **左值 (lvalue)**: 有名字、有地址、可取地址。`int x = 42;` 中 x 是左值。
> **右值 (rvalue)**: 无名字的临时值。`42`、`x + 1`、`std::move(x)` 是右值。
>
> **右值引用 `T&&`**：绑定到右值，允许"偷走"临时对象的资源而不是拷贝。
> ```cpp
> std::vector<int> make() { return {1,2,3}; }
> std::vector<int> v = make();   // make() 返回右值 → 触发**移动构造**
>                                 // 不拷贝数据，直接偷走 make() 的内部指针
> ```
>
> 配合 `std::move`（把左值强转为右值引用）:
> ```cpp
> std::vector<int> a = {1,2,3};
> std::vector<int> b = std::move(a);  // a 的数据被偷走，a 变为空
> ```
>
> **本质**: 右值引用是 C++11 的核心机制，让资源可以"转移"而不是"复制"，避免不必要的内存分配。

### Q: 什么是完美转发？std::forward 做了什么？

> **问题**: 写一个转发函数时，实参的左/右值属性会丢失。
> ```cpp
> template<typename T>
> void wrapper(T&& arg) {        // 万能引用 (Universal Reference)
>     target(std::forward<T>(arg)); // 完美转发: 保留 arg 的左/右值属性
> }
> ```
>
> **引用折叠规则**:
> - `T& &&` → `T&`（左值传入 → T=int& → arg 类型 int& && → int&）
> - `T&& &&` → `T&&`（右值传入 → T=int → arg 类型 int&& → int&&）
>
> `std::forward<T>(arg)` = 根据 T 的类型，决定 static_cast 为左值引用还是右值引用。
>
> **用途**: 工厂函数、emplace 系列、make_shared/make_unique 内部都用完美转发。


### Q: std::move 和 std::forward 的区别？（面试常见对比题）

> | | `std::move` | `std::forward<T>` |
> |---|---|---|
> | 做什么 | **无条件**转为右值引用 | **有条件**保留原始左/右值属性 |
> | 本质 | `static_cast<T&&>(x)` | 根据 T 类型决定 cast 为 `T&` 或 `T&&` |
> | 使用场景 | 我明确知道这个对象不再需要，要交出资源 | 模板转发函数中，原样传递实参给下游 |
> | 典型代码 | `auto b = std::move(a);` | `target(std::forward<T>(arg));` |
>
> ```cpp
> void target(int& x)  { /* lvalue版 */ }
> void target(int&& x) { /* rvalue版 */ }
>
> template<typename T>
> void wrapper(T&& arg) {         // 万能引用
>     target(std::forward<T>(arg)); // 保留 arg 原本的左/右值属性
>     // 如果写 std::move(arg) → 左值也会被错误地转成右值
> }
>
> int a = 10;
> wrapper(a);    // T=int&, forward 保留左值 → 调 target(int&)
> wrapper(42);   // T=int,  forward 保留右值 → 调 target(int&&)
> ```
>
> **一句话区分**: move 是"我主动放弃"，forward 是"我替别人转发，保留原样"。


### Q: Lambda 表达式的捕获列表怎么工作？

> Lambda 本质是**编译器生成的匿名类**，重载了 `operator()`。
>
> ```cpp
> int x = 10;
> auto f = [x](int y) { return x + y; };  // 值捕获
> // 编译器生成:
> // struct __lambda_1 {
> //     int x;                           // 成员变量
> //     __lambda_1(int x) : x(x) {}     // 构造函数
> //     int operator()(int y) const { return x + y; }
> // };
> ```
>
> | 捕获方式 | 语法 | 意义 |
> |----------|------|------|
> | 值捕获 | `[x]` | **拷贝**一份 x，Lambda 内修改不影响外部 |
> | 引用捕获 | `[&x]` | 引用外部 x，Lambda 内修改**直接影响**外部 |
> | 全值捕获 | `[=]` | 所有用到的变量都值捕获 |
> | 全引用捕获 | `[&]` | 所有用到的变量都引用捕获 |
> | 混合 | `[=, &x]` | 默认值捕获，x 引用捕获 |
>
> **陷阱**: 引用捕获如果 Lambda 的生命周期超过被捕获变量 → 悬垂引用 → UB。

### Q: C++ 的 4 种类型转换分别是什么？什么场景用哪个？

> | 转换 | 用途 | 编译/运行时 |
> |------|------|-----------|
> | `static_cast<T>` | 基本类型转换、向下转型（无检查）、void* 转有类型指针 | 编译时 |
> | `dynamic_cast<T>` | 多态向下转型（有 RTTI 检查），失败返回 nullptr | **运行时** |
> | `const_cast<T>` | 去掉 const（唯一合法方式） | 编译时 |
> | `reinterpret_cast<T>` | 指针/整数间强制、完全不做检查 | 编译时 |
>
> **std::move 就是 `static_cast<T&&>`**！不是 reinterpret_cast。
>
> **面试追问**: 为什么不用 C 风格 `(int)x`？→ C 风格等于依次尝试 static→const→reinterpret，不安全且难以 grep。

### Q: static 关键字在 C++ 中有几种用法？

> **4 种**:
>
> | 用法 | 含义 |
> |------|------|
> | 全局 static 变量/函数 | 限制链接性 → 只在本编译单元可见 (internal linkage) |
> | 局部 static 变量 | 函数内生命周期延长到程序结束，只初始化一次（C++11 保证线程安全） |
> | 类 static 成员变量 | 所有对象共享一份，不属于任何实例，类外定义 |
> | 类 static 成员函数 | 没有 this 指针，只能访问 static 成员 |
>
> **项目关联**:
> - `static LlaisysRuntimeAPI const* apis[]`（§4）→ 局部 static，程序生命周期只初始化一次
> - `call_once` 配合 static flag → 线程安全的单次初始化

### Q: 深拷贝和浅拷贝的区别？什么时候需要手写拷贝构造？

> **浅拷贝**: 逐成员复制（编译器默认行为）。如果成员含指针 → 两个对象指向同一块内存 → double free。
> **深拷贝**: 手动分配新内存，复制指针指向的内容。
>
> ```cpp
> class Buffer {
>     int* data_;
>     size_t size_;
> public:
>     // 浅拷贝（默认）: data_ 被复制 → 两个 Buffer 指向同一内存
>     // 深拷贝（手写）:
>     Buffer(const Buffer& other) : size_(other.size_) {
>         data_ = new int[size_];
>         memcpy(data_, other.data_, size_ * sizeof(int));
>     }
> };
> ```
>
> **何时需要手写**: 类持有原始指针管理资源时。用 `shared_ptr`/`unique_ptr` 就不需要（Rule of Zero）。
> **项目中**: Tensor 不需要深拷贝 — Storage 用 shared_ptr 管理，拷贝 Tensor 只增加引用计数。

### Q: 构造函数为什么要用初始化列表？不用会怎样？

> ```cpp
> class A {
>     std::string name_;
>     const int id_;
>     B& ref_;
> public:
>     // ✅ 初始化列表（推荐）
>     A(std::string n, int id, B& r) : name_(std::move(n)), id_(id), ref_(r) {}
>     // ❌ 赋值方式
>     A(std::string n, int id, B& r) { name_ = n; id_ = id; /* ref_ 没法赋值 */ }
> };
> ```
>
> **3 个必须用初始化列表的场景**: const 成员、引用成员、没有默认构造函数的成员。
>
> **效率差异**: 赋值方式 = 先默认构造 + 再赋值（2 步）；初始化列表 = 直接构造（1 步）。对 string/vector 这种有拷贝开销的类型差异明显。


### Q: 为什么引用成员必须用初始化列表？引用的"绑定"和"赋值"有什么区别？（面试追问）

> **引用 = 别名**。声明时必须告诉它"你是谁的别名"，之后永远不能改指向。
>
> ```cpp
> int a = 10;
> int& ref = a;   // ✅ 声明时绑定到 a
> int& ref2;      // ❌ 编译错误！没有绑定目标
>
> int b = 20;
> ref = b;         // ✅ 但这是赋值（把 b 的值赋给 a），不是改绑定！
>                   // ref 仍然是 a 的别名，a 变成了 20
> ```
>
> **函数参数的引用**：调用时自动绑定。`void func(int& c)` 调用 `func(x)` 等价于 `int& c = x;`。
>
> **类成员引用**：
> ```cpp
> class A {
>     int& ref_;
> public:
>     A(int& r) : ref_(r) {}   // ✅ 初始化列表 = 出生时绑定
>     // A(int& r) { ref_ = r; }  ❌ 进入 {} 时 ref_ 还没绑定 → 编译失败
> };
> ```
>
> **三个必须用初始化列表的场景**：const 成员（不能赋值）、引用成员（不能重绑）、无默认构造的成员（没法出生）。本质都是"进入构造函数体 {} 之前，成员已经要被构造，但这三类成员在构造时必须有参数"。


### Q: emplace_back 和 push_back 有什么区别？

> `push_back(T val)`: 先构造临时对象，再**拷贝/移动**到容器尾部。
> `emplace_back(Args&&... args)`: 把构造参数**完美转发**到容器尾部，**原地构造**，省一次拷贝/移动。
>
> ```cpp
> std::vector<std::pair<int, std::string>> v;
> v.push_back({1, "hello"});           // 构造临时 pair → 移动到 vector
> v.emplace_back(1, "hello");          // 直接在 vector 的内存上构造 pair
> ```
>
> **注意**: 对基本类型 (int/float) 几乎没区别。对含移动构造的类型差别也不大（push_back + move ≈ emplace_back）。主要收益在**没有移动构造**的重类型。

### Q: C++ 多线程怎么做同步？mutex/lock_guard/unique_lock/condition_variable 区别？

> | 工具 | 用途 |
> |------|------|
> | `std::mutex` | 最基础的互斥锁，lock()/unlock() |
> | `std::lock_guard<mutex>` | RAII 封装 mutex，构造加锁、析构解锁，**不能手动解锁** |
> | `std::unique_lock<mutex>` | RAII 封装 mutex，**可以手动解锁/重新加锁**，配合 condition_variable |
> | `std::condition_variable` | 等待/通知机制，必须搭配 unique_lock |
> | `std::atomic<T>` | 无锁原子操作，shared_ptr 引用计数就是 atomic<int> |
>
> **典型生产者-消费者模式**:
> ```cpp
> std::mutex mtx;
> std::condition_variable cv;
> std::queue<int> q;
>
> // 生产者
> {
>     std::lock_guard<std::mutex> lk(mtx);
>     q.push(42);
> }
> cv.notify_one();
>
> // 消费者
> std::unique_lock<std::mutex> lk(mtx);
> cv.wait(lk, [&]{ return !q.empty(); });  // 等待直到队列非空
> int val = q.front(); q.pop();
> ```
>
> **项目关联**: CachingAllocator 用 `std::mutex + lock_guard` 保护 multimap（§3 分配/释放流程第一步 `lock_guard(mtx_) 加锁`）。

### Q: C++ 程序的内存布局是什么？堆和栈有什么区别？

> 从低地址到高地址:
> ```
> ┌──────────────┐ 低地址
> │ .text (代码段) │ 编译后的机器指令
> │ .rodata      │ const 全局变量、字符串字面量
> │ .data        │ 已初始化全局/static 变量
> │ .bss         │ 未初始化全局/static 变量 (自动清零)
> │              │
> │ Heap ↓       │ new/malloc 动态分配，向高地址增长
> │              │
> │ Stack ↑      │ 局部变量/函数参数，向低地址增长
> └──────────────┘ 高地址
> ```
>
> | | 栈 (Stack) | 堆 (Heap) |
> |---|-----------|-----------|
> | 分配 | 编译器自动 (移动 sp) | 手动 new/malloc |
> | 释放 | 自动 (函数返回) | 手动 delete/free |
> | 速度 | ~1 cycle | ~100+ cycles (系统调用) |
> | 大小 | 通常 1-8 MB | 可用全部内存 |
> | 碎片 | 无 | 有 |
>
> **面试追问**: GPU 上没有栈吗？→ GPU 每个线程有私有寄存器 + Local Memory（溢出到全局显存），没有传统栈概念。Kernel 参数放在 Constant Memory。

### Q: 迭代器失效规则？vector/map/unordered_map 分别是什么情况？

> | 容器 | 插入时失效 | 删除时失效 |
> |------|-----------|-----------|
> | **vector** | 扩容时**所有**迭代器失效；不扩容时插入点之后的失效 | 被删元素及其之后的失效 |
> | **deque** | 首尾插入不失效(不扩容时)；中间插入全部失效 | 类似 vector |
> | **list** | 不失效 | 只有被删元素的失效 |
> | **map/set** | 不失效 | 只有被删元素的失效 |
> | **unordered_map** | rehash 时全部失效 | 只有被删元素的失效 |
>
> **安全删除惯用法**:
> ```cpp
> // vector
> for (auto it = v.begin(); it != v.end(); ) {
>     if (*it == target) it = v.erase(it);  // erase 返回下一个有效迭代器
>     else ++it;
> }
> ```

### Q: 多继承下虚函数表是什么样的？

> 单继承: 对象只有 1 个 vptr。
> 多继承: 对象有**多个 vptr**，每个基类子对象一个。
>
> ```cpp
> class A { virtual void fa(); };
> class B { virtual void fb(); };
> class C : public A, public B { void fa() override; void fb() override; };
>
> // C 的内存布局:
> // ┌──────────┐ offset 0
> // │ vptr_A   │ → vtable_A (fa→C::fa)
> // │ A 的成员  │
> // ├──────────┤ offset N
> // │ vptr_B   │ → vtable_B (fb→C::fb)
> // │ B 的成员  │
> // └──────────┘
> //
> // A* pa = &c;  // 指向 offset 0，直接用 vptr_A
> // B* pb = &c;  // 指向 offset N，编译器自动调整指针 (thunk)
> ```
>
> **菱形继承**: A→B, A→C, B+C→D → A 被包含两份！用 `virtual` 继承解决（A 只保留一份，但有额外 vbptr 开销）。
> **面试建议**: 尽量避免多继承，用组合代替。

### Q: struct 和 class 在 C++ 中有什么区别？

> **唯一区别**: 默认访问权限。
> - `struct`: 默认 `public`
> - `class`: 默认 `private`
>
> 继承也是: `struct B : A {}` 默认 public 继承，`class B : A {}` 默认 private 继承。
> 其他（成员函数/虚函数/模板/继承）完全一样。

### Q: inline 关键字在现代 C++ 中是什么意义？

> **原始含义** (C++98): 建议编译器内联展开（现代编译器会自己决定，这个建议已无意义）。
> **现代含义** (C++17): **允许多个编译单元中有相同的定义**（ODR 合规）。
>
> 典型用途: 头文件中定义函数/变量而不重复定义错误。
> ```cpp
> // header.h
> inline int MAX_SIZE = 1024;          // C++17 inline 变量
> inline void helper() { /* ... */ }   // 可以在头文件中定义
> ```
>
> **constexpr 函数隐式 inline**。模板函数也隐式 inline。

## 11. C++ 引擎架构面试速查

### 40.1 智能指针

**unique_ptr**: 独占所有权，不可拷贝只能 move。底层：裸指针 + 析构时 delete。sizeof = 8B（和裸指针一样，零开销）。
```cpp
auto p = std::make_unique<Widget>();  // 推荐，异常安全
auto p2 = std::move(p);              // p 变 nullptr
```

**shared_ptr**: 共享所有权，引用计数（control block 里存 strong_count + weak_count）。
```cpp
auto s = std::make_shared<Widget>();  // 只分配一次内存（对象+控制块）
auto s2 = s;  // strong_count = 2
```
- sizeof = 16B（对象指针 + 控制块指针）
- 线程安全：引用计数的加减是 atomic 操作，但对象本身的访问不是线程安全的
- **make_shared 比 new 好**：一次内存分配 vs 两次（对象 + 控制块）

**weak_ptr**: 不增加 strong_count。用于：
1. 打破循环引用
2. 缓存（观察对象是否还活着）
```cpp
std::weak_ptr<Widget> w = s;
if (auto locked = w.lock()) { /* strong_count 临时 +1 */ }
```

**循环引用**:
```
A ──shared_ptr──→ B
B ──shared_ptr──→ A
→ strong_count 永远 ≥ 1 → 内存泄漏
解法: A→B 用 shared_ptr, B→A 用 weak_ptr
```

### 40.2 Move 语义与右值引用

**左值 vs 右值**:
- 左值(lvalue): 有名字有地址，表达式结束后还在。`int x = 1; // x 是左值`
- 右值(rvalue): 临时值，表达式结束后销毁。`42, foo(), std::move(x)`

**右值引用 (T&&)**: 绑定到右值，延长临时对象的生命周期。

**移动构造/移动赋值**:
```cpp
class Buffer {
    int* data; size_t size;
public:
    Buffer(Buffer&& other) noexcept    // 移动构造
        : data(other.data), size(other.size) {
        other.data = nullptr;           // 偷走资源
        other.size = 0;
    }
};
```
移动 = O(1) 指针交换，拷贝 = O(n) 深拷贝。

**std::move**: 不移动任何东西！只是 static_cast<T&&>()，告诉编译器"这个对象可以被偷"。

**完美转发**: std::forward<T>(arg)，保持参数的左/右值性质（在模板里用）。

### 40.3 虚函数与多态

**vtable 机制**:
```
每个含虚函数的类 → 一个 vtable（函数指针数组，编译时生成）
每个对象 → 前 8 字节是 vptr（指向 vtable）

调用 p->foo():
  1. 读 p 的 vptr (对象前 8 字节)
  2. 读 vtable[foo 的 index] (函数地址)
  3. call 该地址
  开销: 2 次间接 + 可能的 cache miss
```

**虚析构必须有**: `Base* p = new Derived(); delete p;` 如果 ~Base 不是虚函数，只调 ~Base 跳过 ~Derived → 资源泄漏。

**纯虚函数**: `virtual void foo() = 0;` → 抽象类，不能实例化。

**override 关键字**: C++11，编译器检查确实重写了基类虚函数（防止签名写错导致隐藏而非重写）。

**final**: 阻止进一步继承或重写。

### 40.4 模板基础

```cpp
// 函数模板
template <typename T>
T max(T a, T b) { return (a > b) ? a : b; }

// 类模板
template <typename T, int N>
class Array { T data[N]; };

// 模板特化
template <> class Array<bool, 8> { char data; };  // 特殊处理 bool
```

**编译期多态**: 模板在编译时实例化不同版本，没有 vtable 开销（静态分发 vs 动态分发）。

### 40.5 并发编程

**mutex + lock_guard**:
```cpp
std::mutex mtx;
void safe_push(std::vector<int>& v, int val) {
    std::lock_guard<std::mutex> lock(mtx);  // RAII，作用域结束自动解锁
    v.push_back(val);
}
```

**condition_variable（条件变量）**:
```cpp
std::condition_variable cv;
std::mutex mtx;
std::queue<int> q;

// 生产者
{
    std::lock_guard<std::mutex> lock(mtx);
    q.push(42);
    cv.notify_one();  // 唤醒一个等待线程
}

// 消费者
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [&]{ return !q.empty(); });  // 等直到队列非空
    int val = q.front(); q.pop();
}
```

**atomic**: 无锁原子操作
```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);  // 原子 +1
```

**memory_order**: relaxed(最弱) < acquire/release(配对用) < seq_cst(最强，默认)
面试只需说: "默认 seq_cst 保证全序一致性，relaxed 只保证原子性不保证顺序，acquire/release 用于生产者-消费者模式"

**死锁条件（4个）**: 互斥  + 不可剥夺 + 持有并等待 + 循环等待
**避免**: lock_guard (RAII) + std::scoped_lock(C++17, 一次锁多个 mutex,内部用 try-and-back-off)

### 40.6 STL 容器底层

| 容器 | 底层 | 查找 | 插入 | 特点 |
|------|------|------|------|------|
| vector | 动态数组 | O(1) | O(1)均摊 | 连续内存, cache friendly |
| deque | 分段数组 | O(1) | O(1)头尾 | 双端 |
| list | 双向链表 | O(n) | O(1) | 指针开销大 |
| map | 红黑树 | O(log n) | O(log n) | 有序, 范围查询 |
| unordered_map | 哈希表 | O(1)均摊 | O(1)均摊 | 无序, 哈希冲突→链表/开放寻址 |
| set/unordered_set | 同 map/unordered_map | 同上 | 同上 | 无 value |

**vector 扩容**: 容量不够 → 分配 2× 新内存 → 拷贝/移动旧元素 → 释放旧内存。
**reserve()**: 预分配容量，避免多次扩容。
**emplace_back() vs push_back()**: emplace 直接在容器内存中构造（省一次拷贝/移动）。

**unordered_map 哈希冲突**: 标准库用 separate chaining（链表法）。load_factor = 元素数/桶数，超过 max_load_factor(默认1.0) → rehash（桶数翻倍）。

### 40.7 常见面试追问

**Q: new/delete vs malloc/free 区别？**
- new: 分配内存 + 调构造函数。delete: 调析构 + 释放内存。
- malloc: 只分配内存（void*）。free: 只释放内存。
- new 失败抛 std::bad_alloc，malloc 返回 NULL。

**Q: struct vs class 区别？**
唯一区别: struct 默认 public，class 默认 private。

**Q: C++ 内存布局？**
栈(局部变量,函数调用) → 堆(new/malloc) → 全局/静态 → 代码段 → 常量段

**Q: RAII 是什么？**
Resource Acquisition Is Initialization。资源在构造函数中获取，析构函数中释放。
例: lock_guard 构造时加锁，析构时解锁 → 异常安全，不会忘记解锁。

**Q: const 引用延长临时对象生命周期？**
`const int& r = 42;` → 合法，42 的生命周期延长到 r 的作用域结束。

**Q: 编译链接过程？**
预处理(展开宏/include) → 编译(生成.o) → 链接(合并.o+库→可执行文件)
静态链接(.a): 代码复制进可执行文件。动态链接(.so/.dll): 运行时加载。

## 12. C++ 深入原理详解（小红书引擎架构面试加强版）

### 41.1 智能指针深入

#### unique_ptr 底层实现原理

unique_ptr 本质上是一个 **模板类**，内部只存一个裸指针：
```cpp
// 简化实现（核心思路）
template <typename T, typename Deleter = std::default_delete<T>>
class unique_ptr {
    T* ptr_;
public:
    explicit unique_ptr(T* p = nullptr) : ptr_(p) {}
    ~unique_ptr() { delete ptr_; }           // 析构时自动 delete

    // 禁止拷贝！
    unique_ptr(const unique_ptr&) = delete;
    unique_ptr& operator=(const unique_ptr&) = delete;

    // 允许移动
    unique_ptr(unique_ptr&& other) noexcept : ptr_(other.ptr_) {
        other.ptr_ = nullptr;   // 源对象置空
    }

    T& operator*() const { return *ptr_; }
    T* operator->() const { return ptr_; }
    T* get() const { return ptr_; }
    T* release() { T* p = ptr_; ptr_ = nullptr; return p; } // 释放所有权
    void reset(T* p = nullptr) { delete ptr_; ptr_ = p; }   // 替换管理的对象
};
```

**为什么 sizeof(unique_ptr) == sizeof(T*) == 8?**
因为它只存了一个裸指针。没有引用计数，没有控制块，所以是**零开销抽象**。
（但如果指定了有状态的 Deleter，则大小会增加）

**自定义 Deleter（面试加分点）**:
```cpp
// 用于管理 FILE*、CUDA 内存等非 new 分配的资源
auto file_deleter = [](FILE* f) { fclose(f); };
std::unique_ptr<FILE, decltype(file_deleter)> fp(fopen("a.txt", "r"), file_deleter);
// 离开作用域自动 fclose

// CUDA 内存管理
auto cuda_deleter = [](void* p) { cudaFree(p); };
void* raw;
cudaMalloc(&raw, 1024);
std::unique_ptr<void, decltype(cuda_deleter)> gpu_mem(raw, cuda_deleter);
```

#### shared_ptr 控制块详解

```
shared_ptr<Widget> 的内存布局:

  shared_ptr 对象 (16B)            控制块 (Control Block)
  ┌──────────────────┐            ┌─────────────────────┐
  │ T* object_ptr    │───────────→│ Widget 对象          │  (如果 make_shared)
  │ ControlBlock* cb │──┐         │ strong_count (atomic) │
  └──────────────────┘  │         │ weak_count (atomic)   │
                        └────────→│ Deleter (可选)        │
                                  │ Allocator (可选)      │
                                  └─────────────────────┘

make_shared<Widget>() 的情况 (1次分配):
  ┌─────────────────────────────┐
  │ strong_count │ weak_count   │  ← 控制块
  │ Widget 对象的内存            │  ← 对象（连续存放）
  └─────────────────────────────┘

shared_ptr<Widget>(new Widget()) 的情况 (2次分配):
  分配1: Widget* ─→ 堆上的 Widget 对象
  分配2: ControlBlock* ─→ 堆上的控制块
```

**引用计数的线程安全**:
- strong_count 和 weak_count 是 `std::atomic<int>`
- 拷贝 shared_ptr = `strong_count.fetch_add(1)` 原子操作 → **线程安全**
- 但！**对象本身的读写不是线程安全的**
```cpp
auto sp = std::make_shared<int>(0);
// 线程1: *sp = 1;   // 不安全！
// 线程2: *sp = 2;   // 数据竞争！对象本身需要额外保护
// 安全做法: 加 mutex，或用 atomic<shared_ptr>（C++20）
```

**析构流程**:
1. 最后一个 shared_ptr 析构 → strong_count 降到 0 → **调对象析构函数 + 释放对象内存**
2. 最后一个 weak_ptr 也析构 → weak_count 降到 0 → **释放控制块内存**
3. 注意：如果还有 weak_ptr 活着，对象已死但控制块还在（weak_ptr::expired() = true）

#### weak_ptr 打破循环引用的完整例子

```cpp
class B; // 前向声明
class A {
public:
    std::shared_ptr<B> b_ptr;
    ~A() { std::cout << "A destroyed\n"; }
};
class B {
public:
    std::weak_ptr<A> a_ptr;    // ★ 关键：用 weak_ptr!
    ~B() { std::cout << "B destroyed\n"; }
};

{
    auto a = std::make_shared<A>();  // a.strong = 1
    auto b = std::make_shared<B>();  // b.strong = 1
    a->b_ptr = b;                    // b.strong = 2
    b->a_ptr = a;                    // a.strong 仍然 = 1 (weak 不加)
}
// 离开作用域:
// a 析构 → a.strong = 0 → A 对象被删除 → b.strong = 1
// b 析构 → b.strong = 0 → B 对象被删除
// 输出: "A destroyed" "B destroyed" ✓

// 如果 B 用 shared_ptr<A>:
// a 析构 → a.strong = 1 (B 还持有) → A 不删除
// b 析构 → b.strong = 1 (A 还持有) → B 不删除
// → 内存泄漏！
```

### 41.2 Move 语义深入

#### 值类别详解

```
表达式
├── glvalue (有身份)
│   ├── lvalue (有身份 + 不可移动)  -- 变量名, *ptr, arr[i]
│   └── xvalue (有身份 + 可移动)    -- std::move(x), 返回T&&的函数
└── rvalue (可移动)
    ├── xvalue (有身份)
    └── prvalue (无身份)            -- 字面量 42, 临时对象 Foo()
```

**面试简化版**: 有名字的 = 左值，没名字的临时值 = 右值。`std::move(x)` 把左值变成右值。

#### 移动 vs 拷贝的实际差异

```cpp
class String {
    char* data_;
    size_t size_;
public:
    // 拷贝构造: O(n)，分配新内存 + memcpy
    String(const String& other) : size_(other.size_) {
        data_ = new char[size_];
        memcpy(data_, other.data_, size_);
    }
    // 移动构造: O(1)，偷指针
    String(String&& other) noexcept : data_(other.data_), size_(other.size_) {
        other.data_ = nullptr;  // 源必须置空！否则双重 delete
        other.size_ = 0;
    }
};

// 实际影响:
std::vector<String> vec;
vec.push_back(String("hello"));  // 临时 String → 移动构造（快）
String s("world");
vec.push_back(s);                // 左值 → 拷贝构造（慢）
vec.push_back(std::move(s));     // 手动转右值 → 移动构造（快）
// 注意: move 后的 s 处于"有效但未定义"状态，不要再用它
```

#### noexcept 为什么重要

```cpp
// vector 扩容时:
// 如果元素的移动构造有 noexcept → 用移动 (O(1))
// 如果没有 noexcept → 退回用拷贝 (O(n))，因为移动到一半如果抛异常，
//   已经移走的元素无法恢复（强异常安全保证要求）
Buffer(Buffer&& other) noexcept;  // ← 这个 noexcept 很重要!
```

#### 完美转发 (Perfect Forwarding)

```cpp
// 问题: 如何写一个 wrapper 函数，保持参数的左/右值性质？
template <typename T>
void wrapper(T&& arg) {            // 万能引用（不是右值引用！在模板中）
    real_function(std::forward<T>(arg));  // 完美转发
}

// 引用折叠规则（编译器规则）:
// T& &   → T&     (左值引用的引用 = 左值引用)
// T& &&  → T&     (左值引用的右值引用 = 左值引用)
// T&& &  → T&     (右值引用的左值引用 = 左值引用)
// T&& && → T&&    (右值引用的右值引用 = 右值引用)

// 实际应用: emplace_back 就是用完美转发把参数转给构造函数
vec.emplace_back("hello", 5);  // forward 到 String(const char*, int)
```

### 41.3 虚函数 / 多态深入

#### vtable 完整内存布局

```cpp
class Base {
    int x;                    // 成员变量
public:
    virtual void foo() {}     // 虚函数1
    virtual void bar() {}     // 虚函数2
    void baz() {}             // 非虚函数（不在 vtable 中）
};
class Derived : public Base {
    int y;
public:
    void foo() override {}    // 重写 foo
    virtual void qux() {}    // 新增虚函数
};

// 内存布局:
// Base 对象:
// ┌──────────┐
// │ vptr (8B) │ → Base_vtable
// │ x    (4B) │
// │ pad  (4B) │ ← 对齐
// └──────────┘  总 16B

// Derived 对象:
// ┌──────────┐
// │ vptr (8B) │ → Derived_vtable
// │ x    (4B) │ (继承自 Base)
// │ y    (4B) │
// └──────────┘  总 16B

// vtable (编译期生成，只读数据段):
// Base_vtable:    [&Base::foo,    &Base::bar]
// Derived_vtable: [&Derived::foo, &Base::bar, &Derived::qux]
//                  ↑ 重写了        ↑ 继承了     ↑ 新增了
```

#### 虚函数调用 vs 直接调用 的性能差异

```
直接调用: call 0x401234          → 1 条指令
虚函数:   mov rax, [rdi]        → 读 vptr (可能 cache miss)
          mov rax, [rax + 16]   → 读 vtable[2] (可能 cache miss)
          call rax              → 间接跳转 (分支预测困难)

开销来源:
1. 两次间接内存访问 (可能 cache miss)
2. 间接调用 → CPU 分支预测器难以预测目标地址
3. 编译器无法 inline（运行时才知道调哪个函数）

实际影响: 大多数场景可忽略。但如果在 hot loop 里每秒调百万次虚函数，
         考虑用 CRTP（静态多态）替代:
```

#### CRTP (Curiously Recurring Template Pattern) — 静态多态

```cpp
// 用模板替代虚函数，零开销
template <typename Derived>
class Base {
public:
    void interface() {
        static_cast<Derived*>(this)->implementation();  // 编译时决定
    }
};

class Impl : public Base<Impl> {
public:
    void implementation() { /* 具体实现 */ }
};

// 编译器可以 inline，无 vtable 开销
// 缺点: 不能用基类指针管理不同子类（没有运行时多态）
```

### 41.5 并发编程深入

#### mutex 家族

```cpp
std::mutex               // 基本互斥锁，不可重入
std::recursive_mutex      // 可重入（同线程可多次 lock），性能差一些
std::timed_mutex          // 可以 try_lock_for(timeout)
std::shared_mutex (C++17) // 读写锁:
                          //   shared_lock → 读（多个线程可同时持有）
                          //   unique_lock → 写（独占）

// 读写锁典型场景：搜索引擎的索引
std::shared_mutex rw_mtx;
// 查询线程（高频，允许并发）:
{
    std::shared_lock lock(rw_mtx);   // 读锁
    return index.search(query);
}
// 更新线程（低频，独占）:
{
    std::unique_lock lock(rw_mtx);   // 写锁，等所有读锁释放
    index.update(new_data);
}
```

#### atomic 与 memory order 详解

```cpp
std::atomic<int> x{0}, y{0};

// Sequential Consistency (seq_cst) — 默认，最安全
// 所有线程看到的操作顺序一致（像单线程执行）
x.store(1);           // 默认 seq_cst
y.load();             // 默认 seq_cst

// Acquire-Release — 生产者消费者模式
std::atomic<bool> ready{false};
int data = 0;
// 生产者:
data = 42;                                        // 普通写
ready.store(true, std::memory_order_release);      // release 屏障: 之前的写对 acquire 可见
// 消费者:
while (!ready.load(std::memory_order_acquire)) {}  // acquire 屏障: 之后的读看到 release 之前的写
assert(data == 42);                                // 保证看到 42 ✓

// Relaxed — 只保证原子性，不保证顺序
counter.fetch_add(1, std::memory_order_relaxed);   // 计数器场景，无需顺序保证
```

**面试答法**: "默认用 seq_cst 最安全。追求性能时用 acquire/release 做生产者消费者同步。relaxed 只用于独立的计数器。"

#### 线程池实现思路

```cpp
class ThreadPool {
    std::vector<std::thread> workers;
    std::queue<std::function<void()>> tasks;
    std::mutex mtx;
    std::condition_variable cv;
    bool stop = false;
public:
    ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i)
            workers.emplace_back([this] {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock lock(mtx);
                        cv.wait(lock, [this] { return stop || !tasks.empty(); });
                        if (stop && tasks.empty()) return;
                        task = std::move(tasks.front());
                        tasks.pop();
                    }
                    task();  // 执行任务
                }
            });
    }
    template <typename F>
    void enqueue(F&& f) {
        {
            std::lock_guard lock(mtx);
            tasks.emplace(std::forward<F>(f));
        }
        cv.notify_one();
    }
    ~ThreadPool() {
        { std::lock_guard lock(mtx); stop = true; }
        cv.notify_all();
        for (auto& w : workers) w.join();
    }
};
```

**核心要点（面试问 "实现一个线程池"）**:
1. N 个工作线程，无限循环从任务队列取任务
2. 任务队列用 mutex + condition_variable 保护
3. 析构时设 stop=true → notify_all → join 所有线程
4. enqueue 用完美转发 + notify_one 通知一个空闲线程

### 41.6 STL 容器底层深入

#### vector 动态扩容完整流程

```
初始: capacity=0, size=0, data=nullptr

push_back(1):
  capacity=0 < size+1 → 扩容!
  new_cap = max(1, old_cap * 2) = 1
  分配 1*sizeof(T) 字节新内存
  移动旧元素到新内存（0个）
  释放旧内存
  → capacity=1, size=1, data=[1]

push_back(2):
  capacity=1 < 2 → 扩容!
  new_cap = 2
  分配新内存, 移动 [1] 到新位置
  → capacity=2, size=2, data=[1,2]

push_back(3):
  capacity=2 < 3 → 扩容!
  new_cap = 4
  分配新内存, 移动 [1,2]
  → capacity=4, size=3, data=[1,2,3,_]

push_back(4):
  capacity=4 >= 4 → 不扩容, 直接放
  → capacity=4, size=4, data=[1,2,3,4]
```

**扩容为什么选 2 倍?**
- 1.5x 或 2x 都行（MSVC 用 1.5x, GCC 用 2x）
- 太小(如 1.1x): 频繁扩容，大量 memcpy
- 太大(如 4x): 浪费内存
- 2x 保证 push_back **均摊 O(1)**: n 次 push 的总拷贝 = n + n/2 + n/4 + ... ≈ 2n

**迭代器失效规则**:
```cpp
vector<int> v = {1,2,3,4,5};
auto it = v.begin() + 2;  // 指向 3
v.push_back(6);   // 如果触发扩容 → 所有迭代器失效!
v.erase(v.begin()); // erase 点之后的迭代器全部失效
v.insert(v.begin(), 0); // insert 点之后的迭代器全部失效
```

#### unordered_map / 哈希表深入

```
桶数组 (bucket array): 
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │
└─┬─┴───┴─┬─┴───┴─┬─┴───┴───┴───┘
  ↓       ↓       ↓
  A→C     B       D→E     (链表法, Separate Chaining)

插入 key:
  1. hash(key) % bucket_count → 定位桶
  2. 遍历桶的链表，key 存在则覆盖 value，不存在则头插
  3. 如果 load_factor > max_load_factor (默认1.0) → rehash:
     桶数翻倍 → 所有元素重新 hash 分配 → O(n)

查找复杂度:
  平均: O(1 + load_factor) ≈ O(1)
  最坏: O(n)（所有 key hash 到同一个桶 → 退化为链表）
```

**面试追问: map vs unordered_map 怎么选？**
- **需要有序遍历** → map (红黑树, O(log n))
- **只需快速查找** → unordered_map (O(1))
- **key 不好 hash**（如自定义结构体） → map（只需 operator<）
- unordered_map **不保证遍历顺序**，每次 rehash 后顺序变化

#### 红黑树（map/set 底层）

```
性质:
1. 节点是红色或黑色
2. 根节点是黑色
3. 叶子(NIL)是黑色
4. 红色节点的子节点必须是黑色（不能连续两个红色）
5. 从任一节点到叶子的路径上黑色节点数相同

→ 保证最长路径 ≤ 2 × 最短路径 → 近似平衡
→ 查找/插入/删除都是 O(log n)

vs AVL树: 红黑树旋转次数更少（插入最多2次，删除最多3次），
          适合频繁插入删除。AVL 更严格平衡，查找略快。
```

**面试够用版**: "红黑树是近似平衡的二叉搜索树，通过颜色约束保证高度 ≤ 2log(n+1)，操作都是 O(log n)。比 AVL 旋转少，插入删除性能好。"

### 41.7 C++ 内存模型与对象模型

#### 对象内存布局

```cpp
class A {
    char c;    // offset 0, 1B
    // 3B padding (int 需要 4B 对齐)
    int i;     // offset 4, 4B
    char c2;   // offset 8, 1B
    // 7B padding (总大小需要 8B 对齐, 因为最大对齐要求是 int=4?
    //             实际: sizeof(A) = 12, 对齐到 4)
};
// sizeof(A) = 12

class B {
    char c;
    char c2;   // offset 1
    // 2B padding
    int i;     // offset 4
};
// sizeof(B) = 8 ← 调整成员顺序可以减少 padding!
```

**规则**: 每个成员的 offset 必须是其对齐要求的整数倍。整个结构体大小是最大对齐要求的整数倍。

#### 堆 vs 栈 vs 静态区

```
高地址
┌────────────────┐
│     内核空间     │
├────────────────┤
│     栈 (Stack)  │ ← 向下增长, 函数局部变量, 自动管理

│                │
│       ↑        │
│     堆 (Heap)  │ ← 向上增长, new/malloc, 手动管理
├────────────────┤
│   BSS 段       │ ← 未初始化的全局/静态变量
├────────────────┤
│   Data 段      │ ← 已初始化的全局/静态变量
├────────────────┤
│   Text 段      │ ← 可执行代码 (只读)
低地址
```

**new 的完整过程**:
1. 调 `operator new(size)` → 内部调 `malloc` → 系统调用 `mmap`/`brk` → 分配堆内存
2. 在分配的内存上调**构造函数** (`placement new`)
3. 返回类型化指针

**Q: 你的 CachingAllocator 是如何设计的？**
```
设计思路: 仿照 PyTorch 的 CUDACachingAllocator 简化版

数据结构: std::multimap<size_t, byte*> free_blocks_
          key=内存块大小, value=GPU 指针
          multimap: 允许多个相同大小的块, 且按 key 排序

分配(allocate):
  1. lower_bound(size) → 找 ≥ size 的最小块 (best-fit)
  2. 如果找到且 block_size ≤ size * 2 → 直接复用（2x容忍度避免碎片）
  3. 否则 cudaMalloc 新分配

释放(release):
  1. 不调 cudaFree! 而是放回 free_blocks_
  2. 但如果总缓存 > 4GB (MAX_CACHE_BYTES) → 真正 cudaFree

为什么要这样?
  cudaMalloc/cudaFree 开销巨大: 约 0.1-1ms per call
  推理每层有多个临时 tensor 申请释放
  28层 × ~5 alloc/层 = 140 次/token
  没有缓存: 140 × 0.5ms = 70ms/token = 14 tok/s
  有缓存: 140 × 0.001ms = 0.14ms/token → 开销忽略

线程安全: std::mutex 保护所有操作
```

### 42.1 SSO (Small String Optimization) — string 底层优化

**核心**: 短字符串不 malloc，直接存在 string 对象内部。

```
sizeof(std::string) = 32 bytes (GCC libstdc++)

[短字符串模式] (长度 ≤ 15):
┌───────────────────────────────────────────┐
│ char buf[16]  │ uint8_t size │ padding... │
│ "hello\0____" │     5        │            │
└───────────────────────────────────────────┘
  → 对象内部存储! 零次 malloc, 极度 cache 友好

[长字符串模式] (长度 > 15):
┌───────────────────────────────────────────┐
│ char* ptr     │ size_t size  │ size_t capacity │
│   → 堆内存    │     100      │      128        │
└───────────────────────────────────────────┘
  → ptr 指向堆上分配的内存
```

**SSO 阈值**:
- GCC (libstdc++): 15 字符
- Clang (libc++): 22 字符
- MSVC: 15 字符

**为什么这个优化很重要？**
- 大多数实际字符串很短(文件名、变量名、ID、标签等)
- malloc/free 的开销 ~= 100ns, SSO 构造 ~= 10ns, **10x 差距**
- 短字符串在对象内部 = cache line 连续访问 → SIMD 友好

**面试回答模板**:
> "string 最重要的优化是 SSO（Small String Optimization），短字符串（GCC ≤15字符）直接存在对象内部，不进行堆分配，避免了 malloc 开销并提高了 cache 局部性。长字符串则退回正常的指针+堆内存模式。其他优化还包括 C++11 的 move 语义（O(1) 转移所有权）、C++17 的 string_view（零拷贝引用）。旧版 GCC 有 COW 优化但在 C++11 后因多线程 atomic 开销被废弃。"

### 42.2 隐式构造与 explicit 关键字

**C++ 编译器生成的 6 个特殊成员函数（Rule of 6）**:
```cpp
class T {
    T();                            // 1. 默认构造
    ~T();                           // 2. 析构
    T(const T&);                    // 3. 拷贝构造
    T& operator=(const T&);         // 4. 拷贝赋值
    T(T&&) noexcept;                // 5. 移动构造 (C++11)
    T& operator=(T&&) noexcept;     // 6. 移动赋值 (C++11)
};
```

**何时自动生成？**
- 你没定义任何构造 → 全部自动生成
- 你定义了**拷贝构造** → 移动构造/赋值**不再自动生成**
- 你定义了**析构函数** → 移动操作**不再自动生成**（Rule of 5 触发）
- 你写了任何构造函数 → **默认构造不再生成**

**Rule of 0 / 5**:
- **Rule of 0**: 不手动管理资源 → 6 个全用默认（推荐！用智能指针/RAII 容器）
- **Rule of 5**: 手动管理资源（如裸指针） → 5 个都要自己写（析构+拷贝构造+拷贝赋值+移动构造+移动赋值）

**隐式转换构造（面试官真正问的）**:
```cpp
class Widget {
public:
    Widget(int size) {}                   // 单参数 → 允许 int 隐式变 Widget!
    Widget(const std::string& name) {}    // 单参数 → string 隐式变 Widget!
};

void process(Widget w) {}

// 危险的隐式转换！
process(42);          // OK? 编译通过! 42 → Widget(42)
process("hello");     // OK? 编译通过! "hello" → string → Widget(string)

// 经典 bug:
std::vector<int> v = 10;  // 编译通过! 10 → vector(10) → 10个元素的空vector!
```

**explicit 阻止隐式转换**:
```cpp
class Widget {
public:
    explicit Widget(int size) {}     // 加了 explicit
};

process(42);           // 编译失败! ✓ 防止了意外转换
process(Widget(42));   // 编译通过 ✓ 必须显式构造

// 实际项目中: 单参数构造函数几乎都应该加 explicit
// 例外: 拷贝构造、移动构造、以及你真的想要隐式转换的时候
```

**在哪些地方容易触发隐式构造（面试官追问的）**:
1. **函数参数传递**: `void foo(Widget w); foo(42);`
2. **返回值**: `Widget bar() { return 42; }`
3. **初始化**: `Widget w = 42;`
4. **容器操作**: `vector<Widget> v; v.push_back(42);`
5. **条件表达式**: `Widget w = flag ? Widget(1) : 42;`

### 42.3 初始化列表 vs 函数体赋值

```cpp
// ❌ 差: 先默认构造，再赋值（2步）
class Person {
    string name;
    string city;
    int age;
public:
    Person(string n, string c, int a) {
        name = n;      // 第1步: name 默认构造为 ""
        city = c;      // 第2步: name = n (拷贝赋值)
        age = a;       // → 每个 string 做了 2 次操作!
    }
};

// ✅ 好: 初始化列表，直接构造（1步）
class Person {
    string name;
    string city;
    int age;
public:
    Person(string n, string c, int a)
        : name(std::move(n))     // 直接移动构造, 1步！
        , city(std::move(c))
        , age(a) {}
};
```

**性能差异**:
- 函数体赋值: 默认构造 + 拷贝赋值 = **2 次操作** per 成员
- 初始化列表: 直接拷贝/移动构造 = **1 次操作** per 成员
- 对 string 这类重型对象，差距显著

**必须用初始化列表的场景**:
1. **const 成员**: `const int id;` — 不能赋值，只能初始化
2. **引用成员**: `int& ref;` — 不能赋值，只能初始化
3. **没有默认构造的成员**: 如果成员类型没有无参构造函数
4. **基类构造**: `Derived() : Base(args) {}`

**初始化顺序**: 按**声明顺序**，不是初始化列表的书写顺序！
```cpp
class Foo {
    int a;   // 先初始化（声明在前）
    int b;   // 后初始化
public:
    Foo() : b(1), a(b) {}  // ⚠ 危险! a 先初始化，此时 b 还未初始化!
    // 正确写法: Foo() : a(1), b(a) {}
};
```

### 42.4 emplace_back vs push_back 深入

```cpp
vector<pair<string, int>> v;

// push_back: 先构造临时对象，再 copy/move 进 vector
v.push_back(make_pair("hello", 42));
// 步骤: 1. 构造临时 pair  2. move 进 vector  3. 销毁临时对象

// emplace_back: 直接在 vector 内存中原地构造
v.emplace_back("hello", 42);
// 步骤: 1. forward 参数到 pair 构造函数  2. 在 vector 末尾直接构造
// 省了: 一次临时对象创建 + 一次 move + 一次析构

// 在 Person 例子中:
vector<Person> results;
results.reserve(N);                          // 预分配
for (int i = 0; i < N; ++i) {
    results.emplace_back("Alice", "Beijing", i);  // 原地构造, 最优!
}
```

**什么时候 emplace_back 没优势？**
当参数本身就是目标类型时:
```cpp
string s = "hello";
v.push_back(s);          // 拷贝
v.push_back(std::move(s)); // 移动
v.emplace_back(std::move(s)); // 和上面一样, 没优势
```

### 42.5 代码优化模式总结（面试代码题常见优化点清单）

```
1. vector::reserve(N)       → 预分配避免扩容
2. emplace_back             → 原地构造避免临时对象
3. 初始化列表               → 避免默认构造+赋值
4. const& 传参              → 避免拷贝
5. std::move               → 转移而非拷贝
6. 循环外提常量             → 避免重复构造
7. string_view              → 只读字符串零拷贝
8. range-based for + auto&  → 避免拷贝
9. [[likely]]/[[unlikely]]  → 分支预测提示(C++20)
10. 避免虚函数在热路径      → 用 CRTP 或模板
```

**完整优化后的代码（面试标准答案）**:
```cpp
struct Person {
    std::string name;
    std::string city;
    int age;
    // ✅ 初始化列表 + move
    Person(std::string n, std::string c, int a)
        : name(std::move(n)), city(std::move(c)), age(a) {}
};

std::vector<Person> generate(int N) {
    std::vector<Person> results;
    results.reserve(N);                      // ✅ 预分配
    const std::string name = "Alice";        // ✅ 循环外定义
    const std::string city = "Beijing";
    for (int i = 0; i < N; ++i) {
        results.emplace_back(name, city, i); // ✅ 原地构造
    }
    return results;   // ✅ NRVO, 不拷贝（编译器优化）
}
```

### 42.6 TP 张量并行 — LLaMA 结构中的切分

```
LLaMA Transformer Block:
┌────────────────────────────────────────────┐
│  Input X (batch, seq, hidden)              │
│     ↓                                      │
│  Self-Attention:                           │
│    Q = X·Wq    → 列切分 (每GPU分到一部分head)│
│    K = X·Wk    → 列切分                    │
│    V = X·Wv    → 列切分                    │
│    Attn 计算   → 各 GPU 独立算自己的 head   │
│    O = Concat·Wo → 行切分 (Wo 按行切)      │
│    AllReduce → 汇总结果                     │
│     ↓                                      │
│  MLP:                                      │
│    gate = X·Wgate  → 列切分               │
│    up = X·Wup      → 列切分               │
│    SwiGLU(gate, up) → 各 GPU 独立计算      │
│    down = act·Wdown → 行切分              │
│    AllReduce → 汇总结果                     │
└────────────────────────────────────────────┘

关键原则:
- 列切分(Column Parallel): 权重矩阵按列切, 输出拼接
- 行切分(Row Parallel):    权重矩阵按行切, 输出求和(AllReduce)
- 每个 Transformer Block 只需 2 次 AllReduce (Attn 1次 + MLP 1次)
- AllReduce 是主要通信开销 → 通信量 = 2 × batch × seq × hidden × sizeof(dtype)
```

### SM 内部执行模型
```
┌─────────────────────────────────────────────────────┐
│  SM (Streaming Multiprocessor)                       │
│                                                      │
│  Warp Scheduler ×4                                   │
│    每个 scheduler 每周期选 1 个 eligible warp 发射指令 │
│    Eligible 条件:                                     │
│      - 不在等待内存 (not memory stall)                │

│                                                      │
│  ★ GPU 靠大量 Warp 切换隐藏延迟 ★                    │
│    Warp A 等待 400 cycle 内存访问 →                   │
│    Scheduler 立即切换到 Warp B, C, D... 执行           │
│    → Warp 切换零开销! (所有 Warp 的状态常驻寄存器)     │
│    → 所以需要足够多的 Warp (Occupancy)                 │
└─────────────────────────────────────────────────────┘
```

### Occupancy 计算实例
```
SM89 限制: 最多 48 Warps/SM, 1024 threads/Block, 16 Blocks/SM
          寄存器 65536 个/SM, Shared Memory 100KB/SM

例1: Block=256 threads, 每线程 32 寄存器, SMEM=0
  Warps/Block = 256/32 = 8
  寄存器限制: 65536/(32×256) = 8 Block/SM → 8×8=64 Warps → cap 48
  Block限制: 16 Block/SM → 16×8=128 → cap 48
  Occupancy = 48/48 = 100% ✓

例2: Block=256, SMEM=48KB/Block
  SMEM限制: 100/48 = 2 Block/SM → 2×8=16 Warps
  Occupancy = 16/48 = 33%! ← SMEM 是瓶颈!
  → FlashAttention 的 SMEM 用量直接影响 Occupancy!

例3: Block=256, 每线程 128 寄存器
  寄存器限制: 65536/(128×256) = 2 Block → 2×8=16 Warps
  Occupancy = 33%! ← 寄存器是瓶颈!
```

## 15. CUDA 线程模型与执行原理

### 层次结构
```
Thread → Warp(32) → Block(至多1024) → Grid
tid = blockIdx.x * blockDim.x + threadIdx.x
```

### Warp 执行原理 (SIMT)
- 32 线程**锁步执行**同一条指令 (Single Instruction Multiple Threads)
- 不同的是每个线程操作不同的数据（不同的寄存器值）
- 分支时: 两个分支**串行执行** (Warp Divergence)
  ```
  if (tid % 2 == 0) A();  // 偶数线程执行 A, 奇数等待
  else B();                // 奇数线程执行 B, 偶数等待
  // 总时间 = time(A) + time(B)，不是 max!
  ```

### Kernel Launch 底层
```cuda
kernel<<<dim3(gx,gy,gz), dim3(bx,by,bz), smem_bytes, stream>>>(args);
```
- CPU 端: 将参数打包推入 GPU 命令队列 → ~5-15µs 开销
- GPU 端: Block Scheduler 将 Block 分配到 SM
- 异步: CPU 不等 kernel 完成 → 继续执行后续 CPU 代码
- `cudaGetLastError()`: 检查 launch 配置错误(不等完成)
- `cudaDeviceSynchronize()`: 等待 GPU 所有工作完成

## 16. 内存合并与访存优化

### Coalesced Access 详细机制
```
一个 Warp 发出 32 个 load 请求:
  线程 0: load addr[0×4]    = 地址 0
  线程 1: load addr[1×4]    = 地址 4
  ...
  线程 31: load addr[31×4]  = 地址 124

GPU 内存传输最小单位 = Sector (32 Bytes)
  128 字节 = 4 sectors → 1 个 cache line

情况1: 完全合并 → 连续 128B → 1 个 cache line → 1 次传输
情况2: stride-2 → 跨 256B → 2 个 cache line → 利用率 50%
情况3: 随机访问 → 最多 32 个 cache line → 利用率 3%

float4 向量化合并:
  32 threads × float4(16B) = 512B → 4 cache lines = 16 sectors
  省 3/4 的 load 指令! 总效率更高。
```

### __restrict__ 的作用
```cpp
__global__ void add(float* __restrict__ c,
                    const float* __restrict__ a,
                    const float* __restrict__ b, int n) {
    // __restrict__ 告诉编译器: a, b, c 不会指向重叠内存
    // 编译器可以: 重排 load/store 指令, 使用寄存器缓存值
    // 不加: 编译器必须假设 a 和 c 可能重叠 → 每次写 c 后重新读 a
}
```

## 17. Roofline 模型与性能分析

### 模型公式
```
性能上限 = min(峰值计算, 算术强度 × 峰值带宽)

其中:
  算术强度 (Arithmetic Intensity, AI) = FLOP / Byte
  FLOP = 算子的浮点运算次数
  Byte = 算子的内存访问量（读+写）
```

### RTX 4060 Ti 的 Roofline 图
```
性能
(GFLOPS)
  ^
  |                             ┌──────────── 峰值计算 ≈ 12,000 GFLOPS (FP32)
  |                            /
  |                           /
  |                          /
  |                         /  ← 斜率 = 峰值带宽 = 288 GB/s
  |                        /
  |                       /
  |      ↑ 拐点 ≈ 41.7 FLOP/Byte (= 12000 / 288)
  |     /
  |    /
  |   /
  |  /
  | /
  |/ ← 原点
  └──────────────────────────────────────→ 算术强度 (FLOP/Byte)
      0.08  0.33   0.5   10    42   170
      Add  SwiGLU GEMV  RoPE  拐点  GEMM
      ↓               ↓      ↓     ↓
   Memory-Bound    M-Bound  拐点  Compute-Bound
```

### 拐点(Balance Point)计算
```
拐点 = 峰值计算 / 峰值带宽
     = 12,000 GFLOPS / 288 GB/s
     = 41.7 FLOP/Byte

算术强度 < 41.7 → Memory-Bound (在斜面上)
算术强度 > 41.7 → Compute-Bound (在平面上)
```

### 各算子实际计算

#### Add 算子
```
输入: a[n], b[n]  输出: c[n]
FLOP = n (每元素 1 次加法)
Byte = 3n × 4B = 12n (读 a + 读 b + 写 c, 每个 4B float)
AI = n / 12n = 0.083 FLOP/Byte → 极度 Memory-Bound
```

#### RMSNorm 算子
```
FLOP ≈ 5d (平方d + 求和d + sqrt + 乘weight d + 乘inv_rms d)
Byte = 3d × 4B = 12d
AI ≈ 5/12 ≈ 0.42 FLOP/Byte → Memory-Bound
```

#### GEMM (Linear)
```
C [M,N] = A [M,K] × B [K,N]
FLOP = 2MNK
Byte = (MK + KN + MN) × 4B
M=N=K=1024: AI ≈ 170 FLOP/Byte → Compute-Bound

但 Decode 时 M=1 (GEMV):
  FLOP = 2NK, Byte ≈ 4NK
  AI = 0.5 FLOP/Byte → Memory-Bound!
```

#### SwiGLU 算子
```
AI ≈ 4/12 ≈ 0.33 FLOP/Byte → Memory-Bound
```

## 18. Warp Shuffle 归约原理与实现

### __shfl_down_sync 底层
```
__shfl_down_sync(mask, val, delta):
  - mask = 0xffffffff → 32 个 lane 全参与
  - lane i 的 val 接收 lane (i+delta) 的 val
  - 数据在寄存器文件内部传输 → ~1 cycle 延迟
  - 不经过 Shared Memory! 不需要 __syncthreads!

32 线程求和: 5 次迭代 (delta=16,8,4,2,1) → lane 0 持有总和
```

### warp_reduce_max (Argmax 变体)
```cuda
__device__ void warp_reduce_max(float& val, size_t& idx) {
    for (int delta = 16; delta >= 1; delta >>= 1) {
        float other_val = __shfl_down_sync(0xffffffff, val, delta);
        size_t other_idx = __shfl_down_sync(0xffffffff, idx, delta);
        if (other_val > val) { val = other_val; idx = other_idx; }
    }
}
// 同时归约 val 和 idx → 每轮 2 次 shfl_down
```

### 二级 Block Reduce (256 threads = 8 Warps)
```
阶段1: 每 Warp 内 Shuffle → 8 个 Warp 的 lane0 各持部分和
阶段2: 8 个 lane0 写入 __shared__ [32] → __syncthreads()
阶段3: Warp0 的 lane0-7 读取 → 再 Shuffle → thread 0 持有总和

为什么需要 __syncthreads()?
  Warp 间不能 Shuffle（Shuffle 只在 Warp 内）
  必须用 Shared Memory 做中转 → 需要同步保证可见性
```

## 19. Shared Memory 与 Bank Conflict

### Bank 物理结构
```
Shared Memory = 32 个独立 Bank, 每 Bank 宽 4 字节
地址映射: Bank ID = (byte_addr / 4) % 32
```

### Bank Conflict 发生机制
```
sA[32][32] (float), 每行 32×4B = 128B

列访问: sA[0][0], sA[1][0], sA[2][0], ...
  sA[0][0] = addr 0   → Bank 0
  sA[1][0] = addr 128  → Bank (128/4)%32 = Bank 0!
  → 32-way conflict → 延迟 ×32!

sA[32][33] (padding 后):
  sA[0][0] = addr 0    → Bank 0
  sA[1][0] = addr 132  → Bank (132/4)%32 = Bank 1 ✓
  → 0 conflict!
```

## 20. CUDA Stream 与异步执行

### 同步 vs 异步
```
CPU 时间线:      [launch kernel] [launch kernel] [memcpy] ...
                      ↓               ↓            ↓
GPU 时间线:      .....[kernel 1].....[kernel 2]...[memcpy]...

默认 stream (0): 所有操作串行
  A<<<>>>(); B<<<>>>(); → A 完成后 B 才开始

多 stream:
  cudaStream_t s1, s2;
  A<<<..., s1>>>(); B<<<..., s2>>>(); → A 和 B 可能并行!
```

### cudaMalloc 是同步的!
```
cudaMalloc 调用过程:
  1. CPU 发请求给 GPU Driver
  2. Driver 搜索空闲 GPU 内存
  3. 可能触发内存整理/页面分配
  4. 返回指针给 CPU
  → 全程 CPU 阻塞 (同步), ~0.5-2ms

所以推理中不能每次 malloc → CachingAllocator 存在的意义!
```

## 21. CUDA 面试八股文

> 本节合并了所有 CUDA 方向的面试八股题。


### Q: Warp 是什么？什么是 Warp Divergence？怎么避免？

> Warp 是 GPU 的基本调度单位，32 线程以 **SIMT** 模式**锁步执行**同一指令。
>
> **Warp Divergence**：Warp 内遇到 if-else 分支时，两个分支必须**串行执行**。总时间 = time(if) + time(else)。
>
> **避免**：让同一 Warp 走同一分支。如 `if (threadIdx.x / 32 < threshold)` 替代 `if (threadIdx.x % 2 == 0)`。
> **Volta+ 改进（Independent Thread Scheduling）**：Volta 架构引入独立线程调度，每个线程有自己的 PC（程序计数器）和调用栈，divergent 线程可以交错执行而非严格"先 if 后 else"。但仍有开销，最佳实践仍是避免 warp 内 divergence。
>
> **项目中的 Divergence 实例**：
> 1. **GEMV warp reduce**：`if (lane_id == 0) output[n] = sum * scale` — 只有 lane 0 写结果，其他 31 线程空闲。但仅 1 条指令，影响可忽略。
> 2. **FlashAttention tile 边界**：最后一个 tile 的 `tile_len < Bc`，循环 `for (t < tile_len)` 导致部分线程提前退出，仅末尾 tile 受影响。
> 3. **GEMV 主循环无 divergence**：`for (i = lane_id; i < K4; i += 32)` 保证 warp 内所有线程同进同退（K4 对 32 整除时完美，不整除时仅最后一轮有 ≤31 个空闲线程）。
>
> **设计原则**：把分支条件设计为 warp 粒度（warp 内所有线程走同一路径）。面试口诀：`threadIdx.x / 32` 分支安全，`threadIdx.x % 2` 分支危险。

### Q: 什么是合并访存？最小传输单位是什么？

> Warp 32 线程访问连续且对齐的内存 → 合并为少量传输事务。最小单位 **sector = 32B**，cache line = 128B = 4 sectors。
>
> 完全合并：32 线程连续 128B → 1 次传输；stride-2 → 2 次（利用率 50%）；随机 → 最多 32 次（利用率 3%）。项目所有 Elementwise 算子用 float4 + Grid-Stride Loop 保证合并。

### Q: float4 向量化的原理和收益？有什么陷阱？

> `float4` 16B，一条 `LD.128` 加载 4 个 float。**收益**：指令数减 4×、LSU 效率提高、cache line 利用率 100%。
>
> **陷阱**：向量化时如果同时缩小 Grid（每线程处理 4 元素→Grid 缩 4×），Occupancy 下降→不够 Warp 隐藏延迟→反而变慢。项目 SwiGLU 踩过这个坑——正确做法是保持 Grid 大小不变，用 Grid-Stride Loop。

### Q: Grid-Stride Loop 相比直接启动 N/256 个 Block 有什么优势？

> 固定 Grid（SM×8=272 Blocks），每线程循环 `for (i=tid; i<n; i+=stride)`。
>
> **优势**：①避免百万 Block 调度开销 ②相邻线程处理相邻元素→合并访存 ③SM×8 确保每 SM 有 8 波 Block，足够隐藏延迟。

### Q: Warp Shuffle 和 Shared Memory 归约区别？

> **Shuffle**：寄存器间直传 ~1 cycle，不需要 syncthreads，但只能 Warp 内（32 线程）。**SMEM**：~20-30 cycle，需要 syncthreads，可跨 Warp。
>
> 项目实践：两级组合——①Warp 内 Shuffle → ②SMEM 中转 + syncthreads → ③Warp0 再 Shuffle。能 Shuffle 就 Shuffle，跨 Warp 才用 SMEM。

### Q: __syncthreads 的作用？什么时候必须用？什么时候不需要？

> Block 级屏障，所有线程到达此处才继续。保证 SMEM 写入对所有线程可见。
>
> **必须**：跨 Warp 通过 SMEM 通信；Tiled SGEMM 搬运 tile 后和计算完当前 tile 后（两个 sync）。
> **不需要**：Warp 内通信（SIMT 天然同步）；Warp Shuffle；只读 Global Memory。

### Q: 什么是 Bank Conflict？怎么解决？

> SMEM 32 Banks，每 Bank 4B。多线程访问**同一 Bank 的不同地址** → 串行。`sA[32][32]` 按列访问 → 32-way conflict。
>
> **解决**：①Padding: `sA[32][33]`，每行多 1 float → 步长与 32 互质 → 0 conflict（项目采用）；②Swizzle/XOR: `sA[row][col^row]`，零空间开销（CUTLASS 采用）；③转置布局使访问按行连续。详见「面试复盘补充」部分。
>
> **广播例外（Broadcast）**：同 warp 多线程访问同 bank 的**同一地址** → 不算 conflict，硬件广播（1 次读取分发给所有请求线程）。
>
> **项目中 Bank Conflict 分析**：
> - **GEMV kernel**: `x_smem[base]`，`base = i*4`，不同线程的 i 以 stride 32 分布 → `base` 间隔 128 bytes = 32 banks → 每线程命中不同 bank → **无 conflict**。
> - **FlashAttention**: `s_q[d]` 顺序读取（连续 bank），`s_k[t * head_dim + d]` 也是行内顺序 → **无 conflict**。
> - **如果要做 SMEM 上矩阵转置**（如 GEMM tiling 中 B 矩阵），`smem[32][32]` 按列读会产生 32-way conflict → 需要 padding `smem[32][33]`。
>

### Q: Tensor Core 是什么？怎么使用？

> 专用矩阵乘加硬件，一条指令 16×16×16 MMA。FP16 TC ~161 TFLOPS vs FP32 CUDA Core ~12 TFLOPS。
>
> **使用**：①cuBLAS 设 `CUBLAS_GEMM_DEFAULT_TENSOR_OP`（项目方式）②WMMA API ③PTX mma 指令。
> sm_89 支持 FP16/BF16/TF32/INT8/FP8。

### Q: cudaMalloc 为什么慢？推理框架怎么解决？

> 全局同步，~0.5-1ms。需要跨 PCIe 与驱动通信、扫描页表、同步 CPU/GPU。推理每 token ~200 次分配 → 100ms 纯开销。
>
> CachingAllocator 从缓存池 lower_bound 查找（~100ns），比 cudaMalloc 快 **5000 倍**。

### Q: Roofline 模型是什么？怎么判断算子瓶颈？

> AI = FLOP/Byte。拐点 = 峰值计算/带宽 = 12000/288 ≈ **41.7 FLOP/Byte**。
>
> AI < 41.7 → Memory-Bound；AI > 41.7 → Compute-Bound。
> Add(0.083)=MB、RMSNorm(0.42)=MB、SwiGLU(0.33)=MB、GEMM(170)=CB、Decode GEMV(0.5)=**MB**。


### Q: 你的 GPU 的 Roofline 拐点是多少？SGEMM 的 AI 怎么算？（面试追问）

> **RTX 4060 Ti (sm_89) 拐点**:
> FP32 峰值 = 22 TFLOPS, 带宽 = 288 GB/s → **拐点 AI = 22000 / 288 ≈ 76 FLOP/Byte**。
>
> **SGEMM 理论 AI**: 对于 M×N×K 的矩阵乘:
> - FLOPs = 2×M×N×K (每个输出元素需要 K 次乘加 = 2K 次浮点运算)
> - Bytes = 4×(M×K + K×N + M×N) (读 A, 读 B, 写 C, 每个 float 4B)
> - AI = 2MNK / (4(MK + KN + MN))
>
> M=N=K=4096 时: AI = 2×4096³ / (4×3×4096²) ≈ 682 FLOP/Byte → **远超拐点 76 → Compute-Bound**。
>
> **面试要点**: 能说出你 GPU 的具体拐点数值 + SGEMM 的 AI 公式，比只说"算力 vs 带宽"有力得多。


### Q: Kernel Launch 是同步还是异步？

> **异步**。CPU 推入命令队列(~5-15µs)后立即返回。`cudaGetLastError()` 检查配置错误（不等完成），`cudaDeviceSynchronize()` 等待所有 GPU 工作完成。

### Q: CUDA Stream 有什么用？默认 Stream 的行为？

> Stream 是 GPU 上的命令队列。**默认 Stream(0)**：所有操作串行。**多 Stream**：不同 Stream 的操作可并行执行。
>
> 注意：cudaMalloc 是**同步操作**——即使在非默认 Stream 上，也会阻塞 CPU 和 GPU。所以必须用 CachingAllocator 避免推理中调 cudaMalloc。

### Q: RMSNorm 的线程映射是怎样的？为什么一行一个 Block？

> Grid=(rows,1,1)，Block=(256,1,1)。**原因**：整行需要 reduce_sum，同一行的线程必须在同一 Block 内才能通过 SMEM + syncthreads 通信。如果把一行拆到多个 Block → 无法直接归约（需要 Argmax 那样的 Two-Phase 方案）。

### Q: SwiGLU 的作用是什么？

> FFN 的门控激活函数。`SwiGLU(x) = up(x) ⊙ SiLU(gate(x))`，其中 `SiLU(x) = x × sigmoid(x)`。gate 通过 sigmoid 产生 0-1 的门控值，控制信息通过率。比 ReLU 更平滑，训练效果更好。

### Q: 归约操作为什么用两阶段 reduce 而不是 atomicAdd？

> **atomicAdd 的问题**：① 同地址串行化（256 线程 atomicAdd 同一地址 → ~5000 cycle）。② FP32 atomicAdd 结果不确定（浮点加法不满足结合律，执行顺序不同结果微不同）。
>
> **两阶段归约**：Warp reduce（5 轮 `__shfl_down_sync` ≈ 10 cycle） → Block reduce（shared memory 汇总 + warp 0 归约 ≈ 20 cycle）→ 总计 ~30 cycle vs atomicAdd ~5000 cycle → **~170× 更快**。本质：归约是规则的树状通信，atomicAdd 是竞争式无序累加。


### Q: GPU 和 CPU 的设计哲学有什么区别？

> **CPU**: 少量核心(4-64)，大缓存(L1/L2/L3 共几十 MB)，复杂控制(分支预测/乱序执行)，优化单线程延迟。
> **GPU**: 大量核心(数千)，小缓存/大寄存器文件，简单控制(SIMT)，优化吞吐量。用大量线程隐藏延迟代替预测/乱序。
>
> 类比: CPU = 一个博士做一道题很快；GPU = 1000 个小学生做 1000 道简单题更快。

### Q: L1 Cache 和 Shared Memory 是什么关系？

> sm_89 上 L1 和 SMEM 共享同一块 128KB SRAM，可配置分割（如 64KB SMEM + 64KB L1，或 100KB SMEM + 28KB L1）。SMEM 是程序员显式管理的，L1 是硬件自动管理的。
>
> 项目 FlashAttention 动态申请 SMEM（`<<<..., smem_bytes>>>`），多了 → L1 变小 → 可能影响其他内存访问的 cache 命中率。

### Q: 什么是 Register Spilling？怎么避免？

> 每个线程使用的寄存器超过 SM 分配的额度 → 编译器将溢出的变量放到 Local Memory (实际在 GDDR6，有 L1/L2 缓存)。速度从 ~0 cycle 退化到 ~400 cycle。
>
> **避免方法**: 减少每线程的局部变量、减小 kernel 复杂度、用 `--maxrregcount=N` 编译选项限制。NCU 中 `Local Load/Store` 非零说明有 spilling。

### Q: 什么是 Warp Specialization？

> v3 FlashAttention 使用的技术。同一 Block 内不同 Warp 分工不同: **Producer Warp** 负责从 Global Memory 加载数据到 SMEM，**Consumer Warp** 负责计算。两类 Warp 通过 SMEM 双缓冲流水线协作 → 加载和计算重叠 → throughput 更高。
> 需要 Hopper (sm_90) 的异步拷贝指令 (TMA)。sm_89 不支持。

### Q: 什么是 Memory Coalescing 的 Sector 模型？

> GPU 内存控制器以 **32B Sector** 为最小传输粒度。一次内存请求可能触发 1-32 个 Sector 传输。
> - 完美合并: 32 线程连续 128B → 4 Sectors → 1 次请求
> - 最差: 32 线程随机 → 32 × 32B = 1024B → 实际只用 128B → 利用率 12.5%
>
> NCU 指标 `L1 Sectors/Request` 越接近 4 越好（理想合并）。

### Q: atomicAdd 的原理和开销？

> GPU 上 `atomicAdd(addr, val)` 是 Read-Modify-Write 原子操作。同一地址的多个 atomic 操作必须串行 → 多线程竞争同一地址会严重退化。
>
> FP32 atomicAdd: ~几十 ns/次（vs 普通 load ~400 cycles 但可流水线）。项目中避免使用——用 Warp/Block Reduce 归约到单线程后再写全局内存，不需要 atomic。

### Q: __threadfence() 和 __syncthreads() 有什么区别？

> `__syncthreads()`: Block 内屏障 + 内存可见性。所有线程等到此处才继续。
> `__threadfence()`: 只保证当前线程之前的写操作对其他线程可见（memory fence），不做线程同步。用于跨 Block 通信场景（如 Two-Phase Grid Reduce 中 Phase1→Phase2 的衔接）。



### Q: 什么是 CUDA Stream？为什么需要多个 Stream？

> **Stream** = GPU 上的指令队列。同一 Stream 内的操作按顺序执行，**不同 Stream** 的操作可并行。
>
> ```
> Stream 0: [MemcpyH2D_A] → [KernelA] → [MemcpyD2H_A]
> Stream 1:      [MemcpyH2D_B] → [KernelB] → [MemcpyD2H_B]
>                     ↑ 与 Stream0 的 KernelA 并行执行
> ```
>
> **典型用途**: 多 Stream 让**数据传输和计算重叠** (overlap)。当 GPU 在跑 KernelA 时，DMA 引擎可以同时拷贝 B 的数据。
>
> ```cpp
> cudaStream_t s1, s2;
> cudaStreamCreate(&s1); cudaStreamCreate(&s2);
> cudaMemcpyAsync(d_a, h_a, size, cudaMemcpyHostToDevice, s1);
> myKernel<<<grid, block, 0, s2>>>(d_b);  // 和 s1 的 memcpy 并行
> cudaStreamSynchronize(s1);  // 只等 s1
> cudaStreamDestroy(s1); cudaStreamDestroy(s2);
> ```
>
> **面试追问**: Default Stream (stream 0) 是同步 stream — 它和所有其他 stream 串行化。用 `--default-stream per-thread` 编译选项可以改变。

### Q: cudaEvent 怎么做精确计时？为什么不用 CPU 计时？

> ```cpp
> cudaEvent_t start, stop;
> cudaEventCreate(&start); cudaEventCreate(&stop);
> cudaEventRecord(start, stream);
> myKernel<<<grid, block, 0, stream>>>(...);
> cudaEventRecord(stop, stream);
> cudaEventSynchronize(stop);
> float ms = 0;
> cudaEventElapsedTime(&ms, start, stop);  // GPU 硬件计时, 精度 ~0.5μs
> cudaEventDestroy(start); cudaEventDestroy(stop);
> ```
>
> **为什么不用 CPU 计时**: CPU `clock_gettime` 包含了 kernel launch 开销 (~5-15μs) + 驱动开销。cudaEvent 在 GPU 端直接打时间戳，准确反映 kernel 本身的执行时间。
>
> **cudaEvent 还能做同步**: `cudaStreamWaitEvent(stream, event)` — 让一个 stream 等另一个 stream 的某个事件完成。

### Q: 什么是 Pinned Memory？为什么比普通内存快？

> Pinned Memory (页锁内存) = `cudaMallocHost()` 分配的 Host 内存。
>
> | | 普通内存 (malloc) | Pinned Memory (cudaMallocHost) |
> |---|---|---|
> | 可被 OS 换出 (page out) | ✅ | ❌ 锁定在物理内存 |
> | cudaMemcpy 方式 | CPU 先拷到临时 pinned buffer → 再 DMA | **直接 DMA 传输** |
> | 传输速度 | ~12 GB/s (PCIe3 实测) | ~24 GB/s (PCIe3 理论峰值) |
> | cudaMemcpyAsync 支持 | ❌ 退化为同步 | ✅ 真正异步 |
>
> **代价**: 占用不可换出的物理内存。分配过多 → OS 可用物理内存减少 → 系统性能下降。
>
> **项目中**: 模型权重加载时可以用 pinned memory 加速 Host→Device 传输。


### Q: malloc / cudaMallocHost / cudaMalloc 三者有什么区别？（面试追问）

> | API | 分配位置 | 特点 |
> |------|----------|------|
> | `malloc()` | CPU 内存 (Host RAM) | 普通虚拟内存，可被 OS 换页 |
> | `cudaMallocHost()` | CPU 内存 (Host RAM) | **页锁定 (pinned)**，不可换页，DMA 可直接访问 |
> | `cudaMalloc()` | GPU 显存 (Device VRAM) | 设备内存，不涉及 pinned 概念 |
>
> **常见混淆**: cudaMalloc ≠ "普通内存"。它是 GPU 显存，和 Host 内存是两个独立的物理空间。
>
> **cudaMemcpyAsync + 普通 malloc 的退化路径**:
> ```
> 普通 Host 内存 → (CPU 同步拷贝到临时 pinned buffer) → (DMA 异步传到 GPU)
>                    ↑ 这步阻塞了 CPU，所以不是真异步
> ```
>
> **cudaMemcpyAsync + cudaMallocHost**:
> ```
> Pinned Host 内存 → (DMA 直接异步传到 GPU)  // CPU 立即返回
> ```


### Q: 怎么选择合适的 Block Size？

> **经验法则**:
> 1. Block size 必须是 **32 的倍数**（Warp size）
> 2. 常用: **128** 或 **256**。极少用 32（太小，Occupancy 低）或 1024（寄存器压力大）
> 3. 目标: 让每个 SM 有足够 Warp 隐藏延迟
>
> **计算方式**:
> - SM 最大线程数 = 1536 (sm_89)
> - 每 Block 256 线程 → 每 SM 最多 6 Blocks → 1536 线程 → Occupancy = 100%
> - 每 Block 128 线程 → 每 SM 最多 12 Blocks，但 max blocks/SM = 16 (sm_89)，还要看寄存器/SMEM 限制
>
> **项目中**: FlashAttention 用 256 threads/block（8 Warps，4 Warps 做 Reduce 已够用）。Add/Embedding 等简单算子也用 256。
>
> **面试追问**: 用 `cudaOccupancyMaxPotentialBlockSize()` 可以让 CUDA runtime 自动选最优 block size。

### Q: 什么是 Tensor Core？怎么编程使用？

> **Tensor Core** = GPU 中专门做**矩阵乘加 (MMA)** 的硬件单元。
> - sm_89 (Ada): 每个 SM 有 4th gen Tensor Core
> - 一条指令完成 `D = A × B + C`，其中 A/B/C/D 是小矩阵（如 16×16×16）
> - FP16 Tensor Core 吞吐: ~330 TFLOPS (vs FP32 CUDA Core ~83 TFLOPS) → **4倍差距**
>
> **编程方式 (三层)**:
> | 层级 | API | 难度 |
> |------|-----|------|
> | cuBLAS | `cublasGemmEx()` | 最简单，推荐生产使用 |
> | WMMA (Warp-level) | `wmma::load_matrix_sync / mma_sync / store_matrix_sync` | 中等，可定制 |
> | PTX MMA | `mma.sync.aligned.m16n8k16.f32.f16.f16.f32` | 最底层，CUTLASS 使用 |
>
> ```cpp
> // WMMA 示例 (C++):
> #include <mma.h>
> using namespace nvcuda::wmma;
> fragment<matrix_a, 16, 16, 16, half, row_major> a_frag;
> fragment<matrix_b, 16, 16, 16, half, col_major> b_frag;
> fragment<accumulator, 16, 16, 16, float> c_frag;
> fill_fragment(c_frag, 0.0f);
> load_matrix_sync(a_frag, sA, 16);
> load_matrix_sync(b_frag, sB, 16);
> mma_sync(c_frag, a_frag, b_frag, c_frag);  // D = A*B + C
> store_matrix_sync(sC, c_frag, 16, mem_row_major);
> ```
>
> **项目中**: SGEMM Level 7 使用 Tensor Core (通过 cuBLAS 间接使用)。直接编程 Tensor Core 是 CUTLASS/Triton 做的事。

### Q: cudaMemcpy 和 cudaMemcpyAsync 有什么区别？

> | | `cudaMemcpy` | `cudaMemcpyAsync` |
> |---|---|---|
> | 行为 | **阻塞** CPU 直到传输完成 | 立即返回，传输在指定 stream 中异步进行 |
> | Host 内存要求 | 任意 | 必须是 **pinned memory**，否则退化为同步 |
> | 常见用途 | 简单场景、调试 | 生产环境、overlap 计算和传输 |
>
> **面试追问**: 为什么 cudaMemcpyAsync 用普通内存会退化？→ DMA 引擎直接操作物理地址。普通内存可能被 OS page out → 物理地址失效 → 必须先拷到 pinned buffer → 等拷完 → 同步了。

### Q: Nsight Compute 和 Nsight Systems 分别用来做什么？

> | 工具 | 粒度 | 用途 |
> |------|------|------|
> | **Nsight Systems (nsys)** | 系统级 timeline | CPU/GPU 时间线、kernel 调度间隔、Stream 并发、API 调用开销 |
> | **Nsight Compute (ncu)** | 单个 kernel | SM Occupancy、内存带宽利用率、L1/L2 hitrate、指令混合、roofline 分析 |
>
> **典型优化流程**:
> 1. 先用 **nsys** 看全局 → 找到瓶颈 kernel（耗时最长的那几个）
> 2. 再用 **ncu** 对那几个 kernel 做 roofline 分析 → 确定是 compute-bound 还是 memory-bound
> 3. memory-bound → 优化合并访存、用 SMEM / 向量化
> 4. compute-bound → 优化指令使用（Tensor Core、FMA）
>
> **项目中**: Profile 脚本 `scripts/profile_ops.py` 调用 ncu 收集各算子指标。SGEMM 优化的 5 个 Level 就是根据 ncu 的 Roofline 分析逐步改进的。

### 7. Tiled SGEMM
```cuda
#define T 32
__global__ void sgemm_tiled(float* C, const float* A, const float* B,
                            int M, int N, int K) {
    __shared__ float sA[T][T+1], sB[T][T+1]; // +1 padding
    int r = blockIdx.y*T+threadIdx.y, c = blockIdx.x*T+threadIdx.x;
    float sum = 0.f;
    for (int t = 0; t < K; t += T) {
        sA[threadIdx.y][threadIdx.x] = (r<M&&t+threadIdx.x<K) ? A[r*K+t+threadIdx.x] : 0.f;
        sB[threadIdx.y][threadIdx.x] = (t+threadIdx.y<K&&c<N) ? B[(t+threadIdx.y)*N+c] : 0.f;
        __syncthreads();
        for (int k=0; k<T; k++) sum += sA[threadIdx.y][k]*sB[k][threadIdx.x];
        __syncthreads();
    }
    if (r<M&&c<N) C[r*N+c] = sum;
}
```

### Q: C 函数指针表多设备抽象有什么缺陷？怎么改进？

**A**: 现有设计缺陷：
1. **类型不安全** — 函数指针 `void*` 转型无编译期检查，参数传错只会运行时崩溃
2. **扩展性差** — 新增 API 需修改结构体 + 所有后端注册，容易遗漏
3. **无能力查询** — 无法知道后端是否支持某功能（如某后端不支持 INT4）
4. **错误处理不统一** — cudaError_t/mxError_t 等各自不同

改进方案：
1. **Device Capability 查询** — 类似 cudaGetDeviceProperties，上层查询后端支持的 dtype/op
2. **Plugin/Registry 机制** — 后端编译为 .so，dlopen 动态加载，类似 PyTorch PrivateUse1
3. **统一错误码** — 定义 llaisys_error_t 枚举，各后端 compat 层翻译
4. **Op 级注册** — 当前 Op 层是 `#ifdef` 源码级分支，可改为 dispatch table 动态注册

**Trade-off**: 现有方案对 3 后端够用且零运行时开销；Plugin 架构适合 10+ 后端但增加复杂度。

### Q: 简述 cudaMalloc 导致性能灾难的根因？143× 加速的关键路径？

**A**: cudaMalloc 的真正问题是**隐式全局同步** — 它会 drain 整个 GPU pipeline，等待所有在飞 kernel 完成，代价远超分配本身的延迟。

143× 加速关键路径：
1. **内存池化** — 启动时一次性分配，推理期间零 malloc/free
2. **预计算** — RoPE freq_cis 等常量预先计算并驻留 GPU
3. **KV Cache 预分配** — 按 max_seq_len 预留，decode 时只更新一行
4. **算子融合** — RMSNorm + 量化/反量化 减少 kernel launch 次数

### Q: 8GB 显存部署 7B 模型的完整估算？（追问复习）

**A**: 7B 参数 × 4 bytes/FP32 = 28GB → 远超 8GB。

**量化路径**:
- FP16: 7B × 2 = **14GB** → 超，不行
- INT8: 7B × 1 = **7GB** 权重 + ~0.5GB KV Cache + ~0.5GB 激活 ≈ **8GB** → 刚好
- INT4: 7B × 0.5 = **3.5GB** 权重 → 余量大，推荐

**KV Cache 估算** (以 LLaMA-7B 为例):
- 每层: 2(K+V) × seq_len × num_kv_heads × head_dim × 2(FP16) 
- 32 层, 2048 seq_len: 32 × 2 × 2048 × 32 × 128 × 2 ≈ **1GB**

**面试回答框架**: ① 先算 FP32 基线 → ② 选量化方案 → ③ 加 KV Cache → ④ 加激活/临时缓冲 → ⑤ 留 10% 余量

### Q: PyTorch 是怎么做多后端 dispatch 的？（追问新知识）

**A**: PyTorch 使用 **C++ Dispatcher** (c10::Dispatcher) 实现多后端分发：

1. **DispatchKey** — 每个 Tensor 携带 dispatch key（CPU / CUDA / XLA / MPS / PrivateUse1 等），表示所在后端
2. **注册机制** — 各后端通过 `TORCH_LIBRARY_IMPL(aten, CUDA, m)` 注册自己的算子实现
3. **运行时分发** — 调用 `torch.add(a, b)` → Dispatcher 查 a 的 DispatchKey → 查表 → 调用对应后端的 `add_cuda` 实现
4. **Fallback 链** — 没注册的 key 沿 fallback 链查找（如 AutogradCUDA → CUDA → CompositeImplicitAutograd）

**与 LLAISYS 对比**:
| | PyTorch | LLAISYS |
|--|---------|---------|
| 机制 | DispatchKey + 注册表 | C 函数指针表 |
| 新增后端 | `TORCH_LIBRARY_IMPL` 注册 | 修改结构体 + #ifdef |
| 运行时分发 | 查 Tensor 的 dispatch key | 显式传入 `runtime_api` 指针 |
| 扩展性 | 极强（PrivateUse1, 第三方可 out-of-tree 注册） | 需源码修改 |

### Q: std::move 之后原对象是什么状态？（追问复习）

**A**: 标准定义：移动后对象处于 **"valid but unspecified"** 状态。

关键要点：
1. **std::move 本身不移动** — 只是 static_cast 到右值引用（`static_cast<T&&>(x)`）
2. **移动构造/赋值才真正转移资源** — 如 `string b = std::move(a)`，a 的内部指针被偷走
3. **移后状态**:
   - `std::string`: 通常变为空串 `""`（但标准不保证）
   - `std::vector`: 通常 `size() == 0`
   - `std::unique_ptr`: **保证为 nullptr**（标准明确规定）
4. **可以安全做的操作**: 赋值、析构。**不建议做的操作**: 读取内部值（结果未定义）

```cpp
std::string a = "hello";
std::string b = std::move(a);  // a 被移动
// a 是 valid but unspecified
a = "world";  // OK: 重新赋值后可正常使用
```

### Q: GPU 内存层次完整对照表（追问复习）

**A**: 从快到慢的完整层次：

| 层级 | 典型大小 | 延迟 (cycles) | 延迟 (ns) | 可见性 |
|------|---------|--------------|-----------|--------|
| Register | 每线程最多 255 个 32-bit | ~1 cycle | ~1 ns | 单线程私有 |
| Shared Memory | 每 SM 48-228 KB (可配置) | ~20-30 cycles | ~2-4 ns | Block 内所有线程 |
| L1 Cache | 每 SM 128-256 KB | ~28-33 cycles | ~20 ns | 单 SM (硬件管理) |
| L2 Cache | 全芯片共享 4-50 MB | ~200+ cycles | ~100-150 ns | 所有 SM 共享 |
| Global Memory (HBM/GDDR) | 8-80 GB | ~400-600 cycles | ~200-400 ns | 全局, Host 也可访问 |

**关键考点**:
- **L1 与 Shared Memory 物理上共享同一块 SRAM**（Volta 以后统一，可配置分割比例）
- **Global Memory 是逻辑概念**，物理上由 HBM2/HBM3/GDDR6 实现
- **面试说延迟用 cycles 更专业**，因为 ns 取决于 GPU 频率
- Constant Memory / Texture Memory 是 Global Memory 的特殊缓存访问路径

### Q: shared_ptr 引用计数的线程安全机制？（R4-Q16）

**A**: 控制块中 `use_count` 和 `weak_count` 是 `std::atomic<long>` 类型，增减操作用 lock-free 原子指令（x86 上是 `lock xadd`），**不是 CUDA atomicAdd**。

**线程安全三级分类**:
| 操作 | 安全？ |
|------|--------|
| 多线程读同一 shared_ptr | ✅ |
| 多线程读不同 shared_ptr（同一对象） | ✅ |
| 一写一读同一 shared_ptr 实例 | ❌ 指针赋值非原子 |
| 多写同一 shared_ptr 实例 | ❌ |
| 访问管理的对象本身 | ❌ shared_ptr 不管 |

C++20: `std::atomic<std::shared_ptr<T>>` 可实现实例级线程安全。

### Q: 什么是 SM Occupancy？越高越好吗？（R4-Q17）

**A**: Occupancy = Active Warps per SM / Max Warps per SM。如 SM 最大 64 warps，当前 kernel 只能跑 32 → 50%。

**影响因素**: 每线程寄存器数、每 Block SMEM 用量、Block 大小。

**不是越高越好**: 高 Occupancy → 每线程可用寄存器少 → 可能 Register Spilling → 溢出到 Local Memory（实际走 Global Memory）→ 反而更慢。延迟被充分隐藏后，再增加 Occupancy 无额外收益。

**低 Occupancy 高性能例子**: SGEMM 的 Register Tiling，每线程计算 8×8 子矩阵，用 ~128 寄存器，Occupancy 仅 25-50%，但数据复用率极高，不需要靠 Warp 切换隐藏延迟。

### Q: CachingAllocator 只增不减怎么办？设计归还策略？（R4-Q18）

**A**: 设计分层归还策略:
1. **被动归还**: OOM 时先释放 free list 空闲块，`cudaFree` 归还 OS，再重试（PyTorch `empty_cache()` 做法）
2. **主动归还**: 提供 `trim()` API，模型切换时调用
3. **水位线策略**: high_watermark = GPU显存 × 90%，low_watermark = 70%，超高水位线时释放到低水位线
4. **释放粒度**: 按大块 (>20MB) 单独管理，小块合并后归还，类似 glibc malloc 的 madvise

注意: `cudaFree` 也有隐式同步开销，不能频繁调用。

### Q: FlashAttention 的 Prefill 和 Decode 应该共用 kernel 吗？（R4-Q19）

**A**: **不应该共用**。

| | Prefill | Decode |
|--|---------|--------|
| Q 形状 | [seq_len, head_dim] (大) | [1, head_dim] |
| Bound | Compute-bound | Memory-bound |
| 优化重点 | GEMM throughput | 减少 KV Cache 读取 |
| 并行策略 | 多 Block 沿 Q 维度并行 | Q 维度无并行，需沿 KV 维度拆分 |

Decode 阶段应使用 **FlashDecoding**: 多个 Block 各自处理 KV 的不同段，最后 reduce 合并，提升 SM 利用率。

**IO 复杂度**: 标准 Attention O(Nd + N²)，FlashAttention O(Nd + N²d²/M)，M 是 SRAM 大小。

### Q: 如何在推理引擎中支持 Continuous Batching？（R4-Q20）

**A**: 需改 4 个模块:
1. **Scheduler（新增）** — 维护 waiting/running 队列，每个 decode step 动态组 batch，请求可随时加入/退出
2. **KV Cache Manager（重构）** — 从连续预分配改为 PagedAttention: 固定大小 Page 池 + Page Table 做逻辑→物理映射，请求结束后 Page 归还
3. **Attention Kernel（修改）** — 支持 variable-length，输入从 [B, seq, dim] 变为 packed [total_tokens, dim] + offsets
4. **Position Encoding（修改）** — 每请求各自维护 position，RoPE 不再全局递增

**PagedAttention 类比**: 虚拟内存之于物理内存 = PagedAttention 之于 KV Cache。
